# 修票草案：多仓票「声明了但没动」的仓被 merge_check 判红

> 本文是**开票前的票面草案**，不是已成立的工单。定稿并开票前需宿主确认 §6 的三个判据。
> 全部结论基于只读核查（读代码、读票面、读 git 记录），**未实跑引擎验证修法**。

## 1 一句话问题

票面写集覆盖了一个仓、而该仓本票确实不需要任何改动时，`merge_check` 的「泳道分支有 commit」判据必判红 → 票在最后一道机械门前**无正当出路**：agent 要么伪造一个无意义改动过闸，要么整票作废。

## 2 判据的精确粒度（**先读这条，防改错**）

**判据粒度 = 仓，不是目录、不是写集条目。**（此条应作为验收第 0 条钉住，见 §5）

| 写集情形 | 是否判红 |
|---|---|
| 某**目录**在写集内、该目录未改动，但同仓别处有 commit | **不红**（条目合并进「该仓有无 commit」一条判定） |
| 某**仓**在写集内、该仓整体零 commit | **红**（本次要治的形态） |
| 某仓有未提交改动（无 commit） | **红**（既有职责：实现未落盘），本次保留 |

机制依据：

- `shared.resolve_repos_for_paths`（`shared.py:1615`）按**最长前缀**把写集条目归属到仓，返回 `{仓: [条目…]}`——多个目录落进同一仓后被合并；
- `shared.build_repo_worktrees`（`shared.py:1720`）按归属结果生成仓级泳道清单（**写集是泳道推导的唯一输入**）；
- `agent_activities._lane_scopes`（`agent_activities.py:2384`）产出**每仓一条** scope；
- `agent_activities.merge_check`（`agent_activities.py:3570/3602-3614`）逐 scope 跑核心判据，多仓时给红项加 `[仓名]` 前缀。

⇒ **目录级空承诺是安全的，仓级空承诺才致命。** 修法**不得**改成「逐条目要求落盘」——那会把正确的东西改错。

## 4 根因（三层，第三层是本次的关键）

**① 判据把「许可面」当成了「义务清单」（本次真正根因）**

`agent_activities.py:3196-3199`：逐 scope 跑 `git log base..branch`，判据 `green = returncode==0 and n>0`。

而引擎**自己在另一处已经写下了相反的口径**——`shared.py:3223-3224`（`refresh_write_set` 注释）原文：

> 「verify_lane 的白名单是**允许写的上限，不是必须清单**，多余的文件只是多留余量——不亮红、不进 diff」

**同一份代码里两个口径直接对立。** ⇒ 本次不是「要实现一个新设计」，而是**把 merge_check 对齐到引擎已有的口径**。这决定了本票的性质与成本。

**② 同一判据在引擎另一处已按正确口径实现（现成先例）**

`shared.py:3300`（机械复核闸）：

```
if lane_commits == 0 and not no_file_changes:   # ← 整票级，且有豁免入口
```

- 机械复核的 0-commit 门是**整票级**（整票 0 commit 才打回），且有 `no_file_changes` 声明可豁免；
- `merge_check` 的同类判断却在**逐仓级**、且**无任何豁免入口**。
- 同一个概念、两套判据；多仓票只在后者上失败。⇒ 修法＝**统一到前者**。

**③ 附带缺口（同票顺手收，成本极低）**

- **文案误导**：`agent_activities.py:3205-3206` 的 `next_action` 把「确实无需改动」与「实现段没落盘」混为一谈，指向「发 rework 回 implement」——实证按它打回一轮，结论不变，只烧一轮。
- **红项可见性**：前一项红会短路后续判据，票面四项全红，读起来像「整个仓都坏了」。建议区分「真红项」与「被短路项」。
- **无测试覆盖**：现有测试里「泳道分支有 commit」**只有桩值**（`tests/test_t26091620_nested_repo_guards.py:306`、`tests/test_t260915_01_detail_face.py:247` 均为 green 桩），**从未覆盖「多仓某仓合法 0 commit」**——这是它长期未被发现的直接原因。

## 5 验收判据（逐条可判定）

**第 0 条（粒度锁）**：判据粒度**必须**保持为「仓」。验收方式：构造一条写集含**多目录**（其中若干目录零改动）、同仓有 commit 的票 → **必须不红**。（防做的人顺手改成逐条目要求落盘。）

1. **多仓 × 某仓零改动 × 零 diff** → 推进（不红）；且该仓在回执/记录里**点名可见**（不静默）。
2. **多仓 × 某仓零 commit × 有 diff** → **仍红**（保留「实现未落盘」的原红）。
3. **整票零 commit**（所有仓都 0 commit）→ **仍红**（原防伪需求不丢；对齐机械复核整票级口径）。
4. **越写集的改动** → **仍红**（既有职责，不动）。
5. **单仓票零回归**：单仓票判据行为逐字节不变。
6. **顺带项**：文案区分「确实无需改动」与「实现未落盘」；被短路项与真红项在票面可区分。
7. **回归用例落盘**：多仓场景须进 `integration/`（引擎侧 UT 之外），并**同时进场景清单**。
