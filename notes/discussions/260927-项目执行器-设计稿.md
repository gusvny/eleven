# 项目执行器（project-executor）——常驻执行器会话、事件账与独立守望者

> **代号**：立项代号＝**项目执行器**（英文 project-executor，宿主 260927 定）。其中常驻会话的名字
> 就是 **project executor**——原名 tick，宿主 260927 定名时统一改为 project executor。
> 「请你办事」的那一层叫 **请求**（界面标签 `Requests`）——早先叫过「待决事项 / Decisions」，
> 宿主 260927 指出：**对象是"问"，不是"答"**，改名见「请求怎么写」一节。
> 界面 mock 见同目录 `260927-项目执行器-mock.html`（tab 可点）。
>
> **来源**：宿主 260927 会话，六轮讨论定稿输入。宿主原话要点：
> ①「dsh 有没有一个能力，session 或者工单需要人介入了就发出声音提醒」；
> ②（范围修正）「我在 session 里开着 ticket，session 做了代签和 block 修复，只有 session 认为
> 我需要介入的时候、或者这个 session 出问题的时候，我才需要提醒」；
> ③「我基本一直开着控制台页面，响在页面里就够」「一声就够，别烦我」；
> ④「这个 deepseek 的 session 的方式还是有点原始，对话一多就漏掉前面说的，也不知道哪些需要我
> 关注、哪些需要我做决定」——「要通用的，每个项目其实都应该有一个 tick session」；
> ⑤「每个 tick 轮询这件事情也有点傻，完全可以基于 ticket 的状态变化来 notify」；
> ⑥架构输入五条（见 Proposal 第一段）。
>
> **本文只写「是什么、为什么」**：接口形状、字段、命令、路径等实现细节在各实现票里定；

## Problem（问题）

1. **一句话**：工单是**自主推进**的——会话自己代签、自己修卡住的票；但它**停下来等人**时、
   或者**自己出了毛病**时，没有人被叫到；而人一旦要去盯，就得盯一整条又长又杂的会话流水。

2. **背景知识**（没参与过的人要先知道）：
   - **工单会话**：一个项目的常驻 agent 会话，替宿主驱动本项目的工单——查问题、定位、代签放行、
     把卡住的票推起来。它**不是**泳道里的开发/集成角色：那些是干活的（会被派活、会改代码），
     工单会话是**站在宿主这一侧做决策与推进**的。
   - **两种「需要人」**：会话主动要人（要授权、要拍板、要你答一句话），和会话被动出事
     （报错、异常结束、看着在跑其实卡死）。两者都不是"看板上有张票在等人"——票上的中间等待
     状态会被会话当场消化掉，拿看板当提醒源必然误报。
   - **上下文会丢**：会话一长就会被压缩成摘要（细节必然丢），会话进程重建后是从零开始；
     仓里 260918 有实测（某日 5 张票出现 115 次「恢复会话失败 → 从零新建」的失忆重跑）。
     所以**不能把重要状态寄托在对话里**。
   - **票的时间线在哪**：票的阶段时间线是工作流的**内存状态**，由 Temporal 的事件历史重放重建；
     读它要走**查询**，而查询必须由**在线 worker** 应答——worker 不在，读不到。
     仓里旧的那份磁盘投影已退役，当前**没有第二份可读**：跨票"发生了什么"今天读不到。

3. **证据**（260927 实测，非推测）：
   - dsh 本体**没有**声音/桌面通知能力：全部官方包里检索「声音/静音/音量/提示音/未读/注意」
     与「浏览器通知/音频/改标题/图标闪烁」**零命中**；钩子协议支持的事件里**没有**"等你输入"这一类。
   - 但 dsh **知道**有人在等：客户端有一张按会话索引的「待办交互」表（授权请求/提问/计划确认），
     宿主侧会话服务**可以对任意会话投递一轮输入**（排队追加或打断当前轮）——「提醒」与「唤醒」
     两条路都现成。
   - 控制台今天靠轮询：看板 5 秒拉一次**本项目的整张票表（含已结束）**、健康与 worker 各 5 秒，
     且都带可见性门（页签不可见即停）；每次拉取后端都要起一次引擎客户端进程去问 Temporal。
     引擎侧另有 15 秒的在跑票巡检（不属浪费，见 Nongoal）。
   - 引擎**已经在状态迁移那一刻产生事件**：票面 `timeline` 每次状态变化一条、`meta.log` 记带话注记，
     并且每次都会打一行 worker 日志。缺的不是事件，是**跨票的平铺流**。
   - 宿主实据：一直开着控制台页面、只要页面内提醒、一声就够、停摆阈值要可配置。

## Requirement（需求）

每条都能当验收标准：

1. **一个项目一个常驻执行器会话**（project executor），项目接入后**该位置永远存在**：会话内容可被结算后更换，
   但位置本身不消失、可随时被唤醒继续干活。
2. **引擎产出工单事件流**：票的状态变化落到**按项目一份**的追加式日志；流里认得出「哪张票、哪一段、
   什么状态、什么时候、第几轮」，并带**去重用的幂等键**。
3. **有变化就唤醒会话**：事件账出现新内容后，**在会话之外**的一方负责把会话叫起来去看
   （排队投递，不因会话当时正忙而丢失）；会话被卡住超过阈值时**升级为人**。
4. **权限有地方设、且由引擎判定**：每个项目可在设置页配置该会话能做什么——**分三组**：
   引擎动作（签/打回/重跑/开票/暂停恢复/清场）、**仓库动作**（主树直修、进泳道动手、提交）、
   元权限（开授权/扩范围，永远只有宿主本人）。**设置页只是编辑面，判定点在引擎**——改配置绕不开引擎的闸。
5. **它会动手，所以动手必须留证**：主树直修、进泳道动手这类**不可逆且绕开合并闸**的动作，
   每一次都要在事件账里留一行（改了什么面、凭什么依据、怎么验证的），并附**修后实测证据**
   （跑过什么、结果如何）。禁止"声称改了、实际没改"。
6. **两条轨的判据是规则，不是临场感觉**：发现问题后走「自己动手修」还是「开票外包」，
   由写死的判据决定（见 Proposal），并且判据本身可被审。
7. **会话不许自己给自己扩权**：授权只能由宿主（或宿主明确指定的身份）开，会话只能用；授权记录
   必须带范围、理由与到期时间。
8. **请求有独立落点与独立入口**：需要人决定的事项有一条可查询的账（待定/已定/已废），
   **不与事件流同文件**、**不与工单同列**、**不叫 todo**（避免与工单混淆）；未答复的请求
   **在任何清理动作下都不得被删除**。
9. **提醒可配置**：提醒的方式、开关、发声时机（含夜间）、以及哪些级别必须发声，**全部是配置项**，
   不是写死的规则；同一件事不重复提醒。会话只报边界变化（要你决定／要你知道／不用管）。
10. **界面有独立入口**：左栏一个项目一行、项目名即入口；点开后中间栏是该项目的执行器面板
    （tabs：Overview / Settings / Alerts / Requests）。**对话沿用现有 UI**，面板只提供跳转入口。
11. **「实在不行才叫人」有硬判据**：会话能自主做的事与必须升级的事各有一份明确清单（见 Proposal），
    升级请求**不阻塞**会话（落成带默认动作的请求，会话继续干别的）。
12. **不静默降级**：事件流读不到、对账不一致、守望者自身停止心跳，都必须**显式可见**
    （标注数据可能过期 + 原因），绝不允许"看起来一切正常"。
13. **重启后可重建**：这套东西**没有 workflow/worker 背书**，所以重启后的恢复必须是机械的、按序的——
    启动即**全量对账**（不信任内存里的水位线）、**孤儿手显式标注**（起了没有结束的手）、
    半截动作按证据复核、**已报过的提醒不重播**。事实不因重启改变，重启只让"手"重新长出来。
14. **请求必须写得能独立读懂**（宿主 260927：「decision 要好好做一下，要说人话、把背景说清楚、
    选项解释要明了、还要能追问」）：一条请求自带**问题（人话的问句）+ 为什么落到你 + 自足背景 +
    选项各自"选了会怎样"与可逆性 + 建议与理由 + 默认动作 + 期限 + 谁被卡住 + 证据指针**；
    支持在**这条请求的线程里追问**，追问与回答都留在它的历史里。
15. **验收动作**（人可复现）：
    - 会话提问或请求批准 → 不盯屏幕，10 秒内听到声音并看到可分辨来源的通知；
    - 会话假死（在跑但长时间无推进）→ 超过阈值后同样被叫到；
    - 会话被自己的审批卡住 → 守望者直接报「它在等自己」，不等超时；
    - 同一件事不处理 → 不再重复响；处理后再出现新事 → 再响；
    - 关掉提醒开关 → 完全静音，其余功能不受影响；
    - 事件账人为删空 → 对账能补齐并把「曾缺失 N 条」记进账；
    - 它做过的每一次主树直修 → 在事件账与面板 `Did today` 里都能逐条查到依据与验证证据；
    - **控制台重启一次** → 不缺事件（补齐并留痕）、不重播旧提醒、孤儿手被点名、半截直修能从
      commit 停点续上。

## Nongoal（不做什么）

1. **不把会话自己当提醒者**。会话可能被审批卡住，由它负责喊人等于让被卡住的人去求救。
2. **不做「共享 Temporal 的数据库」**。实测：该库是回滚日志模式（`journal_mode=delete`，
   无 `-wal`/`-shm`），读者与写者互相阻塞——长读可以让引擎写入失败；且它是内部存储，
   版本一迁就碎，换存储形态（真 Temporal + 服务型数据库）即失效。历史要走官方导出面。
3. **不改引擎里"确保每张在跑的票都有 worker"的 15 秒巡检**。那不是浪费，它本身就是存活判据。
4. **不把票的状态抄一份进事件账**。事件账是派生投影，只记变化，不记当前状态。
5. **不碰 dsh 本体**：不向上游提需求、不打补丁；只用它对外公开的能力（会话投递、待办交互状态）。
6. **不做跨机/多机**：账与守望者是单机形态；跨机另立需求。
7. **不在任何文档里手工维护请求或进度**：给人看的清单永远是**渲染物**。
8. **不许用直修绕过该走泳道的活**：直修只用于「声明允许直修的面」上的修；不许把在飞泳道的工作抢到主树侧做
   （那会制造两处并行改动、必冲突）。
9. **禁碰面不许碰**：控制台、别的项目、保护名单、未声明的面——即使"全权"下也照样拒绝
   （由引擎闸机械拦，不靠会话自觉）。
8. **本期不做**「把事件写账做进活动内直写」之外的引擎改造（例如新的用户级实体、新的签名流程）。

## Proposal（方案）

### 宿主给出的架构（本稿以此为骨）

1. **改引擎**：把工单事件的变化输出到追加式日志，**按项目一份**。
2. **每个项目有一个常驻会话**，位于会话入口的第一位，用同一代号（project executor）。
3. **设置页**：配置这个会话有什么权限、能做什么（例如代签）。
4. **日志一变，就唤起该会话去查看**；会话按自己的权限决定要不要推进。
5. **请求也要有地方存**——与事件账同机制、**不同文件**（理由见下方取舍）。

### High level：四个部件，一条链

```
引擎（状态迁移那一刻）
   └─ 写一行事件 → 项目级事件账（追加式、带幂等键、可重建）
                        │
                        ▼
                 独立守望者（宿主侧，非 agent）
                   ├─ 追事件账（增量）
                   ├─ 对账票面真源（走可见性列表，不依赖 worker）
                   ├─ 判活（自身心跳 / 引擎存活 / 会话是否还在推进）
                   ├─ 判自锁（会话在等一个"它自己发的"请求）
                   └─ 出决定：唤醒会话（排队投递）或 叫人（声音/通知/请求账）
                        │
                        ▼
                 工单会话 project executor（agent 回路，可被授权代签）
                   ├─ 被唤醒后读「简报」：事件账增量 + 请求 + 票面
                   ├─ 按在案权限推进：代签 / 重跑 / 打回 / 清场 / 开修复票
                   └─ 干不动了 → 落一条带默认动作的请求（不阻塞，继续干别的）

                 请求账（独立文件、长保留、有生命周期）
                 设置页（编辑权限与开关；判定仍在引擎）
```

### 关键取舍（为什么这么定）

- **会话是易失的执行体，位置才是常驻的**。project executor 是**岗位**，不是一段对话：对话可压缩、可重建、
  可结算后更换，位置用简报重建即可。所以「第一个会话永远存在」的落地口径是**槽位常驻**，
  而不是"这段对话永不结束"。
- **提醒与唤醒必须来自会话之外**。dsh 宿主侧可以对任意会话投递一轮输入（排队模式不丢、打断模式
  用于紧急），所以"有人看着 → 叫会话"这条链可以在**宿主侧**完成，不需要浏览器开着。
- **事件账是派生投影，不是真源**。它只记变化、不记状态；丢了不影响正确性，只影响发现速度；
  任何时候可从票面重建。之所以值得做，是因为今天跨票的"发生了什么"**根本读不到**——
  只能一张票一张票地问一个活着的工作流。
- **写账动作必须幂等**。写账要落在**活动**里（工作流体里不能做 IO，会破坏重放），而活动的语义是
  「至少一次」——重试会产生重复行。因此每行必须带**幂等键**（票 + 票内事件序号），消费端去重。
  写账失败**不阻断工作流**（它是派生面），但必须**响亮**：写不进就点名，并由对账补回。
- **对账是第一公民，不是兜底**。真源永远是票面。固定节拍比对"账推演出的状态"与"票面真实状态"，
  不一致就以真源为准并把不一致本身报出来；对账同时兼任心跳（对账失败＝界面显式降级）。
- **请求与事件分文件**。保留窗不同：事件按天轮转、短留即可；请求要长留，而且**未答复的绝不能删**。
  同文件必然出现"某天轮转把未答复的请求静默删掉"——那是最坏的失败模式。同机制、同目录、两个文件；
  想要"一个订阅口"就在读层合成视图。
- **权限的判定点在引擎，不在设置页**。设置页只是编辑面；权限记录照引擎现有授权原语的形状
  （谁、范围、理由、**必须带到期**）。并守住红线：**会话不能用任何路径给自己扩权**。
- **升级（叫人）不阻塞会话**。形态是「我已做 A，除非你否，否则我按 B 继续」：请求落成带默认动作的
  请求，会话继续推进别的事；这样"喊人"这个动作不会把会话变成新的人为阻塞点。

### 自主与升级的判据（宿主口径待确认，先给草案）

- **会话能自己做的**：在案授权范围内的签字/推进/重跑/打回/清场；**在声明的直修面内自己动手修**
  （见「它有手」一节）；按已知问题清单能定性的故障；开修复票并跟到关闭。
- **必须升级到人的**：① 需要新授权或扩大范围；② 涉及钱、额度、外部不可逆操作；
  ③ 涉及设计取舍（定稿权在宿主）；④ 同一问题连续 N 次（草案 N=3）未解决，防死磕；
  ⑤ 触红线面（控制台、宿主环境、**别的项目**）；⑥ **要动的面不在声明的直修面内**（它没有改那个面的授权）。

### 授权范围（可配置；宿主 260927 口径：「我睡觉了，它都能做」）

**分两类别，只有一类可以授出去**：

- **代理执行类（可授予，范围可配）**：签字放行、打回重做、blocked 重跑、开修复票、暂停/恢复、
  以及清场（cancel）——宿主睡觉期间由会话代行。
- **权限类（不可授予，永远只有宿主本人）**：新开授权、扩大授权范围、延长授权有效期。
  理由：那是**元权限**。会话若能自己开授权，就能自己扩权——红线当场破，且"谁批的"从此说不清。
  代价如实接受：**睡觉时遇到需要新授权的票，会话只能把它挂成一条请求等你醒**（这类票本来也该等你），
  而不是自己批自己。

**配置的维度**（每项目一份，建议按下列维度声明，而不是一个总开关）：

| 维度 | 说明 |
|---|---|
| 动作集合 | 签 / 打回 / 重跑 / 开票 / 暂停恢复 / 清场，逐项可开关 |
| 对象范围 | 本项目全部票／指定立项／指定票 |
| 时间窗 | 到期时间；或"夜间窗口"（例如你睡觉的时段） |
| 代签身份 | 签字人必须带项目代号（例：宿主（经 sandbar 的 project executor 会话代签）），沿用现有代签纪律 |
| 不可逆动作的加严 | 清场（cancel）这类不可逆动作，即使在"全权"下也应要求**理由必填 + 进不可变历史**，且**禁止用它来"清理"会话自己解决不了的票**（那会变成把问题抹掉而不是解决） |
| 一键收回 | 你醒来想自己接管时，能一键把会话降为只读；**收回必须下一拍即生效** |

**每次动作必须能回答"它凭哪一条授权做的"**：动作留痕要引用授权条目（谁、范围、理由、到期），
这样你醒来一眼能看出哪些是它替你做的——这也是审计与追责的前提。

**授权形态建议**：不要"每睡一次开一次"（太烦，最后一定被绕过）。建议**默认窄档**（例如只允许签
合并闸）+ **睡前可一键切到夜间全权档（带到期时间，睡醒自动失效）**。常设全权是长期高危面，
不建议作为默认值。

**夜间口径是配置项，不是硬规则**（宿主 260927：「提醒也是可配置的啊」）：面板里配"夜间口径"
（全静音 / 只红线级发声 / 照常发声）与"红线级"的判定面（不可逆、超权、涉及别的项目）。
本稿给的**默认值**是「夜间静音 + 红线级例外」——但改默认值不需要改代码，只是改配置。

### 它有手：动作面、两条轨与判据（宿主 260927 纠正）

**先纠正一个错误的模型**：本稿早先把 project executor 画成"只调度不上手"的调度员——**与事实不符**。
现实证据：本仓**33 条「直修」提交**（KI-141 / KI-142 / KI-143、场景去假红、心跳误杀修复等），
且有**成文口径**（宿主令直修、不开票、小步提交留痕、以自跑单测+全量集成替代工单机械闸、
不动控制台、不动任何泳道），同一份记录还**自己上报了缺口**：直修绕开 Temporal 审计与人工合并闸，
审计痕只剩 git 提交信息；并记有实案「声称改了、实际没改」。**所以它是"带手的操作员"。**

**动作面四类**（每类的留痕与人审面强弱不同）：

| 动作 | 走哪 | 留痕 | 人审面 |
|---|---|---|---|
| 引擎动作：签/打回/重跑/开票/暂停恢复/清场 | 正规入口 | 引擎审计 | **强**（闸） |
| **主树直修**：改引擎/集成测试/文档 + 提交 | 直接动手 | 提交信息 + **必须进事件账** | **弱**（事后看流水） |
| **进泳道动手**：在某张票的 lane 里改 | 直接动手 | 同上 | 中（会与在飞 agent 撞树） |
| 设计取舍 / 定不了的事 | 落请求 | 请求账 | 你 |

**发现问题后的两条轨（都合法）**：

- **轨 A · 它自己动手**（分钟到几十分钟，一个 turn 内）：进该票 lane 读日志/复现 → 定位到
  「主树侧共享期望值或引擎问题」→ 直修（**每改一处提交一次，提交即检查点**）→ 自跑受影响测试 →
  重跑该票的闸 → 绿。每一步落一条记录。
- **轨 B · 外包给票**（小时到天）：定位到「真实产品代码缺陷」→ 开修复票（写集=相关面）→
  在**原票**上记一条挂起项（指向修复票，这就是"它为什么在等"的真源）→ **本轮结束**（不 babysit）→
  修复票推进/被驳回时由**事件唤醒**它 → 解阻塞或另作判断。

**选哪条由判据决定，不靠临场感觉**：

1. 要修的面**在不在允许直修的声明里**？不在 → 走票或问你；
2. **有没有硬依据**（已知问题清单有记录 / 复现拿得到 / 日志指向清楚）？没有 → **只定位，别急着改**；
3. 是不是**共享面**（共享守卫、期望值、引擎核心）？是 → **必须主树侧统一改一次**（仓里既有纪律：
   共享守卫与期望值只许在 main 侧改，否则各泳道各改必然分歧）；
4. **会不会与在飞泳道冲突**？会 → 避让或改走票；
5. **结果可观测吗**？改动小且结论明确 → 直修；要看效果、影响面不清 → 走票。

**三条硬规矩**（直修人审面弱，只能靠这三条兜）：

1. **直修面声明化**：允许直修的面（引擎 / 集成测试 / 文档）、**禁碰面**（控制台、别的项目、
   保护名单 → 引擎闸机械拦）、需先请示的面（设计文档、角色声明）。今天靠纪律与记忆，要变成声明。
2. **每次直修进事件账**（不只进 git 提交信息）：一行写出「改了哪些文件、凭什么依据、怎么验证的」。
   这正是那份记录自己上报的缺口的正解。
3. **修后实测才算数**：直修必须附验证证据（跑了什么、结果如何）。没有这条，就会出现"声称改了、
   实际没改"。

**长跑要有预算与检查点**：一个 turn 不能无限深挖；每完成一处就提交（提交即检查点），
被打断或失忆也能从记录接着干。

**如实承认最弱的一环**：泳道有合并闸，直修没有——所以面板必须把它**显眼化**：
`Did today` 逐条列它做过什么（带依据与验证证据）、事件账逐条留痕、保护名单机械拦、一键收回下一拍生效。

### 重启与孤儿处理（宿主 260927 追问：「这些毕竟没有 workflow 和 worker 支撑」）

**这套东西没有 workflow/worker 背书**——所以必须先把"活下来的"和"死了的"分清楚：

| 东西 | 重启后 | 靠什么 |
|---|---|---|
| 票的状态与历史 | **活着** | Temporal 持久化；supervisor 保活/重起 server 与 worker |
| 泳道工作树、代码、commit | **活着** | 磁盘 + git |
| 事件账、请求账 | **活着** | 磁盘上的追加文件 |
| 票上那条"我在等修复票"的挂起项 | **活着** | 在工作流状态里 |
| 执行器的对话 | **活着**（可 resume） | dsh 会话落盘 |
| **守望者的水位线 / 去重集 / 在办记账** | **死了** | 只在内存 |
| **在跑的子代理、后台作业** | **死了** | 在控制台进程里 |
| **正在飞的那一轮 turn** | **半截** | 内存 |
| **等待中的审批/提问请求** | **死了** | 会话级待办交互是内存态 |

**两条必须说清的副作用**：

- **引擎侧会被牵连**：Temporal server 与 worker 是**控制台进程 spawn 的子进程**——正常关闭会 SIGTERM 它们，
  崩溃则留孤儿；重启后 supervisor 按端口单例 + pidfile + meta 决定"接管还是重起"。所以票可能
  **中断一轮**，但由工作流重驱，**状态不丢**。巡检调度在 Temporal 上，不受控制台重启影响。
- **"目标续跑"不是持久的**：dsh 的目标continuation 是进程内许可，重启后要**重新武装**。

**恢复协议（顺序不能乱）**：

1. 先确认引擎侧起来了（读既有的两个探测点：Temporal 健康 / worker 清单）；
2. 守望者一上来就**全量对账**——水位线与去重集都没了，**不能增量续**；从票面重读、把账里缺的补上，
   并把"补了 N 条"记一条账；
3. 从持久源重建"在办画面"：在跑的票（引擎）＋ 票上的挂起项 ＋ 请求账；
4. **处理孤儿手**：账里有"起了"没有"结束"的手 = 进程死时被带走了；标成 orphaned，
   由执行器决定重做 / 接管 / 升级；
5. **处理半截 turn**：结果未知，不许假设——去看证据（git 状态与 diff、票状态）。
   好在**每次直修都是一个 commit**，等于自带检查点；
6. **重新武装提醒去重**：从账里把"已经报过的事"读回来，否则重启一次就把过去 12 小时全重播一遍；
7. resume 会话 + 重读简报：对话能接上，但"我干到哪了"必须**从账里读，不从记忆里读**。

**为此必须配对落账的三件事**（缺一条，重启就会静默出事）：

1. **请求的生死**：审批/提问**产生时写一行、回答时写一行**——否则重启会把"有人在等你"静默吞掉
   （请求没了、等的人也没了，账上看不出它曾经存在）；
2. **手的生死**：`spawn` 一行、`terminate` 一行——否则分不清"还在跑"和"被进程死带走"
   （仓里已有"照搬 spawn 丢了 terminate"的教训）；
3. **提醒的生死**：每次提醒各写一行——去重状态必须可从账重建。

**残留风险照实说**：重启瞬间正在进行的**不可逆动作**可能半截（清场、直修改到一半）。
前者的引擎操作本身原子、可重入；后者靠"每次直修一个 commit"兜——重启后能看到停在哪个 commit，
接着往下走。

**一句话**：状态外置（真相不在内存里）＋ 启动即对账（不信任自己的记忆）＋ 配对留痕（看得出手的生死）
——做到这三条，**重启不改变任何事实，只让手重新长出来**。

### 界面与命名（宿主 260927 定）

**入口**：左栏**一个项目一行，项目名就是 project executor 的入口**（本项目的其它会话缩进在它下面）——
不单列一条 Tick 行。点这一行，中间栏打开**该项目的执行器面板**。

**对话沿用现有 UI**（宿主点名：对话怎么放现在的 UI 已经有了）：project executor 本身就是**一个真会话**，
点项目那行打开的就是**这个会话**，顶上一个 `Executor / Chat` 切换器在"面板"与"对话"两个视图之间翻
（机制照我们自己的知识库页签那套）。所以**没有单独的"打开对话"按钮**——面板不是另一个地方，是同一个会话的另一个视图。

**面板显示"流量"，不显示"结构"**：环路的结构图属于本文档（看一次就够），面板上常驻的是**东西流到哪去了**。
呈现形态有讲究，第一版画错了：把它画成 `41 → 9 → 6 → 2 → 1` 的**链**，会被读成"6 变成了 2 变成了 1"。
实际是两件事——**`41 → 9` 是过滤**（感知到的事件数 ÷ 判定值得唤醒的数），**`9` 分成三份并列的结果**：
自己处理掉（6）／变成请求（2）／升级给你（1）。所以卡片用**"过滤比值 + 三份堆叠条 + 计数/占比/与上一窗口对比"**：
绿色变多、琥珀变少 = 它在自己吃掉活；唤醒数涨而绿色不动 = 过滤太吵。

**"今天"不是定义，是要显示出来的窗口**（宿主 260927 问「怎么定义 today」）：

| 窗口 | 用途 |
|---|---|
| **本次授权窗口（有在案授权时，默认）** | 如 23:00–07:30——正好是你不在、且它权限最大的那一段，两种用途合一 |
| **最近 24 小时（无授权时，默认）** | 不受重置影响的粗看 |
| 本地日历日 | 只用于对账 / 归档 |

**被否掉的一种窗口：「自你上次看过以来」**（宿主 260927：这个 last looked 怕是不行）。理由三条：
①**看过 ≠ 处理过**——扫一眼就重置，会把**没处理**的事从计数里抹掉；
②**"看过"不是个定义清楚的动作**（打开页面算吗？刷新算吗？）；
③它把**两件不同的事**混在一起——"还有什么在等你"是个**状态**，应当作为**常驻计数**（tab 角标），
**不由任何时间窗口推出来**。

四条纪律（选哪个窗口都得守）：①账里存**绝对时刻**、界面按本地时区渲染，项目可声明时区；
②窗口边界**只算一次**（写方与读方共用，不许各写一份）；③窗口起点**必须持久化**（若采用需确认的窗口，
"确认"时刻落一行账），否则重启等于重置窗口；④**边界比较用同一个时钟**——不要把工作流的确定性时钟与墙钟混用
（仓里"用例有保质期"就是这一族的代价）。窗口范围必须**印在界面上**，不许让读者猜。

**面板收成五个 tab**（宿主点名「settings 可以做成 tab，不应该占这么大的空间」；tab 次序按人实际用的顺序：
**先看到要你处理的，配置放最后**）：`Overview · Requests · Alerts · Ledger · Settings`。

- **原始事件流做成 tab，不做常驻栏**：它是排障与对账面，不是整天盯着看的东西；它的**健康度**
  （水位线／跳号／重启补齐）已经在守望者卡片里。做成整宽的 tab 还能给它可用的形态：序号/时间/主体/变化/细节
  五列 + 按票/按主体/按类型过滤 + 跳序号 + 跟随实时。
- **面板不放"说明性"的块**：像"哪份是真源、哪份是派生"这类话，要**就地写在各自的位置上**
  （事件账表头写 `derived · not the source of truth`，请求卡片写"自有账、永不自动删"），
  而不是聚合成一张每次看都一样的卡片——那种块归本文档。

| tab | 内容 |
|---|---|
| **Overview**（默认） | 一眼四件事：守望者**活没活**（心跳时间）、事件账**读到哪**（水位线）、**对账一致否**、**现在在干什么**（一句话）。另配一张**流程图**代替堆卡片：票变化 → 事件账 → 守望者 → 执行器 → 三个出口（自动推进 / 落成决定 / 只有不行了才叫你）。**没数据 ≠ 一切正常**，降级必须显式 |
| **Settings** | 授权范围（动作集合／对象范围／时间窗／代签身份）、提醒（开关、声音、桌面通知、夜间口径、红线级例外、停摆阈值、保留窗）、一键收回、一键夜间全权 |
| **Alerts** | 最近叫过你什么、什么时候、**你处理了没**（不是通知流水账） |
| **Requests** | 每条一句话 + 默认动作 + 期限 + 影响面；点开能回答；已决的回看（谁批的、理由） |

**下指令（三条通道，别混）**：

| 你想干什么 | 走哪 |
|---|---|
| **请它做什么**（自然语言指令） | 跟它的**对话**（现有 UI），或面板底部的快捷输入框；会话正忙时两种投递方式：**排队**（排在当前轮之后、按序执行、不打断——默认）/ **打断**（立刻接管当前轮——紧急刹车）。**打断会让那一轮半截**（文件可能改了没提交、工具结果未知），靠"每次直修一个 commit"兜底；因此**排队的指令必须显示出来**（否则一轮跑十分钟，你会以为指令被忽略），排队项可改、可删、可升级为打断 |
| **让它能做什么**（权限与开关） | **Settings** tab；写入走引擎正规入口，留痕可审计 |
| **回答它问你的** | **Requests** tab；答复后由它继续推进 |

**命名（宿主 260927：「是不是不应该叫 decisions，这是 requests？」——对）**：

- 对象是**它向你提出的请求**，不是"你做出的决定"。用 `Decisions` 命名等于用一个**回答**的词去指代
  **提问**，而且列表里躺着的恰恰是**还没答的**——「Decisions: 2 waiting」读起来别扭。
- **与 `Alerts` 成一对**，这才是两个出口的正名：**Alerts＝告诉你发生了什么**（不用你动手）；
  **Requests＝请你做点什么**（等你答复）。一个"信息"，一个"动作"。
- **与平台词汇一致**：dsh 自己的远程事件就叫 `approval/request`、`user-questions/request`；
  引擎侧的授权记录本质也是"向人提出的请求"。顺着已有词汇走，不另造词。
- **容器里装的是不同种类的请求**（见下表），`Decisions` 只覆盖其中一类，`Requests` 才装得下。

| 请求类型 | 它问你什么 | 你答什么 | 答复落在哪 |
|---|---|---|---|
| **决定** | 几个方案选哪个 / 设计取舍怎么定 | 选项 | 请求自身的答复记录 |
| **授权** | 要不要给它开一个新授权（超出了现有范围） | 批准/拒绝 + 范围 + 到期 | **票面的授权记录**（引擎） |
| **签字** | 某个闸要不要放行 | 通过/打回 | **票面的签字**（引擎） |
| **确认** | 它准备做一个不可逆动作 | 确认/取消 | 请求答复 + 事件账 |
| **补信息** | 它缺一条只有你知道的信息 | 文字 | 请求答复 |

**其余命名纪律**：**不许叫 todo**（与工单最容易混）；控制台界面文案一律英文（既有宿主令），
所以面板标签是 `Overview / Settings / Alerts / Requests`；数据内容不译。

**不做的**：请求**不进工单看板**、不参与工单计数与统计——它有自己的一页。

### 请求怎么写（宿主 260927：「要说人话、把背景说清楚、选项解释要明了、还要能追问」）

**它不是一行状态，是一件要独立成立的东西**：几个月后、一个不记得这段对话的人读它，也要能做出决定。
所以一条请求按固定次序带下面这些内容：

| 部分 | 规矩 |
|---|---|
| **问题** | 一句**人话的问句**。「超出范围的授权请求」是坏标题；「这张票现在能不能合并」是好标题。躲不开的术语，就在同句里解释 |
| **为什么落到你** | 触发原因一行说清：超出授权范围／设计取舍／同一问题第三次／不可逆动作 |
| **背景** | 3–6 句，**自足**：发生了什么、涉及哪张票/哪个文件/哪条数据、已经试过什么、不定会怎样。首次出现的票号要有一句解释。**禁止"如我前面所说"** |
| **选项** | 2–4 个。每个写**选了它会怎样**（不是只写名字）、代价、**可逆性**。必须至少有一个"不做/等等" |
| **建议** | 一条推荐 + 一句话理由（人可以不同意；有推荐只是让决定更快） |
| **不决定会怎样** | 到期行为——规则**很窄**：默认只允许**执行既有规则**，不允许**做出新决定**。所以只有两种合法默认：①"按既有处置走"（例：同一张票同样失败三次 → 打回重做，这是规则不是判断）；②"什么都不改，继续等"。**把"看起来更温和的那个设计选项"当默认，同样是替你拍板设计——这条路必须堵死**（宿主 260927 指出：「按 B 走」这种默认不行） |
| **一直不答会怎样** | 提醒按等待时长升级（面板上标出等了多久；超过 24h 每天提醒一次），**选项永不自动选中**；期间只允许做不需要你决定的事——把比较写得更清楚、推进与这条无关的工作 |
| **期限与谁被卡住** | 什么时候要答案，以及**哪些工作被这条卡住**。"没有东西被卡住、不急"也是个好答案，应当写明 |
| **关联（References）** | **带类型**、可点、**双向**：票 / 提交 / 已知问题（KI）/ 设计文档 / 事件账序号 / 相关请求 / 立项代号。反向同样重要——被卡住的票要写"我在等哪条请求"，已答的请求要写"它导致了什么"（例：夜间全权 → 代签 5 张 · 直修 4 处 · 开 1 张修复票） |
| **追问** | 追问留在**这条请求的线程里**（带是谁、什么时候）。追问可以**补选项、细化背景、改变建议**，改了就在记录里注明（「↳ 已补进选项 A 的代价」）。**不许把追问挪到别处聊**，否则推理链就丢了 |
| **历史** | 只追加：提出／追问／答复／撤回／超期按默认，各一行。已决的要留住**谁答的、何时、为什么、以及它导致了什么** |

**列表要能折叠**（宿主 260927：「每个应该可以折叠一下，不然不容易看全景」）：折叠态一行就要够判断要不要展开
——编号、类型、等了多久、**卡没卡住东西**、**一句话问题**、为什么落到你、默认动作；**排序=先按"卡住了什么"、
再按等待时长**，这样列表读起来是分诊台而不是一堆堆叠。展开才是完整记录（背景/选项/建议/到期行为/关联/追问线程）。

**两条反模式**（点名）：

1. **拿决定当进度汇报**——汇报属于 `Did today`，不属于这里；
2. **追问来回不收敛**——超过两三轮还没聚焦，执行器必须把它**收敛成一条更窄的新决定**，
   或者直接说"这需要当面聊，不适合填表"。

**呈现口径**：控制台界面标签英文（既有宿主令），**决定正文是数据、不译**——所以它用你能读的语言写
（说人话那条优先）。这一条如果宿主想要全英文正文，改的是内容语言，不是机制。

### 请求与提醒的边界（两个出口不能装同一件事）

**一句话**：**请求＝它做不下去，等你给一个答复（球在你手上）；提醒＝它要你知道的一件事（球不在你手上
——它继续干，或者已经坏了）。**

两个判定测试，任何一条都能定性：

1. **「我不看它，会怎样？」** 会停在那儿不动 → **请求**；照旧（继续跑／已经坏着） → **提醒**。
2. **「有答案吗？」** 有答案且系统要拿去用 → **请求**；没有答案、最多"我知道了" → **提醒**。

| | 请求 | 提醒 |
|---|---|---|
| 本质 | 待你答复的**工作项** | 告知你的**事实** |
| 谁在等 | **它等你** | **不等你** |
| 生命周期 | 待定 → 已定／已废／超期按默认 | 触发 → 已读；可能被后续事实自行取代 |
| 谁产生 | 规则判到"需要人"，或它自己判断定不了 | **条件探测器**：停滞／自锁／降级／对账缺口／阈值／红线动作已做 |
| 可指向 | 票、提交、文档、别的请求 | **可以指向一条请求**（自锁就是这么报的） |

由此三条规矩：①**一件事只有一个归宿**——需要你动手的提醒**指向**那条请求（给链接），**不许复制**；
②**已读 ≠ 已答**——标已读不重置任何东西（这也是窗口不能叫"自你上次看过以来"的理由），
请求只有"答了／撤了／超期按默认"才算关闭；③**报警靠探测器，不靠判断**——如果需要用执行器的意见才能报出来，
那它就不是提醒，而是请求或一条 `Did` 记录。

### 通用性审查：哪些是机制、哪些必须由项目声明（宿主 260927 问「扩展到其他项目怎么样」）

**结论**：回路、面板形状、守望者读数、两份账的机制——都通用；**但有五张清单现在写死了沙箱的事实**，
换项目就会错位（或显示一堆无意义的开关）。这正是仓里已经认过账的同类问题：巡检通用化那份草稿写着
「现状把 sandbar 专属保护名单**写死在引擎里**（`docs/design`、`server/roles` 等），其他项目套用会错位」。

| 现在写死的 | 换项目会怎样 | 应改成 |
|---|---|---|
| **授予清单**（签／打回／重跑／开修复票／清场／直修／提交／进泳道） | 这是 dev-lane 的操作面；别的项目模板可能完全不同（内容流水线是"发布／审批"，没有泳道与集成测试） | **从"该项目工作流模板实际暴露的人门与操作"推导**，UI 不钉固定表 |
| **禁碰清单**（控制台 3099／保护名单／别的项目） | "3099 控制台"是**本项目的**；保护名单是**项目数据** | 项目声明；UI 只渲染声明出来的条目 |
| **直修面**（引擎／集成测试／文档） | 别的项目目录结构不同 | 声明 `允许直修／禁碰／先问` 三类 |
| **窗口与保留**（夜间 23:00–07:30、停滞 15m、事件 14d） | 别的项目作息、时区、量级都不同 | 声明。**现成范式**：`project.yaml` 的 `admin_log{keep_days,max_mb}`、`inspection.yaml` 的 IANA `tz` |
| **`Now`/`Doing` 与 commit** | 有的项目没有 git、没有测试、没有泳道 | 整块**能消失**，不是显示空壳 |

**三条结构性问题**：

1. **守望者一进程看多项目**（宿主 260927 定）——一进程、按项目分账，不搞每项目一进程：否则 N 个项目就是
   N 份失败模式与 N 套守护；它的工作（判活／对账／唤醒／叫人）本就能按项目键控。
2. **执行器身份按项目来**（宿主 260927 定）——每项目一份执行器人设与预设 + 一段 charter；今天控制台默认预设是
   **借 integration 岗位人设**的，通用化必须补一份真正的执行器人设，否则新项目一出生就继承"泳道把关人"身份。
   注意：**执行器身份走"会话预设"，与工作流角色集是两套东西**（见下），别混。
3. **模板角色集是引擎固定表**（待定，详见下一节）。

**规模与跨项目**：样例是"一夜 41 条事件"，活跃项目可能一小时几百条——Ledger 必须分页／筛选（概念有、
实现无），Requests 要分组与"显示更多"，Flow 的窗口在活跃项目里是"一周"而不是"一夜"；
**绝对数会误导，主看比例**。跨项目按**票的归属项目**归账、跨项目动作带旗标并升级给那个项目的宿主。

**接入与默认**：**未声明＝零行为变化**（仓里既有铁律）；默认**最小权限**——没有任何授予时，
执行器只能"看"和"问"。这条是通用化能安全铺开的关键。

### 「角色」到底是什么：项目外置模板为什么不能用新角色（宿主 260927 要求细说）

**角色不是标签，它牵四样东西**（实核对：

| 角色决定 | 在哪 | 缺了会怎样 |
|---|---|---|
| **人设**：整份岗位说明书作为 `--patch` 注入 spawn 出来的 agent | `agent_activities.py`（spawn 处）：取项目注册表声明的 `paths.roles_dir`，缺省回落 `<cwd>/server/roles`，读 `<role>.yml` | 文件不存在 → **跳过、退化为默认人设**（不硬失败）——即"名字对不上时，它换个身份照样干" |
| **模型路由**：`model-routes.yaml` 的 `roles:` 段按 (角色, 分工) 取 provider/model | 引擎读表 + 生成一次性钉模型的 patch | 无该角色条目 → 回落到 `default` 档 |
| **票面与泳道**：票的 `role` 字段（看板显示）、lane 与 agent 日志命名、按角色扫描会话 | 多处 | 只影响可读性与归类 |
| **代码里的角色分支**：例如"只有 developer 才做某类扫描"、报告英文化只要求某两个角色 | `agent_activities.py`、`shared.py` | 借用别人的 id 就会**顺带继承**这些分支行为 |

**谁会拒收未知角色**（这是坑的所在）：

- **server 层**：`server/tools/workflow.py` 有一张**固定角色表**——5 个 M10 定稿（developer/integration/ops/
  product-operation/artist）+ 5 个退役兼容 id（dispatcher/editor/proofreader/qa/analyst）；模板校验里
  `role not in ROLES` 直接抛「未知角色」。`workflow list/show` 与开票闸**同源**，所以新角色会**在模板面被拒**。
- **引擎侧**：外置模板加载口（`project_templates.py`）**只校验角色是"非空字符串"**，**不做成员集校验**
  → 引擎**会接受**未知角色。
- **⇒ 两处口径不一致**：同一个模板，引擎收、server 层拒——用户看到的是"它能加载/能跑，却在列表里看不见或开票被拒"。
  这是 KI-079 同族（说明书与实际入口不符）。**这条本身就值得记一笔。**

**还有第二、第三张角色表**（同一个概念散在三处，加角色要同时改，容易漏）：
`inspection_flow.py` 的 `AGENT_ROLE_NAMES`（只列 5 个当用角色）、`shared.py` 的
`ROLE_REPORT_ENGLISH_ROLES`（只列 developer/integration）。角色概念的**单一真源缺位**。

**新项目要新角色的三条路**：

1. **放开成项目声明**：项目在注册表里声明角色（id + 人设文件 + 模型路由 + 报告语言要求），引擎不再查白名单，
   只校验"声明的角色必须有人设与路由可解析"（缺则 fail-closed 点名）。代价：多一处声明与校验面；跨项目角色名不再统一。
2. **保持固定表 + 文档认账**：新项目只能用现有 10 个 id。代价：**被迫借用身份**——不是名字不贴切，而是
   **行为不贴切**（人设、模型档、代码分支一起继承）。
3. **中间档（建议先走这条）**：①把三处角色常量收成**单一真源**；②修掉"引擎收 / server 层拒"的**口径不一致**；
   ③允许项目声明**角色别名 → 绑定到内置角色**（可覆盖人设与路由），从而在不放开全白名单的前提下让新项目有贴合身份。

**与项目执行器的关系**：执行器自己是**控制台会话**，身份来自 dsh 的**会话预设**（不是工作流角色集）——
所以上面这套角色问题**不阻塞**执行器落地，但**阻塞"项目自带工作流模板"这件事**（通用性的第二根支柱）。

## 已定口径与待定口径

**已定（宿主 260927）**：

1. **不做独立于控制台的兜底（方案 C）**。守望者住在宿主插件里。**如实接受残余风险**：守望者与控制台同生共死——
   控制台整个挂掉时没有第三方会叫你。缓解：守望者**自证心跳** + 界面显示"它最后活着的时间"；
   真到那一步，你在电脑前会先发现控制台本身打不开。
2. **代签范围可配置，且「我睡觉了它都能做」**——但要与**权限类动作**分开：签／打回／重跑／开票／暂停恢复／清场
   可授予；**新开授权与扩大范围永远只有宿主本人**（元权限）。代价：睡觉期间的超权票会挂成一条请求等你醒。
3. **提醒全部可配置**：方式、开关、发声时机（含夜间）、哪些级别必须发声，都是配置项。
4. **事件写账做「活动内直写」**：状态迁移处投一个记事件活动，即时、不依赖查询；幂等键兜重复，
   写失败 fail-open 但响亮，对账补漏。
5. **请求不进工单看板**：独立入口、独立一页、不参与工单计数；概念名不叫 todo。
6. **请求要当产品做**：说人话、背景自足、选项讲清"选了会怎样"、支持追问；写作规矩见「请求怎么写」一节。
7. **守望者一进程看多项目**（按项目分账），不搞每项目一进程。
8. **执行器身份按项目来**：每项目一份执行器人设与预设 + 一段 charter。注意它走**会话预设**，
   与工作流角色集是两套东西。
9. **"今天"不做定义**：面板显示**显式窗口**，默认"本次授权窗口（有授权时）／最近 24h"；
   否掉"自你上次看过以来"（**看过≠处理过**）。
10. **授予清单走"轻量过滤式派生"**：不是"推导出一套新东西"，而是**固定操作清单 + 三项过滤事实**——

    | 来源 | 内容 | 说明 |
    |---|---|---|
    | 引擎操作面（固定） | 签／打回／重跑／开票／暂停恢复／清场 | 不随项目变 |
    | **模板**（事实一） | 有没有人门、有哪几个、叫什么 → 决定"签"这项有无意义、范围多大 | **输入已现成**：模板拓扑导出面已带 `kind`，`exit=human` 即 `human` 节点 |
    | 项目声明（事实二、三） | 有无泳道／工作树；哪些目录允许直修 | 读声明 |

    UI 形态不变（仍是勾选项，按模板分组）。**明确不做**：①「每个门 × 每个模板 × 每个项目」的三维矩阵；
    ②把"谁有权签哪个门"这类**策略**塞进推导（那是宿主的决定）；③试图推导操作语义（那些是引擎的、固定）。
    **落地位置**：并入 UI 那张票，不单开票；即便当前只有 dev-lane 一个模板，也要把"这张表从哪来"留成
    明确落点，避免又变成一处硬编码。

11. **停摆判据与保留窗 → 形态=可配置**（宿主 260927：「这两个我也不好说啊，可配置呗」）。
    **判据必须是"证据式"而不是纯墙钟**：主判据＝**有没有推进的证据**（事件在流／产物在变／心跳在报，
    即 KI-138 结论里的"进展驱动心跳"），墙钟只作**偏宽的上限兜底**。依据：本仓 `260ee79` 把 agent 活动
    心跳超时 **3 分钟 → 15 分钟**（实锤 3 分钟静默会误杀仍在干活的 agent），KI-138 追录更查出真因是
    **宿主整机休眠**时 Temporal 一并挂起、3 分钟墙钟把**所有**在飞活动同秒判超时 → **纯墙钟判死在休眠场景下必然误杀**。
    另须**分开报**两件事：**"我这边没信号"**（守望者停了／宿主休眠 → 报"数据可能过期"）
    vs **"它卡住了"**（有信号但无推进 → 报停滞）——休眠场景下这两者会同现，混报会把人引向错误方向。

12. **授权档位形态 → 形态=可配置**：档位本身是**声明出来的**（例如"只读+问"/"可签合并闸"/"夜间全权"），
    出厂默认走**最小权限档**；夜间全权是一个**可选档位**，睡前手动切、带到期。

13. **事件来源走「事件混入」**（宿主 260927「按你的推荐来」）：新增第三个混入（与暂停／跨项目同级）
    承载事件发射，**票① 先做混入 + dev-lane 接线 + 幂等键 + 账格式 + 启动即对账**；
    **巡检族的接线紧跟第二票**（不是"以后再说"——巡检每天都有一次人审收口，漏了它面板就在最常见的
    一类"需要你"上瞎）。外置模板**在加载口强校验"必须混入该混入"**（fail-closed 点名），防新模板静默无事件。
14. **引擎级活动并入"引擎所属项目"的账，行里标 `scope: engine`**（不新造"引擎级账"概念）：
    仓里已有该判定（`project.yaml` 里带 `admin_log` 的条目、其 `dirs` 含引擎仓根）。
    适用对象＝调度扫描、巡检触发器（spawner/watcher）、引擎自身维护（worker 重启、重启后对账）。
    新巡检期票本身**带项目归属**（t260915-20 起盖章），不属此列。
15. **按工作流族分组**：**授权必须真按模板拆 + 按能力过滤**（巡检**没有暂停面** → 不给它显示"暂停/恢复"；
    改的是能力面，不只是显示）；**Flow 与请求/提醒按族分组、窗口统一**（否则巡检的一期会被 dev-lane 的
    几十条事件淹没）。与第 10 条（授权表从哪来）是同一件事的两面，落地时一起做。

**出厂默认值（可随用随改，不需要拍板；改配置即可，不动代码）**：

| 项 | 出厂默认 | 依据 |
|---|---|---|
| 停滞上限 | **15 分钟**（且判据以进展为主） | `260ee79` 的教训 |
| 事件账保留 | **14 天** | 与 `admin.log` 同口径（仓里既有先例） |
| 请求账保留 | **长期**（已答复的也留） | 是决策记录，删了就查不到"当时为什么这么定" |
| 授权出厂档 | **最小权限**（只读+问） | 最小权限原则 |
| 轮转／过大顺切 | 沿用 `admin.log` 那套 | 现成范式 |

**配置放哪**：跟仓里既有做法一致——**项目声明**（`project.yaml` 已有 `admin_log{keep_days,max_mb}` 先例，
`inspection.yaml` 有 IANA 时区）；权限类改动**判定在引擎**且**留痕**（谁在何时把什么改成了什么）。
**纪律：可配置 ≠ 全可配**——建议只暴露这四个旋钮（停滞上限、两份账保留、授权档位、夜间口径），其余固定；
旋钮太多没人调，只增加实现与测试面。

**后续做，不阻塞本 epic**：

16. **模板角色集**（通用性审查第三节；宿主 260927：「角色这个问题能不能之后再搞」——能）。**结论：现在不动**。
    理由：角色集是**引擎级共享**的，所有项目复用 developer/integration/… 正是设计本意，不是将就；
    执行器**自己的身份**走会话预设，与角色集无关。**触发条件**：某个项目要一个内置表里没有的**阶段角色**时再做——
    届时"加一个角色"本身只是三处小改（固定表 + 人设文件 + 模型路由条目），正路走中间档
    （①三处角色常量收成单一真源 → ②修掉"引擎收／server 层拒"的口径不一致 → ③允许项目声明角色别名）。

**已知问题之一（已入账 KI-146）**：**模板角色集的两处闸口径不一致**——server 层
（`server/tools/workflow.py`）用固定表拒收未知角色（实测报文：`stage s2 未知角色 'curator'（可用: …）`），
而**引擎侧外置模板加载口**（`server/engine/project_templates.py` 的类面深检）只校验"角色是非空字符串"、
**不做成员集校验** → 同一模板"引擎收、server 层拒"。另有**同一概念散在三处**（`workflow.py` 固定表 /
`inspection_flow.py` 的 `AGENT_ROLE_NAMES` / `shared.py` 的 `ROLE_REPORT_ENGLISH_ROLES`），加角色易漏。
按纪律这属于我岗应登记的故障模式（KI-079 同族）；**宿主 260928 令入账，已登记为 KI-146**。

**已知问题之二（已入账 KI-147）**：**`TicketWorkflowBase` 事实上无人继承**——
`base.py` 自述是"六个 M11 模板的共享基类"，通用主循环 `_main` 全仓仅此一处定义且无人调用；
五个实际工作流类是裸类或不含它（dev-lane 直接混入两个 mixin 并自认 `stands alone`）。
性质：**意图与现实漂移**（同族于 KI-079「说明书与实际入口不符」）；影响：任何"改一处即覆盖全族"的
引擎改动（例如本 epic 的事件发射）都会**以为在基类上、实际没人走到**。处置方向：要么让各族继承它、要么把这段自述改成"历史方案，现存仅两个 mixin 在用"——**宿主 260928 令入账，已登记为 KI-147**。

**已知问题之三（已入账 KI-148）**：**"哪个项目算引擎所属"这条归属判据被写错**——账本开关写在
**机器级** `~/.sandbar/projects/<项目>/project.yaml` 上，而"哪一份声明说话"本身有判据（该条目的
注册目录是否覆盖引擎仓根）。票①首版用"带 `paths:` 段"冒充该判据，于是开关**写了不生效且全静默**
（不报错、不写一行）。性质：**借鉴既有实现丢了守卫 + 自述仍在声称**（KI-079 同族），并暴露一条新的
测试病：**夹具与实现同源于同一个错误假设 ⇒ 24 条单测自证式全绿**。260928 合并后复核发现，
宿主任命 main 侧直修，已修（含与既有实现的一致性锁 + 红/绿反证）。**对后续票的含义**：④面板必须能答
"**是哪个 project.yaml、哪一条声明**决定了当前开关值"——否则同一个静默失效会以"开关没生效"的面目
复发，而盘面上它与"本来就没开"不可分辨。

**已知问题之四（已入账 KI-149）**：**"机器级声明键"与注册加载器白名单之间没有锁**——票①的开关
写在机器级 `~/.sandbar/projects/<项目>/project.yaml` 顶层（`event_ledger:`），而注册表的唯一装载器
只认一张固定的顶层键白名单；键没进去 ⇒ **整条注册条目被隔离、控制台左栏该项目整块消失**（260928
实案：声明一写，sandbar 即刻不可见；另一 session 修于 `0c0ee58`）。性质：**同一族第二次**
（`admin_log:` 在 260916 已踩过），根因是"新增一个顶层声明键"要同时改装载器四处 + 读者自述，人必漏。
回归已补（`sc_registry_additive_keys`：从读者源码派生段名逐个断言装载器容忍，新增第三个段会被自动
要求放行）。**对后续票的含义（与上一条合并看）**：④面板要能答"**哪一份声明、哪一条键**决定了当前
开关/配置"，并且**声明写入方应能当场自校验**（正面先例：安装器 `project add` 写完即跑装载器解析 +
全表零隔离自检）——否则这一族永远是"事后从控制台消失里发现"。

**已知问题之五（已入账 KI-150）**：**撕裂的结果文件把票卡进重试死结**——引擎读不出（`_read_result` 返回
None）与 agent 的幂等判据（「结果文件在场=本段已完成」）互锁，同 gen 重试必然全败；且旧报错**谎称**
「未写结果文件」（文件其实在场、只是 JSON 半截）。误报半边已修（文案分「未写」/「在场却读不出」并给
处置指引）；**死结本身**（自动挪档自愈）留待定。与本 epic 的关系：epic 票⑥ 就栽在这上面一次。

**已知问题之六（已入账 KI-151）**：**新插件挂载的引导缺口**——`profile-headless/cordis.patch.yml` 是指向
web patch 的软链 ⇒ 一处挂载必然同落两个 profile ⇒ 约定要求两条 `node_modules/<包名>` 软链；但工单写集是
**目录前缀**，`server/profile/` 覆盖不到兄弟目录 `server/profile-headless/` ⇒ **插件票结构上无法自洽完成
自己的挂载引导**（越界守卫会把 headless 链反复挪走，票④ 实案 6 次空转）。现行做法=web 链在票内、
headless 链由 integration 岗合并后补；持久解（守卫别名化 / headless 的 node_modules 直接软链到 web /
约定成文）留宿主定。**对后续票的含义**：再开插件类票时，票面写清「两条链各自的落法」，别再让 agent 空转。

**实现期注意（不用现在拍，但别忘）**：Ledger 需要分页／筛选、Requests 需要分组与"显示更多"、
Flow 的窗口在活跃项目里应是"一周"而非"一夜"；**绝对数会误导，主看比例**。
