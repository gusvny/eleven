## 0 说人话版（一分钟）

现在工单在执行时，人能看到「跑到哪一段」和「agent 自己说在干什么」，
**看不到它做出来的东西**：稿子、渲染图、判读表、台账条目、生成的成品文件。

三个真项目的人门（= 要人签字的那一步）都卡在这上面：

- 建模（`project-vision` / `part-intake`，五段一道人门）：要并排看
  自渲染图、台账条目（位号/重量/接口）、机器闸回执；
- 赛道（`project-vision` / `track-pipeline-v2`，七段一道人门）：要并排看
  逐门判读表、核对图、生成的赛道文件；
- 内容（`project-content` / `content-studio`，八段两道人门）：要并排看
  方案与提取口径、成品稿子、QC 红项。

票面上这些只是一串路径，详情页把路径用分号拼成一行字。人得自己去仓库里翻文件。

本稿的做法：**让产物变成有看法、有轮次、有归属的声明式数据**，
控制台按看法显示；同一声明有两种读法——跑的时候看过程，签字前看定版。
看法、保留政策、清理政策都归项目自己声明；沙盘只提供默认值与框架。

## 1 现状（实测，261030）

### 1.1 票面能承载的产物形态

- `Handoff.artifacts` 是**字符串数组**（`server/plugins/workbench/src/client/index.tsx`
  的 Handoff 类型）；详情页把它塞进一个折叠，值用 `'; '` 拼成一行。
- 唯一**类型化**的产物展示是截图证据：专用只读端点 + 灯箱
  （同文件 `evidenceImgSrc` / `EvidenceLightbox`）。
- 段报告（`results[stage].report`）走 markdown 渲染，算半个例外。

### 1.2 过程可见性今天的现状

能看到的四样：

1. 段状态与时间线（`stage` / `stage_state` / `timeline`）；
2. agent 实时文字流水（`agent-live` / `agent-logs` 两条只读面）；
3. 每段结算摘要（`results[stage]` 的 summary / evidence / deliverables / files_changed）；
4. 机器闸红绿（`gate_runs`）。

缺口：这四样都是**「它说它做了什么」**，没有**「它做出来了什么」**。
所以人和工单之间隔着一层自述。

### 1.3 收口归档今天收什么

`archive_ticket`（`server/engine/agent_activities.py`）复制的是：段结算文件、
`.dsh/sessions` 会话记录、截图证据、归档清单 `archive.json`。
**不包含任意产物文件**。

后果：内容项目的正文不进 git、manifest 落在工作目录、赛道核对图落在
`.sandbar/runs/` 下——泳道一拆就全没了。人过两天回来点开是空的。

### 1.4 三个真项目的产物，按形态归类

| 项目 / 泳道 | 人门要对照的东西 | 形态 |
|---|---|---|
| 建模 `part-intake` | 自渲染验收图 ↔ 台账条目 ↔ 闸回执 | 图 + 结构化条目 + 回执 |
| 赛道 `track-pipeline-v2` | 逐门判读表 ↔ 核对图 ↔ 赛道成品 | 结构化表 + 图 + 外部成品 |
| 内容 `content-studio` | 方案/口径 ↔ 成品 ↔ QC 红项 | 文本 + 账本 + 回执 |
| 通用（代码类，如本仓 dev-lane） | 改动清单 ↔ diff ↔ 测试回执 | 差异 + 清单 + 回执 |

四行合起来，产物只要六种看法就够（§4.1）。**沙盘自己这三条内置泳道还要更少。**

## 2 目标与非目标

### 目标

1. **过程看得见**：工单跑到哪一段时，人能看到这一段已经产出了什么、
   跟上一轮比变了什么、还差什么。
2. **人门审得动**：签字前，人门把该看的几样并排摆出来，而不是给一串路径。
3. **泳道说了算**：一条泳道声明自己的产物与人门看什么；内置泳道与外置泳道
   用同一套说法。
4. **过时不丢**：声明过的产物在收口时一起归档，不受泳道拆除影响。
5. **不认识也不空白**：遇到没见过的产物，控制台给通用卡（名、大小、时间、
   打开/下载），绝不静默。
6. **底座不押在谁身上**：基础能力与任何项目、任何泳道无关；项目要自己的看法，
   各自往上加，互不影响（§10）。

### 非目标（本稿不做）

- 不做在线编辑器、不做 3D 查看器、不做媒体播放器。沙盘只提供隔离窗口与装载通道
  （§9），窗里做什么是项目自己的事。
- 不做「项目界面进控制台插件」那条路（理由与代价见 §9.1 / §9.3）。
- 不改机器闸的判红口径，不改签字通道。
- 不把产物正文塞进 git（内容项目的正文走它自己的写接口，本稿只认「产物在哪」）。

## 3 三个核心概念

### 3.1 产物声明

产物不再是裸路径，而是一条**声明**：它叫什么、什么类型、在哪、哪一段产出的、
（可选）按哪个字段读、要不要打开才知道内容。

草案字段（讨论用，不对齐具体实现）：

| 字段 | 意思 | 例 |
|---|---|---|
| `id` | 票内唯一、跨轮次稳定 | `event-json` |
| `title` | 人话名字 | 逐门判读表 |
| `kind` | 看法（§4：内置六种之一，或项目自定义并映射到内置之一） | `structure` |
| `source` | 在哪：仓库内相对路径 / 外部绝对路径 / 服务端 URL | `fpv-parts/models/x.glb` |
| `repo` | 多仓票时是哪一仓 | `fpv-parts` |
| `stage` | 哪一段产出的 | `pi-model` |
| `note` | 看它要注意什么（可选） | 「门 7/12 判读待补」 |
| `open` | 外部成品怎么打开（可选） | 「用 Dengzhu Studio 打开」 |
| `shape` | 结构化产物的读法提示（可选，如主表在哪个键） | `units[]` |
| `optional` | 缺席是否算异常 | `false` |

要点：`id` 稳定是轮次对比的前提（§3.2）；`stage` 是「过程看板按段归位」的前提；
`repo` 是多仓票的前提（`part-intake` 就是多仓：内容在 `fpv-parts`、游戏与工具在
`fpv-midnight`）。

**兼容**：老票的 `artifacts: string[]` 照旧认。类型按扩展名猜，`id` 用路径派生，
没有轮次信息时按「最后一轮」处理。不迁移、不回填。

### 3.2 轮次（打回重跑不丢历史）

打回重跑会产生新一轮。上一轮产出的东西不能被覆盖掉——「这轮改了什么」
正是人最想看的那条信息。

- 每个产物按「轮次」留档，最新一轮是当前态；
- 过程看板默认显示「最新一轮 + 与上一轮的差异」；
- 人门显示「本次签字要看的那一轮」定版；
- 轮次必须能被机器判出来（不靠人写）。现有 `gens`（段→第几轮读数）是现成底座。

### 3.3 同一声明，两种读法

| | 过程看板（跑的时候） | 人门审阅板（签字前） |
|---|---|---|
| 何时出现 | 段在跑、段刚结束 | 停在人门段时 |
| 看什么 | 最新一轮 + 变化 + 「正在产出什么」 | 定版 + 并排对照 |
| 完整性 | 允许半成品，明确标注 | 只认已结算的产物 |
| 人的动作 | 看、必要时喊话/暂停 | 看、评论、签字或打回 |

**两块不能做成两套声明**：泳道作者写一遍，人只看一处。

## 4 看法：内置六种 + 项目自定义

这里限的不是「产物是什么」（那是项目的话：逐门判读表、台账条目、manifest），
限的是「人拿它做什么」——控制台的**看法**。控制台自带几种默认看法，
其余由项目自己提供，两者共用同一张注册表（§4.2）。

### 4.1 内置六种（控制台自带的默认注册）

| # | 看法 | 看什么 | 三个项目的实例 |
|---|---|---|---|
| 1 | `image` | 图，缩略图 + 灯箱 | 核对图、自渲染验收图、截图证据 |
| 2 | `text` | 纯文本 / markdown | 方案、审校报告、稿子 |
| 3 | `structure` | 结构化数据：声明主表键后显示成表，未声明则显示树 | event.json、calib.json、manifest.json、台账条目 |
| 4 | `diff` | 与基线或上一轮的差异 | 代码改动、判读修订、稿子改稿 |
| 5 | `ledger` | 回执/账本类：逐条红绿 + 计数 | 机器闸回执、发布账、QC 红项 |
| 6 | `external` | 浏览器看不了，只给元数据 + 打开方式 | `.glb`、`.dengzhu` |

**沙盘自己的三条内置泳道**（dev-lane / light-lane / quickmanual-lane）
用得上的是 2、4、5 三种，加截图证据的 1——其余两种是给项目泳道预备的。

### 4.2 项目自定义看法：可以新增，也可以覆盖（框架不变）

**沙盘和别的项目同权**：内置六种只是控制台自带的默认注册，沙盘不享有特权
路径，项目注册走同一张注册表、同一份格式。项目对自己票上的看法可以：

- **新增**内置六种之外的新看法（如三维模型查看、音轨对齐）；
- **覆盖**本票某一内置看法的默认展示（同一个 `image`，赛道项目想用
  图↔表并排、建模想加转盘，都行）。

**框架不允许覆盖**——这五条是控制台的地基，任何项目视图都改不到：

1. **清单归控制台**：这一票声明了哪些产物、在第几轮、大小与时间，
   由控制台列。项目视图只能决定「这一条怎么画」，不能决定「有没有这一条」。
   否则「我的视图只显示好看的几条」就成了漏洞。
2. **机器判词归控制台**：机器闸/QC 的红绿由控制台在框架里独立显示一遍，
   项目视图可以画得更清楚，但不能覆盖、吞掉、或把红画成绿。
3. **原件永远可达**：「看原件」（原字节 / 纯文本 / 下载）与「切回内置看法」
   始终一点就到，不许藏在自定义视图里。
4. **来源可辨**：框架上标注「此视图来自项目自定义」，审计时能分清是谁画的。
5. **覆盖只作用于本项目**：项目改不到别的项目的票；沙盘也只能改自己的。

其余约束：

- 自定义看法**必须声明一个内置看法作兜底**：包没装、加载失败、或人主动切回，
  退回内置看法照样能看，并明示「项目自定义视图不可用」，不白屏。
- 自定义看法描述「人怎么用」，不许描述「长什么样」（写成「三维模型转着看」可以，
  写成「带颜色的甘特图」不行——那会碎成每条泳道一套界面）。
- 自定义看法拿不到签字权，也碰不到主页面（§8）。

**代价照实记**：人审不同项目要换不同的视图。但框架、原件入口、机器判词都在，
「换视角」不会变成「换个地方骗人」。

### 4.3 兜底规则（内置与自定义都适用）

- 认不出看法 → `external` 兜底卡（名/大小/时间/打开），**不空白、不报错**。
- 认不出的看法**可见不静默**：记「哪个项目声明了什么、几张票」，
  攒出证据再决定要不要升成内置。
- 大文件不进页面：只读元数据（大小、修改时间），单文件与总量都设上限，
  超限的显示「太大，不在页面打开」并给打开方式，不静默截断。


## 5 声明写在哪

三处，各管一段，不互相替代：

1. **段在结算时声明自己产出了什么**：段的结算结果里带产物清单。
   这是过程看板的数据源，也是「这一段做完了没有」的证据。
2. **泳道声明人门看什么**：人门那一段声明「审阅板 = 哪几块、怎么并排、
   跟什么对照」。这是数据，不是界面代码。
3. **项目声明产物的落位约定**（可选）：比如「内容正文永不进 git」这类口径。

引擎的位置：**只搬运、不解释**。引擎把声明原样放进工单快照（Temporal history），
不认识类型、不校验业务语义；「怎么显示」全在控制台。
这样外置泳道和内置泳道拿到的是同一个面。

## 6 「进行中」的口径

段在跑的时候去读文件，可能读到写了一半的东西。口径必须写死，否则
人会被半成品误导，最后怪到引擎头上。

- 只读，不校验、不修复、不改 mtime；
- 明确标注「进行中，可能不完整」，且标出最后一次变化的时间；
- 半成品**不参与**红绿判定、不参与签字前的定版；
- 读不到就如实说「读不到 / 文件不在」，不回落成空表，也不冒充上一轮；
- 该产物是否被每轮刷新，由声明决定：有的每轮都变（判读表），
  有的只在某段出现一次（回执）。

## 7 归档与清理：只留该留的，删要有据

### 7.0 先看现状（261030 实测）

四个项目归档合计 **3.0G**：sandbar 1.8G / 497 张票、project-vision 533M / 167 张、
project-content 400M / 187 张、suyou 45M。

拆开 sandbar 那 1.8G：**agent 会话记录 1.2G（67%）**、截图证据 272M（15%），
其余是段结算文件。**今天的大头不是产物，是会话记录**——因为产物文件根本没收。

所以要做的事不是「要不要收」，是「别让归档从文本为主变成大文件为主」。

### 7.1 有家不搬

产物的三种归宿先分清，只有第二种才复制字节：

| 归宿 | 例 | 归档留什么 |
|---|---|---|
| 已进项目自己的库/仓/服务 | GLB 进 `fpv-parts/models` 并提交、赛道进赛道库、内容正文走写接口 | **指针 + 哈希 + 元数据** |
| 只活在泳道里，拆道就没 | 核对图、manifest、审阅报告 | 复制文件（通常很小） |
| 浏览器看不了的外部成品 | `.glb`、`.dengzhu` | 元数据 + 打开方式（`external` 类型） |

### 7.2 按票封顶：超了保留最近的

- 单文件上限 + 单票总量上限（**建议 20MB / 50MB**，项目可改——建模票天生比文档票大）；
- 只归档**声明过的**产物，不扫目录（否则一个 `.sandbox/` 就能撑爆归档）；
- **超限就丢最旧的**：按轮次从旧到新丢，直到降到上限以内。同轮次内按大小丢。
  **签字那一轮的定版不参与丢弃**——超限也留着。
- 每笔丢弃进**清理台账**（哪张票、哪一条、哪一轮、多大、为什么），可查。
  页面上照旧能打开（在飞期间），但会标「这一轮已按政策清理」。
- 归档失败 = 不拆泳道（沿用现有 fail-closed：归档成功才拆道）。

### 7.3 保留政策：默认值由控制台给，项目可改

- 在飞期间保**全部轮次**——过程看板要看「跟上一轮差在哪」，这一条不给改；
- 收口后的保留期默认 **30 天**（全轮次），到期只留**签字那一轮**的定版 + 差异摘要；
- 保留期、单文件上限、单票上限、超限时丢哪些轮次，都是**项目声明的一部分**
  （与看法注册同一处，同一份格式）；项目不声明就用控制台的默认值。
- 单条产物可以声明「全部轮次都要留」（例如最终交付物），政策不为它丢旧轮次。

### 7.4 清理按政策执行，但每一笔都要有据

- 清理按项目声明的政策**自动执行**（政策本身就是预先点过头的那次同意），
  不再每次弹窗问人；
- 每笔清理进清理台账（哪张票、哪一条、哪一轮、多大、依据哪条政策），可查；
- **红线：不许静默**。删了而台账里没有，视为缺陷；
- 政策没声明的项目走控制台默认值；项目也可以声明「不清」——那是它的选择，
  但产物清单与占用照旧在页面上可见；
- **未收口的票不适用保留政策**（未合并、失败、被取消）：那是现场证据，
  一直留到它收口或被人显式处理；
- 已签字的定版永远不在自动清理的范围内，只能由人显式处理。

### 7.5 顺带记一笔（不在本稿范围）

会话记录是当前真正的大头（sandbar 1.2G）。它属于既有归档口径，不归本稿，
但值得单独排一张票考虑压缩/裁剪。本稿只负责：产物面别再往上加一个数量级。

## 8 安全：产物是外人写的内容，控制台握着签字权

- 产物内容**永远不直接进主页面 DOM**。markdown 走现有渲染器（先转义），
  其余类型只走「取文本 → 显示为文本」或「沙箱 iframe」两条路。
- 一条产物都不许带可执行的界面能力。今天能伪造一个「批准」按钮的，
  就只有我们自己写的界面。
- 取产物的通道只读、带路径穿越防护、带大小上限、带并发上限
  （沿用截图证据端点的做法，扩展成按 `id` 取）。
- 评论沿用已有的泳道内评论存储（`review-comments`），不新起一套账。
- **产物清单与机器判词由控制台掌，不由项目视图掌**（§4.2 前两条）：
  项目视图是镜头，不是账本。镜头可以换，账本不能改。

## 9 项目自带界面：两种形态，按需要 DSH 能力与否选

**宿主 261030 定的分工**：界面由项目自己定制，项目自己做；沙盘负责
内置三条泳道（dev-lane / light-lane / quickmanual-lane）的产物面，
外加一条装第三方界面的通道。本节只写这条通道。

**宿主 261030 补的一条事实**：插件需要依赖 DSH 的能力。这条把原来的
「只走页面包」否掉了——要 DSH 能力的项目界面上限更高。

### 9.1 两种形态

| | 甲：沙箱页面包 | 乙：DSH 客户端插件 |
|---|---|---|
| 是否需要 DSH 能力 | 不需要 | 需要（客户端运行时、UI 槽位等） |
| 装在哪 | 项目自己目录里的一组静态文件 | 装进控制台的装配清单（真包，声明 `dsh.client`） |
| 生效 | 下次打开就生效 | 重启控制台（与外置模板同一节奏） |
| 隔离 | 隔离窗口，碰不到主页面 | **无隔离**：跑在控制台页面上下文里 |
| 信任口径 | 内容隔离 | **受信代码**（与外置工作流模板同一条口径） |
| 谁维护 | 项目自己 | 项目自己 |

- **甲**已有先例：执行器面板就是一个服务端托管的独立页面，嵌在工单台的隔离窗口，
  用消息契约对话（`server/plugins/workbench/src/client/executor-view.tsx` 的 iframe）。
- **乙**不是我们发明的东西：DSH 客户端插件本来就是真包（`package.json` 声明
  `dsh.client`，注入客户端运行时与 UI 槽位），经控制台装配清单挂载、重启生效。
  项目和 sandbar 用同一条挂载路，没有特权。

### 9.2 沙盘要做的通道

1. **发现**：项目在自己的登记里声明用哪种形态、装在哪、接管哪些看法
   （新增或覆盖）。控制台启动时扫到。注册表按「项目 × 看法」记，
   **同项目同看法后到者不覆盖先到者，直接点名拒收**；坏了只影响那一包，
   不影响别的项目与内置看法。
2. **装载（甲）**：界面包进隔离窗口；契约最小集 = 哪张票、哪个产物、第几轮、
   字节从哪取（只读）+ 主题。**不给签字权，不给项目登记以外的任何数据面。**
   框架（产物清单、机器判词、原件入口、来源标记）由控制台渲染，不进窗口。
3. **装载（乙）**：按项目登记挂进控制台装配，只在该项目的票上启用。
   框架仍由控制台渲染在插件槽之外；插件出错时整块降级，不影响别的项目。
4. **降级**：两种形态都一样——没装、加载失败、人主动切回 → 退回内置看法（§4.2），
   标出「项目自定义视图不可用」，不白屏、不误报「没有产物」。

### 9.3 已知代价（照实记）

- **乙形态没有技术隔离**：它和签字按钮同一个上下文，框架那条红线
  （清单、判词、原件、来源）在这条路上靠**审查与审计**守，不靠技术边界。
  这与外置工作流模板的取舍同源：受信代码 + 故障隔离，系统级沙箱本轮不做，
  照实记成欠账。
- 乙形态加一个项目要重启控制台（与外置模板「按项目注册、启动时加载、不热加载」
  同一口径）。
- 界面质量由项目自己负责，沙盘不保证好看好用——只保证**能退回内置看法**。
- 每条泳道可以有自己的一套，人门的一致性靠「退回内置看法」兜，不靠强制统一。


## 10 分期（范围，不是进度）

**分界线：基础能力与具体界面分开做。基础能力一项都不押在某个项目身上，
做出来的时候没有一条项目自定义视图也能用。**

### 第一步 基础能力（与泳道、与项目都无关）

做齐这一层，任何人（沙盘自己的泳道、别的项目）之后都能各自往上加自己的看法，
互不影响：

1. **声明格式**：产物不再是裸路径（§3.1），老票兼容照旧。
2. **清单框架**：控制台掌产物清单、机器判词、原件入口、来源标记（§4.2 五条）。
3. **内置六种看法**（§4.1）+ 认不出时的兜底卡（§4.3）。
4. **装载通道**：发现、装载、降级三件事（§9.2）——**必须在基础层**，
   否则「项目自己搞」根本没有入口。
5. **进行中口径**（§6）：跑着的时候能看，且不拿半成品下结论。
6. **过程可见**：按段归位 + 最新一轮 + 与上一轮的差异（§3.2）。
7. **归档与清理**（§7）：有家不搬、按票封顶、保留期、清理台账。

### 第二步 各自往上加（并行，互不影响）

- 沙盘自己的三条内置泳道先接上自己的看法（顺序：dev-lane → light-lane →
  quickmanual-lane）——这是第一个消费者，也是基础能力的实战验证；
- 其他项目各自按自己的节奏接自己的看法，**沙盘不排期、不改代码**；
- 项目之间零耦合：一个项目的界面坏了、慢了、没装，不影响别的项目，
  也不影响内置看法（§9.2 第 3 条）。

### 第三步 只在这一步才做的东西

- 人门审阅板声明（§5 第 2 条：哪几块并排、跟什么对照）与评论落到人门。
  这一步依赖第二步已有真实的自定义视图，否则只是空设计。

## 11 待宿主拍板（逐条给建议，方便直接答）

1. **内置看法是否就这六种**：建议就这六种；项目要别的看法走 §4.2 自定义，
   攒够用法再考虑升为内置。
2. **人门审阅板由谁声明**：建议由泳道声明（内置泳道写在代码里，外置泳道写在
   自己的模块里），不由控制台猜。
3. **归档封顶与保留期** **已定（宿主的 261030 裁定）**：超限**保留最近的**，
   丢最旧的；保留政策（保留期、上限、丢哪些轮次）也由项目自己声明，
   控制台只提供默认值。见 §7.2 / §7.3。
4. **过程看板与审阅板是否同一个位置**：建议同一个位置、两种模式，
   不新开页签。
5. **老票怎么处理**：建议只认路径、猜类型、无轮次，不迁移不回填。
6. ~~先拿哪个项目做样板~~ **已定（宿主的 261030 裁定）**：先做基础能力，
   再由沙盘和其他项目各自往自己的看法上加，互不影响。见 §10。
7. ~~项目自定义界面能不能覆盖内置看法~~ **已定（宿主的 261030 裁定）**：
   沙盘与别的项目同权，可以新增也可以覆盖；框架（清单、机器判词、原件入口、
   来源标记）不许覆盖。见 §4.2。
8. **清理的执行方式** **已定（宿主的 261030 裁定）**：清理也归项目自己定制——
   政策写在项目声明里就生效，不再由沙盘另设开关；项目可以声明「不清」。
   见 §7.4。
