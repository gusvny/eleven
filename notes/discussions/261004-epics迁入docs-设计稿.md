# 立项单（epic）迁入 docs —— 设计稿（草稿，未拆票）

> 来源：宿主 261004 会话原话——「epics 我觉得可以移动到 docs 里去。epic 只保存立项的内容和
> 相关的文档，这些写了后面应该基本不改了（只有 epic 的状态后面会改），所以 git 的提交很少。
> epic 的执行记录这些不存在 epic 的文档上，应该直接用 epic 这个 unique name（epic id）从
> ticket 这边读出来。在 docs 里面，放一个 epics 的目录，然后每个 epic 一个目录（目录名是日期，
> 4 个字母的 hash，epic name），目录里有一个 `<epic name>.md`，然后就是相关的其他文档，包括
> ui mock 等」，以及宿主「按你的推荐来」的授权（语言口径取「跟随 docs」）。
> 本文只写「是什么、为什么」，不写落地状态。细节实现留给拆票。

## Problem

**一句话**：立项单的**形态**是定稿文档，**位置**却在讨论与账本那一侧——两套规矩不同，结果它
既没吃到定稿文档的纪律，又背上了账本才有的约束，同时它的「相关文档」还散落两处。

**背景知识**（给没参与过的人）：

- 本项目有两个库：`docs/` 是**定稿文档库**（有索引与自查清单、语言口径统一、只收已定稿的东西）；
  `notes/` 是**知识库与账本**（讨论草稿、已知问题台账、立项单）。两者制度不同不是历史偶然，
  而是「定稿件」与「会长大的账」本来就是两种东西。
- **立项单**回答「我们要做这件事」：目标、范围、验收口径、边界、以及它的设计稿与界面 mock。
  一笔立项有一个**代号**，建票时用它把票挂到这条立项上；引擎侧按代号就能列出这条立项下的全部票。
- **泳道**是干活的工作流。`notes/` 对泳道是**禁写面**（票据与账本只由 main 侧直管），而 `docs/`
  是允许写入面——这是理解下面取舍的关键：位置决定了「谁能落笔、怎么落笔」。

**实据**：

1. 立项单现在有 13 份、共 164 KB（单份 3.8–29 KB），全部住在 `notes/epics/`。
2. 每份的头部**已经在指**它的相关文档（例：设计基准=`notes/discussions/…设计稿.md`、
   界面 mock=`notes/discussions/…mock.html`）——也就是「一条立项的东西」今天散在**两个库**里。
3. 正文里掺着**执行记录**：引用票号的密度 `project-lifecycle.md` 16 处、`session-entry.md` 11 处、
   `engine-hardening.md` 8 处、`dsh-upgrade.md` 6 处、`doc-lifecycle.md` 6 处。而「这条立项做到哪了」
   的真源是引擎（票上带立项检索键，随时可查），文档里这半是**必变死表**——宪章明令不许在文档里
   手工维护进度与工单清单。
4. 立项单的实际写入节奏**很低**：13 份里绝大多数最近改动停在 9 月上中旬，只有个别在本周被碰过。
   即「写完基本不改」成立——这正是定稿文档的形态（对应 `docs/` 的准入标准），而不是账本的形态。

## Requirement

（每条都能当验收判据用）

1. **一处看全**：一条立项的本体与它的相关文档（设计稿、界面 mock、对外契约图等）**同住一个目录**，
   不需要在两个库之间跳。
2. **正文不含进度**：立项单正文只承载「是什么、为什么、范围与验收口径、边界」；**不出现**进度表、
   工单清单、「已完成 N 张」这类登记表。做到哪了一律按立项代号向引擎查。
3. **代号仍是唯一机器键**：建票挂立项、按立项查票的**对外行为不变**——拿同一个代号，搬迁前后
   查到的立项与票集合逐条相同。
4. **受定稿文档纪律**：进了定稿库就吃定稿库的规矩（头部字段齐备、被索引收录、设计文档自查清单、
   统一语言口径）。
5. **零行为漂移且报错点名**：搬迁前后「代号→立项→票」三态一致；代号找不到、或者同代号命中
   不唯一时必须**具名报错**，绝不静默挑一个。
6. **相关人**：宿主（要能一眼看懂、一眼看全）、integration（main 侧落笔的人）、泳道（读得到）、
   引擎（按代号查票）、以及未来的 agent 读者（把立项当上下文读）。

## Nongoal

1. **不动账本**：已知问题台账、讨论草稿、请求账仍然住 `notes/`、仍然中文、仍然**单写者**。
   本次只迁「定稿件」。
2. **不给文档新造泳道**：文档泳道是另一件事（见 `261004-doclane-设计稿.md`），本次搬迁走现有泳道。
3. **不重建立项与票的关联机制**：引擎按代号查票的能力今天就有，本次只用、不打补丁。
4. **不借搬迁顺手改内容**：除语言口径要求的那一遍改写外，立项单内容零重写。
5. **不引入目录名 hash**（理由见 Proposal 取舍一）。
6. **本次不定「谁有权改立项单」**：沿用现状（main 侧 integration 按宿主授权直改）。若日后开文档
   泳道，这条随之重定。

## Proposal

### 高层（一页能懂）

立项单从 `notes/epics/` 迁到**定稿库下一个「一条立项一目录」的树**：

- 目录名 = **日期前缀 + 立项代号**（人看得懂先后，机器只认代号那一截）；
- 目录里 = 立项单本体（文件名就是代号）+ 它的相关文档（设计稿、界面 mock、契约图……）；
- 立项单头部写**一次性的立项事实**（含状态这一个字段）+ 指向同目录其他文档的链接段；
- 正文只留「是什么、为什么、边界、验收口径」；**执行记录删掉，改为按代号向引擎查**；
- 搬迁是**一次原子动作**：位置、查找规则、引用、索引四类面一起改，改完对外行为逐条不变。

### 关键取舍（每条都说清为什么）

1. **代号是唯一键；目录名只加日期前缀，不加 hash。**
   代号今天已经是唯一的机器键（建票挂立项靠它、按立项查票靠它）。再塞一个来源不明的短 hash，
   等于给同一个对象第三个标识符：查找要从「精确一份」变成「模糊匹配」，人会抄错，两份同代号
   目录打架时无法判定谁对。日期前缀保留，是因为它对人排序有用，且解析规则简单（代号那一截
   才是键）。**查找规则三态写死**：命中一份=通过；命中多份=具名拒收；命中零份=具名拒收。
2. **状态放头部字段，正文禁进度。**
   状态确实要改，但它是**单个、机器可读**的点：放头部。进度不是「少量改动」，它是持续生长的，
   写进正文必然变成死表（今天已经在犯，见 Problem 实据 3）。「做到哪了」有真源（引擎按代号
   查票），文档不必也不该复述。
3. **目录里只收定稿件。**
   立项单的「写了基本不改」是这次搬迁的前提。混进未定稿的讨论草稿，这个前提当场消失，
   而且会让人分不清哪份是准的。规则：草稿仍留讨论库；**定稿后移入**（保留文件历史）。
4. **语言跟随定稿库。**
   定稿库今天是统一语言（唯一刻意例外是术语表）。再开第二个例外，等于宣告「例外常有」——
   规矩就没了。**宿主原话属引用**，可以在英文文档里原样保留中文；这是既有豁免，不需要新例外。
5. **一次搬完，不分两步。**
   位置、查找、引用、索引四类面互相咬合：留着旧位置就会出现「两份都像真源」的中间态，
   而任何一次遗漏都会以红的形式出现（路径变了，按路径记录的东西全部认不出）。宁可一次做完。

### 细节（只写「不写下来就会有人搞错」的部分）

- **命名形状**：目录名以日期起首、以代号结尾；立项单文件名就是代号；同目录其他文档保留各自的
  描述性名字（设计稿、mock、契约图各按自己的形态）。
- **命中规则**：查找一律走「精确代号 + 唯一命中」判据；三态行为（一份/多份/零份）都要有
  具名结果，且零份与多份的错误文案要说得清 **是哪条检查失败**（是没建、还是重名）。
- **立项单头部**：标题、类别、标签、状态、更新日期，缺一不可（定稿库的通用要求）；正文末尾
  要有「相关文档」段，指到同目录的其他文档。
- **删掉的那半怎么算数**：正文里原有的执行记录段落直接删除（不是搬走）；它们的信息在引擎里
  活着，需要时按代号查。搬迁票要给出「搬迁前后查票结果逐条相同」的对照证据。
- **耦合面清单**：见附录 A（勘察结果，供拆票；不是设计内容）。

### 回扣

本提案 → 解决 Problem 的「形态与位置错配、相关文档散落两库、正文养死表」三件事，
→ 满足 Requirement 1–6（一处看全、正文无进度、代号仍是唯一键、受定稿纪律、零行为漂移且报错点名），
→ 不去碰 Nongoal 划下的六条边界（账本不动、不新造泳道、不重建关联、不顺手改内容、不引入 hash、
  本次不定权限）。

## 附录 A：搬迁耦合面（勘察结果，供拆票；非设计内容）

今天与「立项单住在哪」咬合的面（一处不改就会红或出现双真源）：

1. 立项目录的**解析点两侧**：引擎侧与面板侧各有一份同源拼装规则，且**有专门的场景锁「两侧同源
   且等于项目主目录下的立项目录」**——只改一侧即红。
2. **建票挂立项的校验**：代号要能在立项目录里找到，位置变了校验跟着变。
3. **容器脚手架**：新建项目容器时生成的知识库骨架里包含旧立项目录的占位，清单断言按旧路径写。
4. **文档索引**：定稿库的索引器按目录收录，迁入的立项单必须带齐头部字段，否则索引面缺件。
5. **术语看守的路径帽键**：术语禁用词的「按文件次数上限」基线里，有四份立项单以旧路径登记；
   路径一变，它们就成了「不在基线内」即红；且帽值只许降不许升，需要随搬迁一并处置。
6. **正文互引**：讨论库里的 runbook、立项单之间的相互引用，以及其他文档对旧路径的指称；
   历史证据目录里的旧路径引用可不动（那是历史留痕）。
