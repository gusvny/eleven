Interaction, and the wiring check

Two things are actually clickable in this mock and both are now verified mechanically.

Tabs: an earlier revision had three panes whose ids collided with the radio inputs (t2 · t3 · t5), so the CSS pointed at #p2/#p3/#p5, found nothing, and those tabs rendered empty while the rest worked. Ids are now semantic (tab-* for radios, pane-* for panes).

Requests: the first master–detail pass rendered only R-14's detail, so clicking R-13 did nothing — the list looked broken. Each row is now a label bound to its own radio, and the right-hand side holds one detail block per request (det-r14 · det-r13 · det-r11), so clicking a row really does switch the detail, including the resolved one.

The check runs on the mock as a whole: duplicate ids, every <label for> resolving to an input that exists, every radio:checked CSS rule pointing at a real element, and no orphan radio or pane. Nesting checks alone missed both bugs; wiring checks are what catch this class.

Queue vs Steer

These are the two ways an instruction can be delivered to a session that may be busy right now — the session interface's own vocabulary, not something invented here. Queue appends a turn: it waits for the current one to finish and runs in order, interrupting nothing — the default. Steer interrupts the running turn and takes over immediately; it is the emergency brake (it is about to do something you do not want, or it is stuck in a loop), because that turn stops half-done — files may be edited but not committed and an in-flight tool call's outcome is unknown. The mitigation is the same discipline used for restarts: every direct fix is a commit, so the checkpoint survives. Two consequences for the UI: a queued instruction must be visible (otherwise a ten-minute turn makes you think it was ignored), and a queued item can be edited, removed, or promoted to Steer.
