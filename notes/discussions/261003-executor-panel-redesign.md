# 执行器面板改版（261003 宿主定稿口径）

> 来源：261003 与宿主的逐轮过稿。宿主原话要点：「这个设计太烂了」「UI 简洁一点，不要搞一堆
> 说明文字」「有选项的 request 就不要让人填文字」「overview 里显示 executor 最近做的事情，
> 比如 sign 了某个 ticket、retry 了某个 ticket」「要有一个按钮可以 enable/disable executor」
> 「needs you 的信息按 80% 的 ASD-STE100 标准来写作」「把 overview 和 requests 合并，两个竖排
> 并列」「grants 可以开个 tab，让人选择」。
>
> 视觉基准（宿主已过目）：`notes/discussions/261003-executor-panel-redesign-mock.html`。
> 本文是草稿账本条目（notes 属草稿纸）；定稿迁 `docs/design/` 由宿主决定。

## 1. 为什么要改（现状的四个毛病）

1. **看不出「有没有事等你」**：未答与已答的区别藏在详情里（有无输入框），列表本身不告诉人。
2. **答过的行永久占着主视野**：请求行设计上不删除，于是列表只增不减，越用越糊。
3. **满屏解释性长句**：界面上到处是给自己辩白的长文案，读起来像说明书，不像操作面。
4. **没有「它最近做了什么」**，也没有能开关执行器的地方；授权只能在接口层面改，页面上
   没有授予控件（详见 §5）。

## 2. 版面（定稿）

- 顶部只有 `Executor` + 项目标签。**不要**项目选择器（下拉 / 手填 key / Load 按钮），
  **不要**轮询状态行（"polling every 5s · last ok …"）——从哪个项目行进面板，就是哪个项目。
- 页签：**Overview / Grants / Alerts / Ledger / Settings**，等待条数以徽标挂在 Overview 上。
- **Overview 与 Requests 合并**（原 Requests 页签取消）：**两栏并列**——左「等你回」，
  右「最近动作」；窗口窄于约 760px 自动改为上下叠放（面板挂在控制台中列，宽度不定）。
- Ledger 简化成四个数字（行数 / 重复 / 坏行 / 缺口）+ 账本路径 + 最近三条事件。
- Settings 只留守望者与提醒配置。

## 3. 交互（定稿）

- **每条 waiting 项可展开**：收起态一行（状态点 + 问题 + 类型·等待时长 + 三角）；展开后三段：
  ① 详细内容（等宽小字块，超高自动内滚，最高约 170px，再长也不撑爆列表）；
  ② 回答控件；③ 溯源小字（谁提的 / 请求 id / 默认动作）。
- **有选项的请求给按钮，不让人打字**；没有选项的才给输入框。选项与默认动作由请求方在提出时
  一并给出（新增数据面，见 §6）。兜底入口叫「Type an answer」。
- 答完即收进折叠的 `Answered`，可再展开回看（详细内容与答复都保留）。
- **授权集中在 Grants 页签**：总开关 + 被点名的执行器会话 + 六个权限各一个开关 +
  「仅宿主」的改权限条目（灰、不可点）+ Give all / Give none 快捷键 + Save。
- Overview 上的 `Disable executor` 与 Grants 总开关是**同一份状态**：关掉＝
  **收回全部授权**（它只能看和问），**守望者照常运行**（仍唤醒、仍告警）。
- 「最近动作」每条：时间 + 动作 + 票号 + 一句话结果；动作上标出**凭哪条权限**做的。

## 4. 文案（定稿：英文按 80% ASD-STE100 口径，中文按同构的「受控中文」8 条）

两种语言各按自己的口径，同一份产物不混用。STE 是英文标准（受控词典绑定英文），
但**规则层**同样适用于中文——261004 宿主令：「STE 类似的作为中文输出的标准」。

### 4.1 英文产物（ASD-STE100，80% 口径）

1. 短句：描述句不超过约 25 词；一句一个意思。
2. 主动语态、现在时；要人做的事用命令句。
3. 一个词一个意思，全文固定术语：ticket / executor / permission / session / stage / gate /
   merge / alert / watchdog。
4. 不用行话、比喻、缩写词；不用缩略形式（don't、won't 一律写全）。
5. 名词簇不超过三个词。
6. 标识与数字用冒号引出（`Ticket:`、`Request id:`、`Default action:`）。
7. 状态句也写成完整句（「Self-lock cleared.」）。
8. 面板内所有文案（含 Grants / Settings / Ledger / Alerts）一律照此口径，不留例外。

样例（改前 → 改后）：

| 改前 | 改后 |
|---|---|
| Anything to add before I open this ticket? | Do you have more instructions before the executor opens this ticket? |
| Grant executor permissions? | Which permissions do you give to the executor? |
| …locked by a shared fixture, so a future rename … instead of drifting silently. | A shared test file locks two lists: the knob list and the permission words. / If you change one name on one side, the build stops. / The two lists cannot go out of step without a signal. |
| 选项 None | 选项 No permission |
| stall — t261002-10 idle 16m | Ticket t261002-10 did not move for 16 minutes. |
| 区标题 Needs you（习语） | Needs your answer |
| 兜底链接 Other… | Type an answer |

### 4.2 中文产物（受控中文：与 STE 同构的 8 条）

适用于中文对话回复、中文备注、中文交接与说明文字。

1. 一句一个意思；陈述句不超过约 25 字，超了就写成两句。
2. 主动语态、现在时；要人做的事用命令句（「先打回，再重跑」）。
3. 一个词一个意思：按 `docs/terminology.md` 用词表（中文为主，在册术语可留英文原词）；
   同一个东西全文不许换叫法。
4. 不用行话、隐喻、四字格堆砌、生造缩写（术语表在册的英文原词除外）。
5. 名词串不超过三段——「泳道合并冲突消解回路上限」这类要拆成短句或用标点断开。
6. 数字与标识用冒号引出（「票号：t261003-10」「已等：12 分钟」）。
7. 状态写成完整句（「执行器停摆。」不是「停摆中」）。
8. 不用双重否定、不堆被动、不填空词（「进行／相关／处理／情况」能删就删）；
   不写自我辩白的长句。

样例（改前 → 改后）：

| 改前 | 改后 |
|---|---|
| 该票当前处于因主同步同批文件反复冲突而转人工处置的阻塞状态 | 票卡住了：合并 main 时同一个文件反复冲突，已经交给人工。 |
| 执行器尚未被唤醒，故未能对阻塞做出响应 | 没人叫它，所以它不知道票卡住了。 |
| 请在上述选项中择一以完成授权范围的配置 | 选一个授权范围。 |
| 相关处理流程正在进行中 | 正在跑第 2 步。 |

## 5. 本次改版必须一并覆盖的既有缺陷（定位已核实，只定位未修）

1. **授权保存面会静默丢掉「点名执行器会话」**：保存回执报成功，但写盘的声明里没有这一项。
   引擎侧认这个字段、读出面也认，唯独保存路径不搬运它。后果两个：界面上保存「点名」会丢；
   此后任何一次保存（包括一键收回）都会把它一起抹掉。**改版后的 Grants 页有会话输入框，
   等于把这个洞摆到台面上，必须先修。**
2. **授权读出把「行数」当「操作数」**：读出面的计数按「操作 × 模板」的行数统计，六个操作会被
   报成 18，界面上写成「18 个操作已授予」。改版后必须是「Permissions: 6 of 6」这种口径。
3. **会话点名缺失时的读出面**：点名缺席时能力矩阵仍照常渲染，容易读成「已授予」。改版后的
   读出面要显式区分「没点名 / 点名了但零授予 / 已授予」。
4. **请求的选项与默认动作在镜像路上被丢掉**（261004 实测，违背 §6 那条「一并给出」）：
   `question-bridge.ts` 的镜像只搬 `question`/`detail`/`raised_by`/`kind`，`options` 与
   `default_action` 都不进账（`appendRequest` 本身收这两个字段）。后果：执行器就算规规矩矩
   用 `ask_user_question` 提问，面板也只给「Type an answer」——**选项按钮永远不出现**。
5. **一次多问被压成一条**：镜像把第一问当 `question`，其余各问编号拼进 `detail`。面板上
   看不出「有三个决定要裁」；应答回填又按「整行恰等于某条 option 标签」匹配，且各问各自
   `filter`，**两问出现同一标签时一次应答会同时命中**。
6. **纯汇报占着待答位**：没有可答问题的条（原文写着「不必单独回复」）照样进请求账，
   面板把它算进「Needs your answer」——宿主点开发现无话可回。

7. **写端点没有身份面（261004 实证，详见 KI-193）**：控制台首页要 token（`curl /` → 401），
   插件路由不要（`/sandbar-executor-panel/api/...` → 200）；且 `by` 由调用方自报
   （`src/host/api.ts:155/190/217/227`）。执行器会话同机有 shell ⇒ 一条 curl 即可自授六项权限、
   伪造宿主应答。授权面的写必须回到引擎侧 `META_OP` 判定（面板只投递），审计要记来源。

## 6. 待定项（给实现方，别另拍）

- **「最近动作」的数据来源**：必须能回答「做了什么 + 凭哪条权限」。引擎对受闸写动作已留下
  可核对的观测键；实现方须选一个稳定的只读来源，并规定不可得时**显式降级**（点名原因），
  绝不用空列表冒充「最近没动作」。
- **请求的选项数据面**：提出请求时一并给出选项与默认动作；没有选项才退回自由文本。

## 7. 验收要点（票面 acceptance 引用本节）

- 版面与 §2 一致：五个页签；项目选择器与轮询状态行不存在。
- 交互与 §3 一致：选项按钮、条目可展开且长内容内滚、两栏并列且窄屏叠放、收回授权只影响授权。
- 文案全量符合 §4（Grants / Settings / Ledger / Alerts 逐页抽查）。
- §5 三条各有回归：保存后点名仍在；读数报「6 of 6」；点名缺席时读出面显式区分三态。
- 视觉以 mock 为基准：`notes/discussions/261003-executor-panel-redesign-mock.html`。

## 8. 请求要能回（261004 宿主实报「这么写我能回吗」后定）

**现况实测**（项目请求账 13 行：8 条请求 + 5 条应答）：3 条待答里，1 条问句与选项只覆盖了
两件事中的一件（第二件无选项可点）；1 条根本不是问句（原文写着「不必单独回复」的汇报）；
剩下 1 条能答，但 1678 字的证据把决定压在最后一行、且落在 170px 的滚动框里。已答的 5 条里有
两条是「要不要重启 / 要不要开票」这种是/否题，**一个按钮都没有**，宿主只能手打。

**写请求的规矩（谁提问谁遵守，与「必须说人话」同族）**：

1. **一次请求 = 一个决定**。两件事分两条；多问的用 `ask_user_question` 的多问形状提，
   不要塞进一条的 `detail`。
2. **`question` 是一行问句**（≤60 字），把要裁的事和可选方向说清楚；背景不进问句。
3. **`options` 2–4 条短标签**（每条 ≤20 字，推荐项排第一并标「推荐」）；**没有选项就必须给
   默认动作**（不答会发生什么），别让宿主自己想。
4. **`detail` 只放证据**，摆在问句**之下**；长清单/大表格折进折叠段。结论先写，过程后写。
5. **纯汇报不进请求账**：没有要裁的事就写进台账或聊天；「要不要开票」也要写成问句。
6. **术语要么不用，要么当场一句话解释**——请求账与聊天同一口径（黑话不算人话）。
7. **引用另一条请求：用「短句柄」，不写原始 id**（261004 宿主实报「上面还写了 req 的 id，
   但其实我也不知道是哪个，因为 ui 上也没有显示 id」）。原始 id 形如
   `req-1791085168678-0001`——它现在**只在展开后的 trace 小字里**才有，卡片面上没有任何可对照的
   标记；而且后缀 `0001` 在同一批里会重复（实测账上三段都叫 `-0001`）⇒ 光看后缀也认不出。
   **规则**：面板每张卡在可见位置显示一个**短句柄**（唯一、稳定、≤6 字符、可复制），
   追加/续报一条请求时引用它（必要时附**原问句的关键词**，例如「追加·上一条（开票权那条）」）；
   **禁止**把原始 id 当人对人的指代。历史行不留改动：面板对正文里出现的原始 id
   自动渲染成该短句柄（可点、跳到那条），让**已经写下的旧行**也认得出来。

**面板侧的实现要求**（判据，不是建议）：

- 选项**不展开就能看见并直接点**；点一下即应答。
- 一次多问时**逐问一行、各自可答**，答哪问是哪问（同标签不串问）。
- 显式给出「不答会怎样」（默认动作）与该条的等待时长。
- 答案框支持**多行**；选项之外的自定义答复能落到**指定的那一问**上。

验收以本节 1–6 与上面四条判据为准；基线 mock：`notes/discussions/261003-executor-panel-redesign-mock.html`
（本次要补「请求卡」一屏：多问、选项常显、默认动作、多行答框）。

## 9. 请求的处置：Dismiss（261004 宿主裁定）

宿主原话：「这个 request，是不是缺个 dismiss 之类的按钮，就是我看到了。不想处理。」

**定稿**：请求卡加一个 **Dismiss** 动作，语义是「**看过了，不裁**」——不是同意，也不等于默认动作被触发。

- **落账**：新增行类型 `dismiss`（`{type:'dismiss', dismiss_for:<id>, at, by:'host'}`），**与 `answer` 分开**——
  answer 带决定内容，dismiss 不带。读出视图的 `status` 增第三态：`waiting | answered | dismissed`。
- **界面**：点一下就从「Needs your answer」出去，落进**折叠的 `Dismissed · N` 组**（与 `Answered` 并列）；
  卡上写「Dismissed by you. Your default action applies.」——**默认动作照旧由执行器执行**，
  执行器不得把 dismiss 当批准。
- **不许再问同一件事**：被 dismiss 的请求，执行器**不得原样重投**；同一件事有新证据要重提时，
  必须在 question 里点名「上一条已被 dismiss + 新证据是什么」。
- **可以改主意**：dismiss 之后仍可补一个 answer；answer 一到状态回 `answered`，
  两条痕（dismiss 与 answer）按时间序留在 trace 里。
- **谁能不能 dismiss**：宿主专属（与授权面同级）；执行器不得 dismiss 自己的请求。
- **与「无决定的条」的关系**：源头仍然要治（§5 第 6 条：没有可裁的事不进请求账）；
  dismiss 是宿主手里的**兜底出口**，不是给脏数据擦屁股的常态路径。
