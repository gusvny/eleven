# 261004 并发上限（Running tickets）设计稿

> 状态：**草稿，等宿主过 mock**（`notes/discussions/261004-concurrency-limit-mock.html`，v1）。
> 宿主令原话：「今天你要『控制并发』，实际可用的手段只有人肉暂停 + 不再派新票。要不要开票把上限
> 做成声明（例如「同时非终态泳道 ≤ N，超了排队」——这个我想做成 project 级别的，在 executor panel
> 上可以配置。就在 overview 上加吧。做个 mock 我看看。」

## 1. 为什么要有它（261004 实测）

- **引擎里没有这个旋钮**：查过 `activities.py` / `agent_activities.py` / dispatch 面，只有闸内并发
  （`SANDBAR_HANDOVER_CONC`、场景并发 12），**没有「同时在跑的泳道 ≤ N」**。
- 今天同时开过 **7 条泳道**，代价是实打实的：verify_lane 的 pytest 段 5.5 分钟/轮，两条时序敏感
  测试（`test_d2b_carrier_…`、`browser-state.test.mjs` 的 detail-scroll）在负载下随机红，
  还可能被误读成「实现段 code-fault」（KI-182/184 同族：机器噪声污染放行口径）。
- 现有的控制手段只有**人肉**：暂停（**段间生效**——在飞的段会跑完）+ 不再派新票。前者不精确，
  后者靠人盯。

## 2. 形态：两块一对（宿主 261004 二次裁定后改的）

> 宿主两次口径：先要「Overview 上加」，看过 v1/v2 后说 **「过于 informative」**（点名：后果句、队列明细、
> FIFO 说明、折叠说明都不要）；再补 **「我们左栏已经有工单列表了，可以在左栏调优先级，左栏工单列表的 ui
> 一起调整」**。所以上限与顺序**分居两处**，各司其职。

### 2.1 右栏（执行器面板 Overview）：**只管上限**，一行

```
RUNNING TICKETS  [AT THE LIMIT]                        set by you 10-04 14:02
┌──────────────────────────────────────────────────────────────────────────┐
│ Limit  [−] 3 [+]  ·  3 at work  ·  4 waiting                    [Save]   │
└──────────────────────────────────────────────────────────────────────────┘
```

- 状态 chip 三态：`room to start one` / `at the limit` / `over the limit`（琥珀）；
- **界面上不解释、不列队列、不放折叠说明**——口径写进本文档，不写进界面（宿主要求）；
- 审计行（谁在何时改的）保留在区块头右侧，一个短语。

### 2.2 左栏（控制台的工单列表）：**管顺序**，顺序就是启动顺序

- 每行两行制：**第一行 = 票号 + 标题**（给足宽度），**第二行 = 阶段**（小字等宽）；
- **排队中的票**行首带**位次号**（1、2、3…），并可**拖动**（⋮⋮ 把手）或用 **⌃ / ⌄** 调序；
- **在跑的票**行首是**绿点**、**你暂停的票**是**琥珀点**——它们**不参与排序**（无把手、无箭头）；
- 列表头只报两个数：`3 at work · 4 waiting`（不写句子）；
- 一行版式决定：左栏 380px 宽（340px 下标题被截得太狠）。

## 2.3 两块怎么配合

**左栏的顺序 = 谁下一个开跑；右栏的上限 = 同时最多几个在跑**。额度一释放（有票完成/失败/转人门/被暂停），
就按左栏顺序从队首取一条开跑。宿主只在一处调顺序、一处调上限，不必记两套规则。

## 3. 语义（判据写死，别留给实现各拍）


1. **只有「当前段正在跑」的票占额度**（agent 在思考、或某个检查在跑）。
2. **不占额度**：等宿主签字的票、被你暂停的票、已终结的票——它们不耗机器时间，
   就不该占坑（这条是这块设计的核心，不写清就会变成「一堆停在 merge 的票把额度全占住」）。
3. **超出即排队**：队列 **FIFO**；票已创建但**首段不得开跑**，直到有额度释放。
4. **下调到低于在跑数：不打断任何在跑段**，只影响下一次启动（面板明写这句，避免以为会杀活）。
5. **额度的每个终态都要销账**：完成 / 失败 / 被暂停 / 转人门 / 取消——凡占过额度的，每个终态都要放回去
   （资源生命周期纪律：否则额度会「泄漏」，表现为永远排不上队）。
6. 范围 **1–10**，默认 **3**（今天的实测：3 条在跑时闸的墙钟与抖动都正常，5–7 条开始出噪声）。

## 4. 落点与审计

- 声明落在**本项目自己的声明文件**里（机器级项目目录，宿主直管；与 `executor-grants.json`、
  `watchdog.json` 同族），**不写进受保护的仓内配置**。
- 每次改动入项目动作账（谁、何时、从几改到几），面板显示最近一次改动；与授权面同一纪律
  （`by` 不可由调用方自填——KI-193 的教训）。

## 5. 引擎侧要什么（真正的工程量在这）

1. **一个「排队」态**：票创建后不等于立刻开工；派活/启动侧在开跑前判额度，不够就排队（不是先跑再暂停——
   段间暂停拦不住首段）。
2. **额度释放的触发面**：段结束、票终结、票转人门、被暂停——每处都要销账（见 §3.5）。
3. **可见性**：排队位次与已等时长要能被面板读到（面板只读账，不自己算）。
4. **与既有暂停的关系**：被暂停的票自动不占额度（不需要额外动作）。
