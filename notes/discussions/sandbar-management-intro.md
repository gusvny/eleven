# Sandbar：从 Agentic Coding 到 Agentic Engineering

## ——一套 Engineering Domain Harness 先导实现

> **核心论题：下一次工程生产力的突破，可能不来自更强的模型，而来自一个更好地组织、验证和复用模型智能的系统。**
>
> 面向管理者的技术介绍 · 2026-09 · 内部草稿

---

## 一、问题陈述：Agent 已经很强大，瓶颈移到了人这一侧

先把一个容易犯的归因纠正掉：问题不是「工程师不会用 Agent」。恰恰相反——今天的工程师已经非常会用 Agent 了，同时开 3–4 个会话并行推进是常态。真正的问题是使用方式本身：**编排仍然由人肉承担**。

```
Engineer
 ├── Agent #1：开发
 ├── Agent #2：评审
 ├── Agent #3：测试
 └── Agent #4：另一个任务
```

人负责：判断哪个 Agent 做什么、给 Agent 喂上下文、记住各自的进度、在窗口间切换、把 A 的结果转述给 B、出错后恢复、电脑关机后重建全部背景。往下挖，是四个层层递进的架构问题：

**问题一：人是调度层，切换本身就是成本。**
3–4 个并行会话已接近人的认知极限。真正浪费的往往不是 Agent 的 token，而是**人的认知切换**：每切一次窗口，人脑要重新加载当前任务、当前状态、为什么这样设计、做到哪了、哪些假设还没验证、下一步是什么。公式化地说：**Agent 并行度 ≠ 人的生产力**——「4 个 Agent + 1 个人肉调度器」不等于 4 倍产出，只等于一个被调度工作填满的人。

**问题二：聊天记录不是工程状态。**
Agent 会话里的上下文是易逝的：会话结束、终端消失、电脑关机、上下文窗口到限、换 Agent、换模型——任何一件发生，大量工程上下文即告蒸发。第二天开工的第一句话经常是：「我们昨天做到哪了？」而工程真正需要持久的是另一套东西：**目标、任务、依赖、状态、决策、产物、证据、验证结论、失败、重试、责任人、下一步**——今天的工具链里没有任何一层为它们负责。聊天记录 ≠ 工程状态（Conversation ≠ State），这其实是非常严重的架构缺陷。

**问题三：Agent 看得见任务，看不见工程。**
给系统加一个支付功能，真实的依赖结构是：接口定义 → 数据库 schema → 前端适配 → 测试 → 性能验证，环环有先后，改了 schema 就得同步改查询与回滚预案。这些依赖今天活在哪里？活在负责人的脑子里、项目排期表里、站会的一句口头交代里——没有任何一层系统真正掌握它。于是并行干活的 Agent 各自埋头改自己那一片：写接口的不知道 schema 已经变了，写测试的在测一个过时的版本，两个半成品最后拼不上。**工程的依赖全景图，至今只能由人脑持有**——Agent 不知道自己的改动挡住了谁、依赖着谁、重复了谁。

**问题四：Coding 只占工程生命周期的一小环，而验证还是老办法。**
一个工程任务的真实生命周期是：需求 → 架构 → 规划 → 依赖发现 → 实现 → 测试 → 集成 → 评审 → 安全 → CI → 部署 → 灰度 → 观测 → 事故 → 回滚 → 文档。即便 Agent 把 coding 提速 5 倍，验证仍然停在两个老极端：AI 自己检查自己（生成者自验，幻觉无人拦），或者人逐行读两千行 diff（瓶颈回到人）——整个生命周期的吞吐根本没有变。**行业需要从 AI Code Generation 升级到 AI Engineering Execution。**

**问题五：工程能力的底座，租在别人的闭源模型上。**
前四个问题决定工程跑多快，第五个决定跑在哪条路上。先看一个容易被叙事掩盖的趋势：**模型的代码能力提升可能正在放缓**——新一代旗舰（如 Fable 5.1、Astra）的代码能力边际提升开始收窄。「买最强的闭源模型」，沉浸在「顶尖模型无敌」的叙事里其实是**饮鸩止渴**：短期见效快，长期越依赖越空心、越受制。隐性代价有四层：

- **成本失控**——顶级模型单价数倍于次级模型，而工程场景的 token 消耗随并行度与迭代次数线性放大：编排、返工、验证的每一轮都烧在最贵的模型上，吞吐越提升账单越失控；
- **黑盒不可控**——闭源模型行为随供应商版本静默漂移：一次升级，昨天验证过的产出今天不再可复现，工程质量的根基被动摇；更隐蔽的是供应商侧的**隐性降级**——安全审查、成本优化、容量压力都可能让你的请求被悄悄换模型、砍上下文、加过滤（Huggingface 已公开披露过此类模型路由不透明问题）：**企业即使付费，也无法合同性地保证获得标称能力的 100%**；推理过程不可审计，出了问题无法归因到「模型为什么这么做」；
- **合规与数据风险**——代码、schema、业务逻辑全量流经第三方 API；无法自托管，私有化部署与强监管行业（金融、政企）直接无解；模型废弃、限流、涨价都是供应商单方面手里的牌；
- **资产空心**——所有能力都长在别人的模型里，换代即贬值；竞争对手用同一个模型得到同样的产出——零差异，零护城河。

**打铁还需自身硬**：企业的工程能力必须长在自己的系统里，而不是租在别人的模型里。

**五个问题的共同根源：模型层年年进步，模型之上的工具层也在快速进步——但往上那一步「让一群 Agent 像工程组织一样工作」，至今没有成熟答案。模型红利持续兑现，却被系统层的原始状态漏掉：模型更聪明了，验证仍是生成者自报的，经验仍在随会话蒸发，并行仍靠人盯窗口，供给仍攥在模型供应商手里。瓶颈正在从模型层移向系统层。**

## 二、现有工具的边界：通用 coding harness 止步于「单个 Agent」

工程师手头的工具——Claude Code、Cursor、Codex 这类通用 coding harness——已经相当强大。但一层之隔，两个问题：通用 harness 回答的是 **how to execute**（单个 Agent 怎么工作：shell、文件、git、工具、沙箱、模型路由、子任务派生）；企业真正要回答的是 **what to execute + how to know it's done**（Agent 到底该做什么、什么时候算做完）。上面五个问题，通用工具结构性补不上：

**1. 它的单位是会话，不是任务。**
任务在普通 harness 里不是持久化实体，只是会话里的一段对话——会话结束，任务的上下文、进度、承诺全部蒸发，跨会话接力靠人复述背景。「多开几个会话」不是编排，只是把调度负担从写代码挪到了盯窗口。

**2. 它给人更多上下文，不替人组装上下文。**
贴哪些文件、解释什么背景，仍是人的工作。更关键的是它不区分「验证过的事实」和「讨论中的草稿」——什么可信、什么待验证，这种可信度分层是工程领域的知识，通用 harness 结构上不携带。

**3. 它的验证默认是「生成者自报＋人抽查」。**
派一个 subagent 复核？它和写代码的 agent 共享同一棵推理树，本质是同一个大脑的自我对话，不是独立证据。测试当然能跑，但流程不强制「闸门不过、不得进下一站」；「做完了」由 Agent 自己宣布，而不是系统按完成定义判定。

**4. 它的失败经验不变成系统资产。**
坑踩过了，只留在会话历史里；下个会话、下个项目从零开始。没有缺陷账本、没有「修复必须钉死回归测试」的机制、没有知识从讨论到定稿的沉淀管线——用得越久，不会越聪明。

### 它们内建的 workflow 能力，同样止步于此

这些工具如今也在把「流程」塞进来：plan mode、subagent 委派、skills 记忆、hooks 自动化、云端后台任务。逐个看它们卡在哪里：


| workflow 机制           | 它做到的             | 结构性问题                                              |
| --------------------- | ---------------- | -------------------------------------------------- |
| 计划模式（plan / todo）     | Agent 自己列步骤、自己执行 | 计划活在会话内存里：不持久、没有验收标准附着、「勾完」≠「做对」——计划不是可审计的承诺       |
| 子任务委派（subagent）       | 派生子 Agent 干活、复核  | 树状委派共享同一棵推理树——复核是同一个大脑的自我对话，不是独立证据；子任务的验证结论不留结构化痕迹 |
| 技能与记忆（skills / rules） | 沉淀提示词、规则、偏好      | 平面知识，不区分「已验证的事实」和「讨论中的草稿」；靠人手工维护，失败不会自动变成免疫力       |
| 钩子自动化（hooks / CI 集成）  | 单点触发检查、拦截        | 不是流程引擎：没有持久状态机，崩溃即蒸发；表达不了「闸门不过、不得进下一站」的流程纪律        |
| 云端后台任务（cloud tasks）   | 异步跑完交付结果         | 黑盒执行：中间没有人审点；任务之间互相不知道对方存在——没有工作图，并行靠人开多个黑盒        |


五个机制殊途同归地缺三样东西：**持久化的流程状态**（关机、崩溃、换模型，任务就得重来）、**客观的完成判定**（做完由 Agent 自宣或一个 CI 信号，没有分层验证与证据链）、**组织级记账**（权限、审计、资产沉淀不在系统的一等公民位置）。

一句话：**通用 coding harness 及其 workflow 是「会话的自动化」——把一个会话做得更长、更自动，本质是能力放大器；缺的那一层是「工程的组织化」——让几十个 Agent 像一个工程组织一样工作，有分工、有交接、有验收、有账本、有记忆。放大器不产生组织者。**

## 三、缺失的一层：Engineering Domain Harness

把 AI 工程栈拆开看，中间缺了一层：

```
┌─────────────────────────────────────────────┐
│      ENGINEERING DOMAIN HARNESS（缺失层）    │
│   工作图 / 上下文组装 / 验证体系 / 经验沉淀  │
├─────────────────────────────────────────────┤
│      GENERAL AGENT HARNESS（已有）           │
│   模型路由 / 工具 / 沙箱 / 子任务 / 运行时   │
├─────────────────────────────────────────────┤
│      FOUNDATION MODEL（已有）                │
│   Claude / GPT / Gemini …                    │
└─────────────────────────────────────────────┘
```

底层模型决定「单个 Agent 能解多难的问题」；通用 Harness 决定「Agent 会不会用工具」；**领域 Harness 决定「几十个 Agent 能不能围绕一个长期工程目标持续、并行、可恢复、可验证地工作，并且越用越强」**。第一节五个问题——人肉调度、状态蒸发、看不见工程、验证老办法、闭源依赖——的答案全部落在这一层。而这一层，行业里还没有标准答案。

**Anthropic 的费马大定理形式化项目，就是这一层真实起作用的公开实例。** Claude 并非独自完成：早期多 Agent 尝试因丢失全局状态而停滞；引入 Prove2Me（数学领域的 Domain Harness——定理依赖图、任务前沿、持久化进度、并行执行、结果复用、机器验证）之后，不到两周完成约 1300 万行 Lean 证明。**让能力可组织化的不是更强的模型，是领域 Harness。**

软件工程没有 Lean 这样的完美验证器，但同样可以建立「分层的证据体系」：能机械验证的交给机器（构建、测试、回归、性能），智能判断留给独立的 Agent 角色，最终决策留给人。

领域 Harness 与通用 harness 是叠加关系而非替代关系：通用层越强，领域层的产出越高；但通用层再强，也长不出「什么算做完」的答案——那必须是企业自己的资产。

## 四、sandbar：这一层的第一个可运行实现

sandbar 是我们构建的 Engineering Domain Harness 先导实现，目前处于验证阶段。一句话定义：

> **把一个高级工程目标，转化成一张持久化、带依赖、边界清晰、可验证的工作图；然后持续调度 Agent 与确定性工具去执行，直到目标按「完成定义」被客观证据满足。**



### 总体设计：四个决定

整个系统由四个设计原则支撑，每个原则正面回应一个问题：

**决定一：人声明目标，系统掌握全局。** 工程意图与目标之间的依赖结构一旦声明，就成为系统持有的知识，由系统组织推进；

**决定二：会话是易逝的，工程状态是持久的。** 一切工作成果必须落在会话之外——可恢复、可交接、可审计。任何执行者都只是临时的：来了干活，走了无损。

**决定三：完成由证据判定，不由生成者宣布。** 「做对了」是系统依据客观证据得出的结论，不是产出者的自我声明；验证的责任永远在与实现无关的一方。

**决定四：智能是可替换的供给，资产是自己的。** 系统的质量不建立在任何特定模型的聪明之上，而建立在组织与验证之上——模型按需取用、随时可换，积累下来的验证资产属于自己。

### 怎么做到：四层沉淀

四个决定如何落地？靠四层沉淀——**知识沉淀进文档，意图沉淀进 spec，纪律沉淀进工单流程，对错标准沉淀进验证资产**。每一样都成为系统的一部分：不随人走，不随会话蒸发。

#### 第一位：文档管理——知识的沉淀

这套系统对「文档」的态度和惯例相反：文档不是写出来存档的，**是 Agent 上下文的可信度来源**。它具体解决了四个没人解决好的问题：

**A. AI 上下文里「哪句可信」无从分辨。**
惯例是把仓库文档一股脑塞给模型——但文档有定稿、有草稿、有过时的，混塞等于污染。这里的答案是**两区分离**：

- **notes/——过程区**：讨论稿、草稿、立项探讨。允许粗糙、允许有错、快速迭代，是思考的现场；
- **docs/——定稿区**：只有验证过的知识才能进——设计定稿、术语表、操作手册，可信度的最高层。

两区之间是一道**毕业闸**：notes 的内容只有通过验证事件（人工拍板、测试在案、成果落地）才能「毕业」进 docs——不是时间到了就搬，是验证过了才搬。Agent 组装上下文时读定稿层，过程区内容带状态标注。**可信度不是靠提示词祈求模型「请自行甄别」，而是靠目录结构物理保证。**

**B. 文档写完就腐烂。**
同步靠两个机制，不靠自觉：每项工作完成时，系统会追问「沉淀一问」（这项工作验证了什么新事实？要不要入册？）；发现文档与实现不同步时登记**债条目**进账本，由定时巡检跟踪销账。文档保鲜成了流程里的环节，不再是个人美德。

**C. 换个人（或换个 Agent），知识清零。**
全部知识以结构化文档存在仓库：术语表（增删走人工审核）、立项单、设计文档、缺陷账本、债条目，每篇带元信息与机器索引。新会话、新 Agent、新人按知识库接手，不依赖任何人的记忆——这正是「问题二：状态蒸发」在知识维度的答案。

**D. 文档与代码的发布永远不同步。**
答案是 **Document as Code——文档像代码一样管理**：与代码同仓库、走同一条开发流程（同样的审查、测试、签字、合并）、随同一次发布交付、可 diff、可回滚。线上跑哪个版本，使用者拿到的就是哪个版本的文档——没有「系统是 v2.3、wiki 停在 v1.8」的经典漂移。对使用方而言，文档不是去 wiki 上翻的附属品，而是**随产品一起交付的最新版本**，天然可作为交付物与合规材料。

文档管理的本质是**把知识当作工程状态来管理**：分层、有生命周期、有同步机制、有账本、与代码同发布。它是「上下文组装机」的底座——没有这个底座，上下文组装只是把垃圾摆整齐。

#### 第二位：spec 驱动——意图的沉淀

一切工作从 spec（规格说明）开始——写下来，经人审定。spec 在系统里是两级契约：

- **方向级（立项单）**：每个工程方向一份——目标、范围、各项工作的依赖顺序、关键决策、验收口径；
- **任务级（工单票面）**：每张工单开工前写清「做什么、为什么、怎么算好」——它同时是 Agent 的任务契约、验收的依据、审计的凭据。

此后的一切由 spec 驱动：工作从 spec 拆解而来，验收以 spec 为据，讨论的结论回写 spec。**spec 是人与系统之间的契约，也是一切 Agent 工作的源头上下文。**

纪律是 spec 先行：关联立项的工作必须先有立项单，实践中的重要工作也一律先落 spec 再动手。「做什么」先于「怎么做」落笔——模糊的意图在开工之前就被迫显形，而不是在验收时才暴露；方向错了在纸面上纠正，代价远小于在代码里纠正。

#### 第三位：执行——工程纪律的沉淀（工单系统）

工程纪律不依赖个人自觉，而是固化成工单系统的流程。每个开发任务是一张工单：

```
工程目标
   ↓ 拆解
工单 = 有边界的工作单元（目标 + 完成定义 + 改动边界）
   ↓
执行：Agent 在隔离工作区实现，只动边界内的东西
   ↓
验证：独立立场的 Agent 设计并执行测试，机械闸门逐道校验
   ↓
签字：人审证据，批准或打回（打回自动重做，有限次）
   ↓
落库：一单一提交合并主干，全程不可变留痕
```

任何一道闸不过，自动打回上游重做（有限次，超限转人工）；**没有一道闸靠「自觉」**。其中最关键的一条纪律：**完成定义（Definition of Done）是系统的一等公民**——验收条件开工前写定，之后只有系统能依据客观证据判定「DONE」，Agent 永远不能自己宣布「做完了」。道理很朴素：**结论必须出自裁判，不能出自选手**。

而且流程本身不是写死的——工单流程以模板定义（模板即代码），可按项目与组织的形态定制：严格的组织增设人工关口，信任度高的团队让更多闸门自动化；开发流、内容流、杂务流各走各的模板。**纪律的强度是组织的选择，流程引擎保证所选纪律被不折不扣地执行。**

#### 第四位：验证的沉淀——对错标准是长出来的

对错的标准，起点写在 spec 里（开工前定义），生长在验证体系里：每个修过的缺陷登记入账，并转化为一条永久钉死的回归测试——**同一个坑，第二次出现就被机器拦下，不需要任何人还记得它**；验证过的做法沉淀为守卫场景；定时巡检自动体检系统健康与文档一致性。验证体系因此是**带记忆的**：踩过的坑变成闸门，验证过的做法变成默认——用得越久，它对「什么算对」的理解越厚。

#### 底座

业界常见做法是给自己的流程和工具**添加** Agent——AI 作为新功能挂在既有系统旁边，流程还是老流程，Agent 只是加速件。我们的方向相反：**把工程的一切——spec、工单、验证、知识——嵌入 harness 去执行。** harness 不是嵌进我们系统里的插件，而是承载我们全部工程实践的执行底座。方向一反，架构形态完全不同：不是「老流程＋AI 点缀」，而是工程实践整体入驻底座、按底座的纪律运转。

两个外部组件，各管一段：

**Temporal——流程引擎，管「工单这条流程本身」。** 开源的分布式持久化工作流引擎（源自 Uber 内部系统，在生产关键链路上久经考验）。每张工单是一条 Temporal 工作流：走到哪个阶段、谁签了字、测试结果如何，全部作为事件持久化在服务端——进程崩溃、机器重启，流程从上次的位置继续。「关掉浏览器，工单照常推进」「Agent 崩溃，自动续跑」这两句话的机制来源就是它。**工单状态的可信度不靠自研代码保证，靠久经生产考验的引擎保证。**

选它做流程底座，还有四个决定性理由：

- **工作流即代码（workflow as code）**——流程用通用编程语言写，不是 YAML 或拖拽图：天然可单元测试、可版本管理、可组合复用。「模板即代码、流程按组织定制」直接长在这个能力上；
- **部署形态两栖**——既可以嵌入式单机部署（适用于开发者单机开发的情景），也可以作为独立服务集群扩展（企业化部署的形态）：同一套代码适配两种情景，不用换引擎；
- **运行中的流程可动态更新**——流程模板迭代时，在飞的工单不必作废重来，打补丁原地继续；
- **人机交互是引擎一等原语**——「人审签字」（signal）与「随时查状态」（query）不是外挂补丁，是引擎内置能力：人工关口天然融入流程，而不是流程旁边再立一套审批系统。

**dsh（DeepSeek Harness）——Agent 运行时，管「干活的那群 Agent」。** DeepSeek 官方的 Agent 运行时，负责 Agent 会话的起停、工具供给（shell、git、文件）、沙箱与权限、多模型路由、审计与计量。sandbar 说「起一个 Agent 做这张工单」时，实际执行起停、供工具、记账的是 dsh；工单台、签字界面、度量面板这些操作面，也长在 dsh 的插件体系上（与其他四款主流运行时的横评见附录 A）。

我们构建的是其上的领域层：sandbar——spec、工单、验证、知识库，以及把它们串成一个工程组织的领域逻辑。

## 五、关键转变：工程师做什么——定义问题、决定方向、设计验证

先直面一个量级问题：当一个人带着这套系统一天产出万行级代码、产生几十上百次提交，他还能一行一行看代码吗？

物理上已经不可能。逐行评审成立的前提是「产出量级在人眼带宽之内」——这个前提已经被打破。所以这不是「要不要降低审查质量」的取舍题，而是「工作方式必须换代」的必答题。

这套系统改变的是工程师的职责边界，最重要的一点先旗帜鲜明地说清楚：**纯执行类的工作，不应该再是工程师的职责。** 代码的编写、测试的执行、返工的重做——一切「到达路径」上的工作，全部由 Agent 队伍承担。过去一名工程师身兼的五种角色——编码、评审、调度、拼装上下文、跟进进度——其中属于「执行」的部分整体移出，交给系统。工程师保留的，是三个只有人能做的判断：**定义问题、决定设计方向、验证**——Agent 队伍负责到达，工程师负责决定「去哪里、走哪条路、怎样算到达」：

- **定义问题**——把模糊的需求变成清晰的问题陈述：真正要解决什么、为谁解决、什么不在范围内。问题定义错了，后面的一切都在高效地做错事——这是杠杆最大、也最无法外包的一步；
- **决定设计方向**——方案空间里的方向抉择：技术路线、架构取向、关键取舍。Agent 可以生成方案、展开细节、列出各方案的证据，但「往哪走」的判断由工程师拍下——方向感是经验与责任感的产物，不可委托；
- **验证**——定义「怎样算做对」，并把尽可能多的判断变成机器可判定的闸门：验收标准（开工前写清「怎么算好」）、约束边界（允许改哪里、红线在哪里）、对抗性测试体系（独立立场按「挑错」设计）、终审签字（只审证据包与关键差异，不逐行读代码）。

一句话：**问题定义得越准、方向选得越对、验证设计得越好，Agent 队伍就走得越远**——模型的智能可以被调度，而「要解决什么、往哪走、什么算对」这三个判断必须由人做出，并由系统固化下来。

## 六、价值：五层杠杆，每层都有实证

**第一层：消除人肉编排（Human Leverage）。**
人从「调度 4 个 Agent 的项目经理」变成「目标设定者 + 最终批准者」：只在两个时刻出现——立工单（目标+约束+验收标准）、签字拍板。实测：授权后整条流水线夜间无人值守自行推进，人早上来审证据、做决策。

**第二层：让 Agent 工作成果持久（Durable）。**
Agent 会话可以随时消失，工程状态永不丢失。实测：Agent 活动超时崩溃后，流程自动重试续跑；工单跨天、跨进程、跨会话继续，无人重新解释背景。

**第三层：并行规模化（Parallelism）。**
泳道隔离让并行不再互相踩脚：实测 5 个立项单、30+ 张工单按依赖图推进，单夜 5 单并行推进、自动结项。吞吐的约束从「人能盯几个窗口」变成「审批带宽有多少」。

**第四层：用证据替代逐行评审（Evidence over Code Review）。**
在万行/日、百提交/日的量级下，逐行评审早已不是选项。人的评审对象变成「证据包 + 关键 diff」——例如一次数据库变更的签字页长这样：

```
变更：订单表加索引
为什么：查询延迟 480ms，超 SLO
验证：基准 480ms → 30ms ｜ 单元/集成/回归 全过 ｜ 兼容性 PASS ｜ 回滚演练 PASS
裁决：独立 Agent 复核 PASS ｜ 人工签字：批准
```

评审从「读两千行代码」变成「读一页证据」。已修复缺陷一律登记并有回归测试钉死，不允许悄悄复发。

**第五层：AI 工程变得可度量。**
每张工单、每个立项的 token 消耗、模型成本、各阶段时长全部入账——完成一个工程方向花了多少成本、返工损耗占多少、哪个环节最贵，账本清清楚楚。AI 工程从「月底看 API 账单吓一跳」变成「按项目核算的投入产出」：预算可管理、效率可对比、浪费可定位。

**叠加增益：系统越用越强。** 五层杠杆是静态的放大，还有一条随时间复利的增益：每个修过的缺陷登记入账并用回归测试永久钉死（同一个坑不踩第二次），验证过的事实沉淀为定稿知识，引擎自身也由这条流水线开发（自举）。用得越久，系统越聪明。

用公式说：过去，人的生产力 ≈ 编码速度 × 编排容量——后者随窗口数很快见顶；换到这套系统，工程吞吐 ≈ Agent 能力 × Harness 利用率 × 并行度 × 验证质量——四个因子全部由系统放大，不再被人眼与人脑的带宽封顶。

五层叠加，所以目标不是「coding 提速 5 倍」，而是**端到端工程吞吐 2–5 倍**——规划、实现、测试、评审、返工整个生命周期都在系统内。

## 七、从工程师的桌面到企业基础设施

Agent 不该只活在开发环节，更不该活在员工的笔记本电脑里。这是从「个人效率工具」到「企业生产系统」的关键一跃。

### 生产环境的 Agent 应用

除了写代码，企业里更高频、风险更大、也更需要纪律的场景，天然适合「工作图＋闸门」的模式：


| 场景      | 工作图形态                                        | 为什么适合                           |
| ------- | -------------------------------------------- | ------------------------------- |
| 数据库变更   | 前置检查 → 依赖分析 → 变更 → 验证 → 回滚预案                 | 全链可机械验证；错误代价最高的地方，最需要闸门         |
| 性能调查    | 指标基线 → 近期变更 → 假设生成 → 并行调查 → 基准对比 → 候选修复 → 回归 | 典型值班场景：把「资深工程师半夜查问题」变成系统自动推进的任务 |
| 数据/版本迁移 | 预检 → 依赖 → 迁移 → 验证 → 回滚 → 后检                  | 确定性链条，正是持久化流程引擎的原生形态            |
| 巡检与值班   | 定时扫描 → 异常检测 → 自动立案 → 人审处置                    | 无人值守定时质检，异常自动立成工单进流水线           |




### 让 Agent 脱离员工的电脑

今天普遍的用法：Agent 会话跑在员工笔记本上，人盯窗口，电脑一关一切暂停——Agent 只是个人工具的延伸。企业级的要求恰恰相反，sandbar 在机制上已经做到：

- **状态在服务端**——任务的全部真相存在 Temporal 流程引擎（服务端持久化执行）以及代码仓库里，不在任何人的聊天窗口里；
- **执行在独立进程**——每张工单有专属 进程与隔离工作区，由引擎调度执行；人的浏览器只是一个观察与签字的窗口，**关掉它，工单照常推进**；

诚实边界：当前部署形态仍是单机（引擎、流程引擎、操作面板跑在一台机器上），容器化与多租户云端部署在路线图上。但架构上没有拦路石：状态外置于流程引擎、执行外置于 worker进程、界面外置于 web 面板——三者天然可分离、可扩展。

## 八、战略价值：为什么这是公司资产，而不是一个工具

**1. 把模型供给的主动权拿回自己手里（问题五的答案）。**
Harness 的对冲逐点回应问题五的四层代价：**验证体系让「错误可捕获」替代「从不犯错」**——错误被闸门拦得住的模型，就不必是最贵的闭源模型；**开源模型＋强 Harness 成为工程可选项**——智能差距由拆解、上下文、迭代补齐，换来的是全链路私有部署、数据不出域、模型版本自己钉死（升级先过回归钉死再上线，不受供应商侧任何隐性调整的影响）；**按岗位路由模型**——贵模型只用在最终裁决与复杂推理，常规实现和测试跑在成本优的模型上；**能力沉淀在自己账本里**——工作图、验证规则、缺陷免疫跨模型保值。sandbar 不绑定任何模型供应商：模型按岗位路由、随时可换，供给完全自主。初步实证「普通模型＋Sandbar 逼近强模型＋通用code agent」，若经严格 A/B 证实（见第九节），意味着可以用成本更优、供给可控、可自部署的模型组合达到同等工程产出——成本与供应链两个层面的战略选项。

**2. 模型会换，Harness 和验证资产不会。**
明年会有新模型，后年又有更新的。但工作图结构、完成定义、验证规则、缺陷账本、可信度分层的知识库、已验证的工程模式——这些「工程智能层」是企业自有资产，跨模型保值，且**随使用增值**：每个踩过的坑都变成系统免疫力的永久增量。

**3. 领域模式复利。**
每个被验证过的工程模式（迁移、回滚、性能验证、事故修复…）都成为后续 Agent 可复用的构件。新任务不再从零开始，而是「检索已验证模式 → 适配 → 再验证」。

**4. 审计与合规天然就绪。**
每张工单从目标到合并全程不可变留痕。对内是工程治理，对外是合规材料——这在 AI 深度参与生产的监管环境下会越来越重要。

## 九、诚实的分界：已验证的与待验证的

**已实证（日常运转数据，自有项目）**：70+ 张工单走完全流程（真实缺陷修复、UI 重构、引擎加固、测试体系建设）；3 个在管项目；引擎自身也由这条流水线开发（自举）；夜间无人值守；单夜 5 单并行；Agent 崩溃恢复；缺陷回归钉死机制日常运转。

**待验证（建议列入下一步研究议程）**：

1. 编排时间下降幅度（对照基线：人肉编排的上下文切换成本）
2. 并行扩展曲线（2/4/8/16 个并行工单的真实 scaling）
3. 模型替代效应（中等模型 + 强 Harness vs 强模型 + 弱 Harness 的严格 A/B）
4. 评审负载（证据驱动评审 vs 逐行评审的时间与缺陷逃逸率）
5. 自迭代增益（缺陷复发率随系统使用时间的下降曲线——「系统免疫力」的量化）
6. 跨领域泛化（从当前工程域扩展到数据库变更、性能调查、迁移等域）

**已知最大风险：工作图本身拆错。** 系统再严密，若目标被错误拆解，后面所有 Agent 会非常高效地做错的事——这是「垃圾进垃圾出」的 Agent 版本。sandbar 的对策已内建：方案段之后设独立复核闸（完整性、依赖正确性、遗漏任务、危险假设逐项检查，不过即打回），且工单由人立项、合并由人签字——拆解错误在前后两个人工关口都可被拦截。

## 十、下一步：按「一个域 + 一条工作流 + 一个团队」扩展

不建大平台，选高结构化、强验证可能的领域做对照试点（数据库变更管理是理想候选：天然有前置检查、依赖、验证、回滚的确定性链条），以「当前工作流 vs Harness 工作流」A/B 对照，用工程前置时间、人工编排时间、评审时间、缺陷逃逸率、单验证成果成本回答最终问题：

> **Domain Harness 是否能在不降低质量的前提下，显著提升工程吞吐。**

四点结论：

1. **dsh 是六项全过的唯一者**——这也是 sandbar 能把工单台、签字界面、度量面板全部长在底座上的原因。
2. **连内核都是插件**——dsh 由 cordis 微内核插件系统组装：从 LLM provider、bash 工具、文件系统到会话持久化，全部是可独立替换的插件包，同一能力可有多种实现并存（本地 bash 与沙箱 bash、本地文件系统与受控文件系统）。这不是「提供扩展点」，而是「内核本身即插件集合」：Claude Code 与 Codex 是闭源单二进制，扩展只能走它们预留的钩子；opencode 与 pi 开源可改，但动内核意味着 fork 与长期维护分叉。**内核插件化意味着任何一层不满意都能单独替换、平滑演进，不必推倒重来**——对把底座当长期资产的企业，这是结构性的保值。
3. **模型绑定是隐藏的分水岭**——Claude Code 与 Codex 的工程能力很强，但与各自模型生态绑定，直接撞上第五个问题（闭源依赖）；opencode 与 pi 在模型自主上合格，但操作面、治理、编排入场券缺位，做个人工具优秀，做企业底座不够。
4. **生态关系的不对称**——dsh 的 provider 适配器里就包含 pi 生态的模型（pi-ai）：底座可以把轻量工具的供给面吸收为自己的组件，反过来不成立。

同样要诚实表态：**dsh 目前处于早期状态**——上表列的是架构形态的判断，不是成熟度承诺。它的能力面（插件体系、治理、编排）已经齐全到支撑 sandbar 的全部实践，但版本迭代快、生态尚小、文档仍在完善，企业级采用需要评估这条时间线。之所以仍选它：六项入场券的**架构形态**是稀缺且难以后补的（微内核、插件宿主、模型自主都是结构性设计，不是功能堆叠能补出来的），而成熟度会随时间增长——形态对了，成熟只是时间问题；形态错了，成熟也是错的方向。

另一个值得记录的动向：pi 团队也在逐层长成完整 harness 栈（CLI → 统一多模型 API pi-ai → 应用组装运行时 chord）——独立团队收敛到同样方向，反向佐证「缺失的一层」真实存在。差别在于：dsh 今天是成品（11 个插件在跑），chord 今天是积木。

**通用 harness 的正确形态不是更聪明的 CLI，而是可编程、可扩展、模型自主的工程底座。领域层的每一项能力都建立在这六项上——通用层的质量，决定领域层的上限。**
