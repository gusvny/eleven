# code review 阶段（ghost）— 261017 讨论稿

> 状态：**待立项**（本稿只定形状，不改流程；落地走票）。
> 起因：261017 一夜里四个真实失手都是"有人看一眼 diff 就能发现"的类型——
> 落地写了受保护基线、删掉了仍被 import 的模块、把断言削弱来换绿、用例里一个作用域 bug。
> 现有 dev-lane 里 **没有一层在评"代码对不对"**：`review_plan` 只看方案、
> `arbitrate` 只裁"红是产品的错还是测试的错"、`acceptance_walkthrough` 只走产品面、
> `merge` 只是人签字。代码层是空的。

## 一、位置与性质

- 新段 `code_review`，**与 `arbitrate` / `acceptance_walkthrough` 同级**（integration 角色）；
- 具体时点：`run_integration_tests` **绿之后** fork 出去，与 `acceptance_walkthrough` **并行**；
  闸红则不起（没有可评的稳定 diff）。
- **ghost step**：跑、产报告、**不影响任何结果**——不拦流程、不打回、不分叉判定。
- 它**不是**闸的补充（那三条卫生检查——受保护面/悬空引用/削弱断言——属于闸的候选，另议），
  它评的是**实现是否兑现 spec 的意图**。

## 二、输入（顺序是硬要求）

1. ticket spec（含 epic 相关信息，如有）；
2. 代码 diff；
3. integration 的测试报告。

**必须"先 spec+diff，再测试报告"**：反过来会变成"测试绿了所以没问题"的盖章。
不给它看 plan / arbitrate 的自辩材料（避免被既有结论带跑）。

## 三、评审要回答的五问

1. 实现是否符合 spec 的**意图**（不是只看字面）；
2. 有没有**遗漏**（spec 里说了、代码里没有）；
3. 实现方式是否**合理**；
4. **抽象是否合适**——不是"摊大饼式"地把所有东西堆在一处；
5. 是否**易维护**。

## 四、输出（review report）

- 语言：**英语**；风格：**言简意赅、说人话**（不堆术语、不写长篇）。
- 结构：`review report`（一段总述）＋ `items`（意见列表）。
- 每条意见必须带：`file` + `line` + 引用的 **spec 条款**（原句或验收项）＋一句话 finding ＋为什么。
- 三个级别：
  - `1 block`：必须整改；
  - `2 preferred`：最好改；
  - `3 minor`：小问题。
- 硬性约束：
  - **条数上限 10**；
  - **`items: []`（无意见）是合法且不惩罚**的结果（不设"必须找出问题"的压力，避免硬凑）；
  - 不评代码风格/命名/格式（那是 lint 的活）、不提"换个库更好"除非影响可维护性；
  - **不改代码、不打回**（ghost 的边界）。

## 五、意见的去处

- `block` 项写进**票面 `pending`**（遗留项），**人审 merge 时就在眼前**；
- 不阻断、不冻结、不进 KI 册；
- 人可以选择整改、另开票、或带着它合并（不要求理由留痕——保持简单）。

## 六、明确不做（本轮讨论已裁掉）

- ✗ "两次同区 block 自动升级成 KI"：判"同区"虽然可机械定义（同文件／同一条已声明的表面／同一条 spec 条款），
  但整体复杂度不合算（宿主 261017 明确：先不做）。
- ✗ 让 reviewer 决定打回（ghost 不参与判定）。
- ✗ 自动修改代码。

## 七、开放问题（落地前要定）

1. 是否在 `acceptance_walkthrough` 的报告里引用一句"review 有 N 条 block 未处理"（让签字的人一定看到）？
2. diff 过大的时间盒／截断策略（先评风险面：`server/engine/**`、测试面、受保护面）。
3. 模型档位：**不降档**（"抽象是否合理"这类判断小模型给不出）。
4. 是否所有 dev-lane 票都跑（成本约 10–20 分钟／票）；还是按 write_set 触发（碰 `server/engine/**` 或测试面才跑）。

## 八、影响面与验收（草案）

- 影响：`server/workflows/dev-lane.yaml`（受控文件，**走票**）新增 ghost 段；输出 schema；`pending` 接线。
  不改引擎的判定逻辑、不改闸、不改线轮。
- 验收草案：
  - 一张真票上跑一次，报告落在票面/结果文件；
  - `items: []` 合法；
  - `block` 项出现在 `pending`；
  - merge 人审能看到这份报告；
  - 全程不影响票的 stage 推进（ghost 自证）。
