# 会话哨兵——会话需要人介入或会话出事时提醒

> **来源**：宿主 260927 会话原话——「dsh 有没有一个能力，比如 session 或者工单需要人介入了，
> 就发出一个声音来提醒一下啊。没有的话我们在 sandbar 里怎么做一下呢？」
> 随后两轮口径修正（宿主原话）：
> ①**提醒对象是会话，不是看板待办**——「我在 session 里开着 ticket 的时候，session 做了代签和
> block 修复，这种情况下，只有 session 认为我需要介入的时候，或者这个 ticket session 出问题的
> 时候，我才需要提醒」；
> ②声音「**一声就够，别烦我**」；
> ③停摆判据（多久没动静算出事）「**可配置**」。
>
> **本文只写「是什么、为什么」**：接口形状、字段与命令等实现细节在各实现票里定；
> 落地状态与进度查立项单/工单，本文不记。

## Problem（问题）

1. **一句话**：会话（agent）替我跑票时是**自主推进**的——它自己代签、自己修卡住的票，大多数时候
   不需要我；但它一旦**停下来等我**、或者**自己出了毛病**，我只能靠「恰好回头看屏幕」才发现，
   等待时间就是纯浪费。

2. **背景知识**（没参与过的人要先知道这些）：
   - **什么是「会话」**：控制台里一个 agent 的工作会话（一次对话）。我可以在这个会话里让它去
     驱动工单：查票、签字放行、处理卡住的票。会话是**一边干一边等我**的——它干得动的部分不会
     问我；只有遇到「要不要批准这个动作」「这个问题得你定」这类事，它才把控制权交回给我。
   - **什么是「出问题」**：两种都算。一是会话**自己报错或异常结束**（它还在，但干不下去了）；
     二是**假活**——会话看着还在跑，实际上已经卡死、长时间没有任何动静。
   - **为什么不能靠看板**：我在会话里跑票时，票上那些「等待签字」的中间状态会被会话**当场消化**
     （代签、把卡住的票重新推起来）。看板上出现的「等待人处理」，此刻往往**不是**我的活——按看板
     提醒会一直误报。真正该提醒的是**会话这个动作主体**的状态。
   - **现状**：控制台页面**没有任何声音或桌面通知**；一切提醒都是「视觉的、被动的」——必须人正在
     看那一屏才成立。

3. **证据**（260927 实测，非推测）：
   - **dsh 本体没有这个能力**：在本机在跑的那套 dsh（0.1.5-rc.2，全部官方包）里检索
     「声音／静音／音量／提示音／未读／注意」**零命中**；检索「浏览器通知／音频播放／改页面标题／
     图标闪烁」同样**零命中**。它的界面不会出声、也不会弹系统通知。
   - **现成的 hook 机制也不够用**：dsh 有一套事件钩子协议（可复用 Claude Code / Codex 的钩子配置），
     但它支持的事件只有「会话开始、收到提示、工具调用前、工具调用后、要停下来、子代理起停」——
     **没有**「需要你确认／等你输入」这类事件；而且当前这套 profile 根本没挂钩子包。
   - **但 dsh 知道「有人在等」**：它的客户端对外暴露一张**按会话索引的「待办交互」表**，
     一次覆盖三类事——动作授权请求、agent 提问、计划确认；另有会话状态（加载中／就绪／出错）
     与「会话一直在落盘活动」的现成数据面。
   - **本仓已有可挂的地方**：控制台是本仓自己的插件（`server/plugins/workbench`），本来就是 dsh 的
     客户端插件、已经在往 dsh 的界面槽里挂东西，也已经每 5 秒拉一次看板（出错时退到 30 秒）；
     同类读会话落盘的面（工单实时动态面板）也已存在。**不需要改 dsh，也不需要向上游提需求。**
   - **宿主实据**：宿主当晚提出需求并明确「我基本一直开着控制台页面，响在页面里就够」——
     即**不要求**在浏览器关掉时也能响。

## Requirement（需求）

每条都能当验收标准：

1. **触发面只有两类**：
   - ①**会话正在等我介入**——动作授权请求、agent 提问、计划确认，**三类都算**，一视同仁地提醒；
   - ②**会话出问题**——会话自身报错或异常结束；或**会话在跑却没有动静**超过设定时长。
   工单看板上的状态（等待签字之类）**不作为**触发面。
2. **提醒形态**：一声短提示音 ＋ 一条桌面通知。通知要能分辨「**哪个会话、要我做什么**」，
   并且**点一下能回到那个会话**。
3. **不重复**：同一件事在没被处理期间**只响一次**；新出现的事再响。不许出现「每隔几秒响一次」。
4. **可配置**：至少三项可配——**没动静多久算出事**、**声音开关**、**桌面通知开关**；
   三项都要有合理默认值，默认值开箱可用。
5. **误报控制**：长时间的工具调用（跑集成测试、构建这类几十分钟不产出新事件的动作）**不得**
   被判成「出事」。判据要基于「会话整体是否还在推进」，而不是「最近几秒有没有事件」。
6. **盲区如实声明**：本提醒依赖**网页服务本身存活**。服务整体不可用时，本提醒**必然不响**——
   这一条必须写进文档，不许用机制假装覆盖。
7. **验收动作**（人可复现）：
   - 让会话提一个问题 / 请求一次授权 → 不盯屏幕，**10 秒内**听到声音并看到通知；
   - 制造一次假活（会话卡住）→ 超过设定时长后**同样**响；
   - 同一件事不处理 → **不再响**；处理后出现新事 → 再响；
   - 关掉声音开关 → **完全静音**，其余功能不受影响。

## Nongoal（不做什么）

1. **不做宿主侧独立发声**（浏览器关着、或网页服务挂了时仍能响）。它是本方案盲区的正解，但代价是
   要在宿主机上另起一个常驻看守——**本期不做**，等主方案用过、确认「值不值得」再单开一票。
2. **不做手机／IM 推送**。更重、更远；本期不做。
3. **不动 dsh 本体**：不向上游提需求、不给 dsh 打补丁。只用它**对外公开**的能力。
4. **不做「循环响到处理」「不同事情不同音」**。宿主已明确「一声就够」；多音方案留到有人真的
   嫌一声不够用再说。
5. **不做看板待办提醒**（等待签字的票、卡住的票）。理由见 Problem 2：在会话跑票的语境里，
   这不是我该被叫醒的事。**注意**：这不否定「无人值守时的看板告警」这个需求本身——那是另一个
   场景（宿主不在会话里跑票时），要另立需求另写文档，不在本期。
6. **不改票的逻辑**（不新增票状态、不改签字流程）。本方案是**只读的旁路观察者**，对引擎零写入。

## Proposal（方案）

### High level

在这块控制台页面里常驻一个**会话哨兵**。它不新开场子，而是**挂在页面已有的节拍上**（页面本来
就在按固定间隔刷新会话与看板），每拍做三件事：

1. **看有没有会话在等我**——读那张「待办交互」表（它是全体的、按会话索引的，三类待办都在里面）。
2. **看会话有没有出事**——会话自己报错／异常结束，或者**在跑却长时间没有推进**（用界面已有的
   「会话一直在落盘活动」这一数据面判断「还活着」）。
3. **比一比上一拍和这一拍的差别**：把「需要人的事」当成一个集合，**只有当集合里出现了上一拍没有的
   新成员**，才提醒——响一声 ＋ 发一条桌面通知（写明哪个会话、什么事，点了跳过去）。
   **已经有了的事不重复提醒**，直到它被处理掉。

一句话：**只在「从不需要人」到「需要人」的边界上响一次。**它是个只读的旁观者，从不碰票、不碰会话。

### 关键取舍（为什么这么做）

- **只认「状态变化」，不认「状态存在」**。如果按「现在有人在等 → 响」，页面每 5 秒刷新一次就会
  变成每 5 秒响一声。这类功能最常见的做坏方式就是这个，本节把它当硬约束写死。
- **挂在「会话要人」这个统一状态上，而不是逐个事件去接**。三类待办（授权、提问、计划确认）本来就
  聚在同一张表里；顺着这张表做，未来 dsh 增加第四类待办时**自动被覆盖**，我们不用改。
- **只用 dsh 对外公开的能力，不锚内部细节**（理解要深、绑定要浅）。哨兵依赖的是 dsh 公开的
  「待办交互」与「会话状态」两类信号，不依赖它的内部结构或偶然的执行顺序——dsh 小版本升级
  不应该把我们打红；真打红了，说明我们接错了地方。
- **误报优先于漏报的取舍方向要说清**：默认阈值取「宁可稍晚叫，也别在跑长测试时乱叫」——因为
  乱叫一次，人就会关掉它，之后所有提醒都失效。阈值可配置正是为这个服务。
- **盲区如实写、不假装覆盖**：见 Requirement 6 与 Nongoal 1。
- **声音用页面自己合成**，不引入音频文件：不给仓库添资产、不依赖外部文件是否被正确打包。

### 回扣前三段

- 解决 Problem 1：会话等我时**不必靠回头看屏幕**；会话假活或出错时**不再静默烂掉**（Problem 2 的
  证据面正是本方案要接的三类输入）。
- 满足 Requirement 1–7：触发面收敛成两类（1）、一声＋通知＋点击定位（2）、去重（3）、三项可配（4）、
  长任务不误报（5）、盲区声明（6）、验收动作可复现（7）。
- 避开 Nongoal：不做宿主侧发声与手机推送（1、2）、不改 dsh（3）、不做多音与循环（4）、
  不碰看板待办与票逻辑（5、6）——本方案对引擎**只读**。

## 附：实证记录（260927，供实现票与验收票查证）

- **检索结论**：dsh 0.1.5-rc.2 全部官方包里，声音／通知／标题闪烁／图标类关键字**零命中**；
  钩子协议支持的事件集里**没有**「等人输入」类事件；当前 profile 只挂 dsh 基础包、网页界面包
  与本仓自己的插件，**未挂**任何钩子桥包。
- **可用的对外信号**：dsh 客户端对外提供①「待办交互」总表（按会话索引，含授权请求／提问／计划确认
  三类，每项带它会话的身份）；②会话状态与「会话活动落盘」两路健康数据面。
- **本仓可挂点**：控制台插件 `server/plugins/workbench`（客户端半已用 dsh 界面槽；宿主半已有
  `/sandbar-workbench/api/*` 路由族）；已有读会话落盘的先例 `src/host/agent-live.ts`；
  页面轮询现状见 `src/client/index.tsx`（健康 5 秒 / 降级 30 秒）与 `src/client/visibility-poll.ts`。
- **宿主口径**：一直开着控制台页面，页面内提醒足够；要一声；阈值可配置。
- **顺带记录（不在本期范围）**：宿主同一轮问到「工单需要人介入也提醒一下」——本期按 260927 口径
  收敛为**只提醒会话**；看板类提醒（无人值守场景）若要做，另立需求。
