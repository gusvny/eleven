# 文档泳道（doclane）—— 设计稿（草稿，未拆票）

> 来源：宿主 261004 会话原话——「我们后面可能需要一个 doclane 来落文档，这样可以避免在 main
> 上直写，你觉得呢？」本文是 integration 岗位的回答（赞成 + 边界 + 取舍），供宿主裁定。
> 本文只写「是什么、为什么」，不写落地状态；阶段取名、写集默认值等留给拆票。

## Problem

**一句话**：定稿文档今天的落笔只有两条路——跟开发票挤同一条十段流水线（太重），或者在 main
侧直写（无闸、且每次都要宿主口头授权锚）。

**背景知识**（给没参与过的人）：

- **泳道**是干活的工作流：票带写集白名单，跑机器段与人门，最后过合并闸入 main。写集是「这张票
  允许动哪些路径」的硬边界，越界会被拦并具名点名。
- **两个库的写权限不同**：定稿文档库是**允许写入面**（放进写集即可写），知识库与账本面是
  **禁写面**（票据与账本只由 main 侧直管）。所以「文档能不能由泳道写」这件事，能力上早已成立。
- **已有先例**：一张文档票（评审清单页）就是走普通泳道落进定稿库参考目录的，写集钉在该目录下的
  几个路径。也就是说，缺的不是能力，而是**形状**与**归属规则**。

**实据**：

1. 本会话 integration 侧在 main 直写的实际量级：术语扫尾、一条守卫的报错可见性、两行文档失真、
   抢救一个漏提交的单测——**全是两行/一句话级**的修正，但每一次都必须拿到宿主的显式授权锚才能
   动 main。main 侧直写没有写集、没有第二双眼睛、没有机器门。
2. 反过来，把这些塞进十段流水线同样不合理：十段里有实现、跑集成、证据截图这些**文档根本不存在
   的面**，成本与产出严重不匹配。
3. 而文档修正是**高频小额**：一次搬迁票能牵出好几处一句话级的连带修正（见 epics 迁移设计稿
   附录 A）。两条现有路径对这个量级都不合适——这正是要立这条泳道的理由。

## Requirement

（每条都能当验收判据用）

1. **不再依赖 main 直写**：文档落笔有正常的入轨路径——有票、有写集、有复核、过合并闸。
2. **形状与量级相称**：一句话/两行级的修正不必跑完整开发流水线。
3. **人门不省**：**宿主拥有的定稿面**（立项单、术语表、写作标准、评审清单）必须有人签；
   普通参考页与说明页可由 integration 角色复核后合并。
4. **规矩只有一处**：语言、头部字段、索引收录、设计文档自查这些都仍由定稿库自己声明；泳道只声明
   「它适用于哪些面」，**不复制**第二套。
5. **账本不进这条道**：已知问题台账、讨论草稿、请求账这类持续生长、多写者必然打架的账本继续
   单写者（main 侧）。新泳道不得成为绕过这条纪律的口子。
6. **冲突面小**：文档票短命、及时合并；不与 main 长期抢同一批文档。

## Nongoal

1. **不改现有开发泳道**：新泳道是新增，不是改造；现有阶段与语义零回归。
2. **不动账本禁写令**。
3. **不引入第二套文档格式或语言规矩**。
4. **不做文档的自动生成/批量迁移**（那是别的票）。
5. **不承诺「一切文档改动必须走泳道」**：宿主点名的单点急救仍然允许直写。
6. **不做文档的版本/发布流**：定稿库只有 main 一条线。

## Proposal

### 高层（一页能懂）

给文档落笔一条**短的**道：**计划确认 → 写 → 审 → 合**，其中「审」按文档归属决定是机器闸后由
integration 角色判、还是在最后挂一道**人门**。写集默认只钉定稿文档面；账本面不开口；语言/格式
规矩一律复用定稿库自己的声明。**优先复用现有短泳道**，只有确实需要不同阶段时才新增模板（见取舍一）。

### 关键取舍（每条都说清为什么）

1. **先复用，再考虑新模板。**
   今天已有的**短泳道**（阶段数明显少于开发泳道）加上「文档写集 + 归属人门」的约定，可能就已经
   够用；新增一条工作流模板意味着多一套阶段定义、多一组场景、多一份要维护的东西。**建议第一步
   只做约定与默认值**（文档票走短泳道、写集钉定稿面、按归属挂人门），跑几票之后若确实缺阶段，
   再新增模板——避免为了「有个名字」先造一整套。
2. **段要短，是因为文档没有那些面。**
   实现、跑集成、证据截图对文档不成立；把它当开发票办，只会让文档修正被拖成跨天的事，反而逼人
   回到 main 直写。
3. **人门按归属分流，而不是按大小分流。**
   人门是稀缺资源，应花在「宿主的东西」上：立项单、术语表、写作标准、评审清单这些是宿主的定稿面，
   必须人签；参考页与说明页由 integration 角色复核即可。按「改动多少行」决定要不要人签是错的
   方向——一行也可能改掉立项范围。
4. **写集钉定稿面，不做账本例外。**
   账本的单写者纪律不是洁癖，是被多写者打架与草稿直落坑过一次之后立的规矩。文档泳道不得开口子；
   要改账本，仍走 main 侧。
5. **不新写语言门，而是扩现有门的适用面。**
   定稿库目前不在抄写语言门的覆盖范围里。与其新写一个「文档语言门」，不如把定稿面纳入现有的同一道
   门（例外面=术语表本体与写作标准里引用的中文清单），这样规矩一处、判据一处。
6. **急件通道保留但要点名。**
   宿主点名的单点急救仍可直写 main——但要留下「这是急救、不是常规路」的痕迹，否则新泳道会被
   慢慢绕空。

### 细节（只写「不写下来就会有人搞错」的部分）

- **写集默认值**：文档票默认写集只含定稿文档面；要动别处必须在票面上写明原因（写集是声明面，
  不是默认全开）。
- **人门挂在哪些面**：宿主拥有的定稿面在合并前挂人门；其余页在 integration 角色复核后即可合。
- **语言门的例外面**：例外必须**具名**（写清哪几份文档为什么例外），不做「整个目录豁免」。
- **短命分支的可见口径**：验收里加一条可查的「及时合并」口径，避免长命分支与 main 反复冲突。
- **与 epics 迁移的先后**：先做迁移（走现有泳道就够），文档泳道随后；两件事不耦在一张票里。

### 回扣

本提案 → 解决 Problem 的「两条路都不合形状、main 直写无闸」→ 满足 Requirement 1–6（入轨、
量级相称、人门按归属、规矩一处、账本不动、冲突面小）→ 不去碰 Nongoal 划下的六条边界。

## 待宿主拍板

1. **要不要现在做**：建议排在 epics 迁移之后（迁移走现有泳道即可，不必等新泳道）。
2. **人门分流粒度**：宿主拥有的定稿面各自点名，还是按目录整片挂人门（我建议点名——整片挂会让人门
   退化成例行盖章）。
3. **是否复用现有短泳道起步**：我的建议是复用起步，跑几票看缺不缺阶段，再决定是否新增模板。
