# 请求账升级：议题线程 + 归属 + 归档（设计稿，草稿）

> 来源：宿主 261004 会话连续追问与拍板。拍过的四条：
> ① 请求可以是一个 **thread**（有回复），整个 thread 有一个**状态**（dismissed / resolved 之类）；
> ② 一条请求可以**关联**之前的请求；
> ③ 每条请求上要有**来源票**（ticket）与**问题归属**（epic）两个字段；
> ④ 来源可以是**项目会话**（不是"全局会话"——那个词作废）。
> 本文只写是什么、为什么，以及我看到的坑；落地细节留给拆票。

## Problem

**一句话**：今天的请求账是「一条问句 + 一条应答」，它既装不下族、也装不下状态、也装不下归属，
而且它住在仓外——所以它只能承担"今天怎么办"，承担不了"以后别再踩"。

**背景知识**（给没参与过的人）：

- **请求账**：执行器向你提事、你在面板上答事的账。追加式，一项目一本，写在机器级目录里。
- **KI 册**：已知故障模式的册子（模式 / 触发 / 会踩它的改动 / 回归用例），在仓内，随 git 走，
  巡检**直接读它**当输入。
- **工单与 epic**：一张票是具体一次交付；epic 是一条立项（一堆票的归属）。

**实据**：

1. **族不存在**。今天 43 条请求里，`finding` 23 条、`decision` 17 条。其中大量是**同族的实例**，
   而账本里只能靠正文手写「【追加·原条 req-…】」来表达关联 ⇒ 人看不出族，票就只能**一实例一张**地开
   （这正是"永远做不完"的一个来源）。
2. **没有状态**。答了就是答了。`dismissed` / `resolved` / 过期 / 被取代都不存在。
   面板要的"告警已消解"也没有地方放（**同一种形状**）。
3. **没有归属**。一条发现该归哪个 epic 管、从哪张票冒出来，全靠正文里手写字号 ⇒ 路由靠人记，
   仪盘（每票 / 每 epic 有多少发现）只能人肉数。
4. **仓外、无备份**。现路径 `~/.sandbar/projects/<key>/requests.jsonl`（本机 145 KB、86 行）。
   不进 git、不备份、换机即失 ⇒ 它不适合当"事故不重演"的记忆。
5. **只增不减**。事件账与动作账都有保留期（keep_days / 滚动归档），**请求账没有**。

## Requirement

1. **一条议题 = 一个线程**：头（问句 + 选项）+ 任意条回复；**只追加，永不改写**（今天"拒绝二次应答"这条性质必须保留）。
2. **状态齐**：`open → answered → resolved | dismissed | superseded`。**谁能设哪一态写死**（见下）。
3. **关联齐**：`supersedes` / `duplicates` / `follows_up` / `blocks`。族视图靠它机械可得。
4. **归属两字段**：**来源票**（事实，可空）+ **问题归属 epic**（判断；必填，或 `none` **加一句理由**）。
5. **来源分三类且可验**：执行器会话 / 项目会话 / 泳道 agent；**项目字段由会话登记派生，不信自报**。
6. **压缩**：终态且**没有未终态的关联**者可以压。压之前，属于"会复发的模式"的**必须先归档**。
7. **归档进定稿库（docs）**：每条写全 模式 / 触发条件 / 会踩它的改动类型 / 回归用例指针 / 状态。
8. **仪盘**：每票发现数、每 epic 发现数、答→解时长。用来回答"是不是永远做不完"。

## Nongoal

1. **不做聊天**：右栏 chat 是平台的面，本账不复制对话流。
2. **不把账本变成进度表**：宪章禁止在文档里手工维护进度与工单清单。
3. **不做自动应答、不做自动关闭**：到期只是**显示与提醒**（今天这条口径不变）。
4. **不整份搬 KI 进定稿库**：先分类（会复发的才进），否则是换房间放垃圾。
5. **本期不做"全局会话"**：宿主已明确，说的是**项目会话**。

## Proposal

### 高层（一页能懂）

同一本账、同一种追加式，但长成**两个层次**：

- **工作集（仓外，随手用）**：议题线程。头 + 回复 + 状态行 + 关联行。答完、做完、压掉。
- **归档层（仓内 `docs/`，严肃件）**：**只有"会复发的模式"**才进。英文、有头部字段、被索引、人审准入。

一条议题的一生：

```
open ──(你答)──> answered ──(做事的人带证据)──> resolved
  │                  │
  │                  └──(你判定不必做)──> dismissed
  └──(被新议题取代, 新的打 link)──> superseded
```

压掉一条的判据（宿主提的那条，加上了定义）：
**状态是终态，且没有未终态的议题链到它。**

### 关键取舍

1. **两字段是两个意思，不能合成一个**。
   `ticket` = **来源**（这条从哪张票的工作里冒出来，是**事实**）；
   `epic` = **问题归属**（这个**问题**该归哪个 epic 管，是**判断**）。
   今天就有例子：`-28` 的搬运撞上抄写语言门——来源票是 `-28`，问题归属是**文案/本地化**那条 epic。
   混成一个字段，两种问法都答不准。
2. **`epic` 必填或 `none` + 理由**，且只做一条硬校验：**代号在册**（仓内可离线查）。
   **不**做"与来源票的 epic 一致"的校验——那会把合法历史判成错，也会造出假红。
3. **`project` 派生、不自报**。项目会话与执行器会话都在我们的登记面里（`sessions.json` /
   `executor_sessions`）⇒ 项目由**登记**推出。同 `by` 那条教训：写者身份不许调用方自填。
4. **状态由谁设，写死**：
   - `answered` / `dismissed`：**你**（面板上点）；
   - `resolved`：**做成事的那一方**带证据落（票号 / 提交号），不许顺手点；
   - `superseded`：新的议题打 `link` 时，老的自动判。
5. **压缩不等于删除**。压之前写一条**摘要行**（议题号 + 问句一句话 + 终态 + 谁何时 + 归档指针），
   原始行滚动到月度归档文件。理由：审计要的就是"当时为什么这么定"。
6. **归档进定稿库的动作归 main 侧**（你或我），执行器与泳道只提"建议入册"。
   定稿库要人审——这条不能破。

### 细节（不写下来会搞错的）

- **行类型**：`request`（头）/ `reply` / `state` / `link`。状态变化与关联都**各占一行**，只追加。
- **来源三类判据**（离线可查）：执行器会话 = 被 `executor_sessions` 点名；
  项目会话 = 在那项目的 `sessions.json` 里有登记；泳道 agent = 引擎注入的通道。**其余一律拒收**。
- **回复的写者**：你、执行器、我（integration）；**项目会话只能提问与补事实，不能应答**。
- **代投（今天很常见）**：我替你答的行要能分辨——建议行上分三处写：`by`（谁定的）、
  `via`（谁代投）、`anchor`（你的原话/锚）。今天这些信息全塞在一句 `by` 的括号里。
- **过期**：`expires_at` 只驱动**显示与分级提醒**，**不改状态**（与今天口径一致）。
- **重复投递**：同一（来源票 + 问题归属 + 主题）已有未终态议题时，**应当关联而不是新开**；
  这条要有机械检查（否则族还是散）。
- **并发与单写者**：沿用现成的 flock + 追加写，一本账一个写者。
- **保留**：给这本账补上保留策略（与事件账同族的 keep_days / 滚动归档），压缩规则叠在它之上。

### 回扣

本提案 → 解决 Problem 的五条（族不存在、没有状态、没有归属、仓外无备份、只增不减）；
→ 满足 Requirement 1–8；→ 不碰 Nongoal 的五条（不做聊天、不做进度表、不自动关闭、不整份搬 KI、不做全局会话）。

## 我还看到的问题（逐条，带我的建议）

1. **"答了"不等于"做完了"**。你答了、事还没做，是常态。所以状态必须两段。
   建议：`answered` 之后只有**带证据**才能 `resolved`；证据就是票号或提交号，写不进证据就不许解。
2. **会挂着不动的终态**。答了 3 天没人做、或做完了没人标 resolved ⇒ 假滞留。
   建议：`answered` 超 N 天未 resolved 给**低级别提醒**（复用守望者现成的分级机制）；不自动关闭。
3. **压缩会吃掉审计**。压得越狠越查不到"当时为什么这么定"。
   建议：必写摘要行 + 月度归档文件（不是删）。
4. **账本在仓外 ⇒ 唯一副本会丢**。这条压着"归档"的分量：
   只要是"会复发的模式"，**必须先落仓内再压**；顺序反了就是永久丢失。
5. **双份记账的漂移**（你先前问过的那个）。同一事实会在三处出现：议题线程、定稿库条目、票面。
   建议：**状态各管一段**——线程的状态只管"这场对话到哪了"；定稿库里那条的状态才是"这个模式修没修"。
   两者不一致时，**以定稿库为准**（它是给人看、给巡检读的）。
6. **代投的署名**（今天已经踩过）。我替你答的行里，"谁定的"要靠括号里的散文表达。
   建议：三字段（`by` / `via` / `anchor`），且**面板上分列显示**，否则审计时读不出责任。
7. **"到期"会不会静默消音**。红线类的事不能因为过了期就不响。
   建议：到期只影响**显示与提醒级别**，**不改变它是否算未处理**。
8. **身份可伪造的风险面**。会话 id 经注入链送达（调用方 prompt 改不了），但一旦我们把"项目会话可提"
   放开，判据必须**只看登记**，不看自报的字段。这条要在实现里钉死，并配一条反例场景。
9. **跨项目的发现**。一条发现同时关乎两个项目时落哪本账？
   建议：按**问题归属**落到一个项目，并在另一项目落一条**关联行**（一本账一个写者，简单）。
10. **账本的名字会变味**。它将来装的不只是"请求"，还有决定、发现、答复。
    建议：文件名不动（追加式连续性），但**词表在 schema 注释里定死**（"议题/线程/回复/状态/关联"），
    免得下一个读账的人按老名字理解。
11. **巡检读的是旧账**。巡检现在直接读 `notes/debts/known-issues.md`。
    归档层搬进定稿库之后，**这条读取路径要一起改**，否则巡检读的是旧账、新账没人看。
12. **存量 157 条要分类**。整份搬 = 换个房间放垃圾。
    建议：只把"会复发 + 已定案 + 有回归用例"的迁进定稿库（我估 40–60 条），其余留 notes 作历史或清掉。
13. **一实例一条票的老毛病**。这是"永远做不完"的直接来源。
    建议：把"同票同归属已有未终态议题 ⇒ 必须关联"做成机械检查；并给仪盘一条"每票发现数"。
14. **别让它变成聊天**。线程化最容易滑向"什么都往里写"。
    建议：**头**保持窄契约（一次一个决定），散文一律进**回复**。

## 待宿主拍

1. 形态认不认：**一本账两层存放**（仓外工作集 + 仓内定稿归档），还是别的分法。
2. 压缩的**摘要行**要不要（我建议要）。
3. 定稿库里的归档件形态：**每族一页 + 一个索引页**（我建议），还是一个文件。
4. 归档动作归 main 侧（你或我），执行器只提"建议入册"——这条确认一下。
5. 存量 157 条：按"会复发 + 已定案 + 有回归用例"三条筛，我估 40–60 条进定稿库，其余留或清。
