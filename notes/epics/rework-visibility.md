## 一、问题（现状事实，260910 实核）

**打回（rework）只拨阶段指针，不碰工作区文件。**

- 引擎全仓搜无 `reset --hard` / `git stash` / 文件恢复类动作；
  `dev_lane._auto_rework` 只改 meta（stage/role/status/last_rework_note）+ 记账。
- 每段 agent 收工，worker 代落盘提交一次（提交信息带 `gen N`）——
  泳道分支上**已经有一串按代次排列的历史**，回退的原料是现成的。
- 于是打回后下一个 agent 面对的是「上一轮改到一半的树 + 一句文字打回理由」：
  它不知道哪些改动是本轮引入、哪些是更早代的、哪一部分是好的一部分是坏的。
  交接报告是文字，文件是既成事实。

**后果**：跑歪一次之后的实际选项只有两个——让 agent 自己收拾现场（常越收拾越乱），
或整段重跑（浪费额度与时间）。

## 二、讨论与修正（260910，宿主要求写草稿）

初版设想是「时间旅行」：打回时可选连文件一起 `reset --hard` 回第 N 代。

**宿主质疑（成立，本单据此收窄范围）**：如果被打回的是一大片改动、而真正要返工的
只是一小块，整代回退会把好的改动一起丢掉——粗暴且不合算。

**修正后的口径（三档，按风险与收益排序）**：

1. **来路可见（无破坏性，真缺口）**：打回时把「gen N → 当前 HEAD」的差异
   （改了哪些文件、哪一代引入、各自 diff）随派活一并交给接手 agent 与人。
   零破坏，成本=把已有信息摆出来。
2. **按路径选择性回退（收益主体）**：把指定文件/路径恢复成第 N 代的样子，
   其余保持不动——「12 个文件里只有 3 个跑歪」时只回那 3 个。
   人下指令、引擎机械执行，确定性、可审计。
3. **整代回退（兜底武器，窄用）**：仅适用于「整代全废」（选错路子、整段产出是垃圾、
   污染写集外文件）。作为同一能力的破坏性参数存在，界面与文档必须显式标注
   「会丢弃该代之后的全部改动」。

## 三、范围与验收（待审定后细化；此处只定方向）

- 档 1：打回派活载荷含差异摘要 + 完整 diff 落交接报告/证据目录；
  验收=构造「第 2 代改歪、第 3 代接着改」场景，断言接手 agent 的上下文里
  两代改动可分辨（不靠它的自我叙述，靠载荷断言）。
- 档 2：CLI 人门信号（与 sign/rework/pause 同族）指定「源代次 + 路径集合」；
  验收=多文件场景只回指定文件，其余文件内容与 HEAD 一致（逐字节断言）；
  恢复后的树 == 源代次版本（`git diff <源代> -- <paths>` 为空）。
- 档 3：同信号 + 显式破坏性开关；验收=回退后 HEAD 树 == 源代次树、
  未提交脏改动被清、事件历史留下「谁/何时/退到哪里/为什么」。

## 四、红线与约束（提案，待宿主拍板）

1. **只退本泳道自己的提交**：源代次必须属于本票泳道分支，跨票/跨仓一律拒
   （防越权、防误碰 main）。
2. **已被 merge 消费的代次禁止回退**（那等于回退 main）。
3. **破坏性动作只归人门**：与 pause/resume 同族，agent prompt/activities
   无发送入口，代签纪律同现有红线。
4. **回退后必须重新过人门**，不许静默继续往下走。
5. 回退是破坏性能力：实现前需先定**审计与可见性**（写进不可变事件历史 +
   交接报告 + 工单台显式徽标），再谈开关。

## 五、非目标

- 不做「自动判断哪一代该回」——判断权在人（agent 可以提议，不能决定）。
- 不做跨票/跨泳道的历史浏览与回退。
- 不在本单内改动 merge/settle 语义。

## 六、优先级

**低**（宿主 260910 明确：目前看来优先级不高）。理由：
- 它优化的是「跑歪之后的补救成本」，而当前更痛的是「跑歪之前不发生」——
  pause/resume（t260908-01）等段间控制能力更靠前；
- 档 1（可见性）成本低，可作为廉价先行项，独立成一张小票随时插入；
- 档 2/3 属引擎新增破坏性能力，风险面与「只定位不修复」纪律同量级，
  应在段间控制面稳定后再评估。

## 七、待宿主拍板项

1. 是否维持「低优先级、暂不排期」；
2. 档 1 是否先行单独立项（小票，无破坏性）；
3. 档 2/3 的破坏性开关形态（CLI 信号参数 vs 工单台 UI 按钮）与是否需要双人确认；
4. 本单是否与 ticket-pause 合并为同一「段间控制」主线立项。
