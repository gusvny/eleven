## 二、逐条红的判定（三条红 + 四条环境红）

### ① `t260903-10-installer-orphan-claim` —— 测试自身的观察竞态（成立，但改动位置不当）

- 复现：main 原版与泳道改动版**当前均绿**（负载敏感，安静面不复现）。
- 逐行核对泳道改动（相对 main 差 11 行）：把「等 pidfile 文件存在」收敛为「等其内容为数字」，
  超时则显式报「观测缝未就绪，环境/时序面」而非裸 `int('')` 异常。
  **断言强度未放水**（8s 期限与三态语义不变）。
- 根因：场景自建桩的 pidfile 写序为 `open(w)+write`（先截断后写，非原子），
  读者落在截断窗口读到空串 → 场景 exit 1 被计为**假产品红**。
- 判定：**测试自身的观察缺陷**，非产品缺陷；但该文件（`integration/t260903-10/`）是共享测试面，
  按纪律此类修改应由 main 侧统一落一次。→ 尾巴 A。

### ②③ `capture-chat-e2e` / `capture-chat-active` —— **产品缺陷（仲裁报告的「产品面零红」不准确）**

- 报错出处＝`server/ui-check/capture.mjs:714` 的 `assertDistinct`：**产品代码**（截图工具的健全性断言），
  非测试代码。其语义＝逐张比对截图字节哈希，出现**完全相同**即抛异常。
- 该断言已有两处豁免先例（`console-refresh.png`、`console-sessions.png`，均为历史实锤后加入）：
  「同帧是正确行为」的视图应从比对袋摘出。
- 本次撞上**第三例**且未被豁免：板面视图的深/浅两个外观（报告点名 `console-board-light ≡ console-board`）
  → 抛异常 → **整个截图流程当场中止** → 后续「7 视图齐否」「截图在否」连锁失败（故一红即 7 条）。
- 复现对照：泳道内**单独**跑 `capture-chat-active` ＝ 绿（11 张图、`pass=15 fail=0`）；
  两条 capture 场景**并发**跑 ＝ 双红（我做的成对撞实验）。
- 对 main 全量（巡检轨）的连带影响：在 main 主检出里跑时另有「build 陈旧且无法自动重建
  （主检出无 `server/plugins/workbench/node_modules/.bin/tsdown`）」的前置红 → 该场景族
  **无法直接搬到巡检轨**，需先修（→ 尾巴 B 一并处置）。
- 判定：**产品缺陷 + 触发条件=并发/全量**。危害面＝截图是「验收走查」与「UI 证据」的原料，
  工具中止即证据链断。修法（豁免表补项 / 中止语义）在本票写集外，故本票不代修。
