# 知识库设计（Knowledge Base Design）

> 本文件是溯游项目「知识库」的设计定稿，也是「文档先行」原则的第一次实践。
> 变更本文档须走文档 review（§5.2），达成一致后实现才随之调整。

## 1. 定位与总原则

知识库是溯游项目的**活的记忆 + 决策依据**，由 `docs/` 目录承载。三条总原则：

1. **讨论先行，定稿沉淀**（260904 随 doc-lifecycle 立项修订；原「文档先行」原则细化为两段式）：**想清楚**在 `notes/`（讨论稿、决策缘由、epic 追踪——快、糙、volatile，丢了不伤系统）；**确认是真的**才进 `docs/`（本目录，定稿、说人话、遵循写作指南）。沉淀由**验证事件**触发（宿主拍板／工单收口／测试在案即触发，不限时点），不是等大扫除。工单引用铁律：契约内容（做什么、验收口径）自足抄进票面；背景长文档全文引用路径＋**必须已提交且干净**（无未提交改动——泳道读的是 HEAD 冻结副本，脏改版 agent 读不到）；**未提交/带脏改的引用文件=拒建工单**（260904 宿主令，引擎开票闸校验）。
2. **人类大量参与**：文档是人类审阅、决策、协作的主场，所有 UI 都必须为「人看得舒服」服务。
3. **可检索、可链接、可 diff**：每篇可被索引检索；关联文档必须互链；变更必须能以「block 级 diff」供人逐块审阅。

## 2. 目录结构（四类）

`docs/` 下四个目录，一个文档只归一类：

| 目录 | 语义 | 放什么 | 不放什么 |
|---|---|---|---|
| `design/` | **设计** | 溯游 HLD、工单工作流台设计、产品/玩法/内容开发想法、机制设计——一切「想做的东西长什么样、为什么这么做」 | 具体操作步骤 |
| `content/` | **内容运营** | 怎么做内容运营：具体做法、流程、editor 注意事项、写作铁律的展开、管线用法 | 产品/机制设计 |
| `ops/` | **运维** | 系统怎么 build、怎么部署、怎么监控、环境、故障处置 | 设计决策 |
| `reference/` | **参考资料** | 做过的 evaluation、调研、spike 记录、外部资料摘录——「查证用的事实与结论」 | 未成型的想法 |

- 根目录 `docs/README.md` 是人工索引（入口）；`docs/index.json` 是机器索引（脚本生成）。
- 边界不确定时：**设计类归 design，操作步骤归 content，环境部署归 ops，调研/evaluation 归 reference**；仍拿不准就 report，不硬塞。

## 3. Markdown 规范

### 3.1 frontmatter（每篇必带）
```yaml
---
title: 文档标题
category: design | content | ops | reference
tags: [标签1, 标签2]
status: active | draft | deprecated
updated: YYYY-MM-DD
---
```
- `title` = 文档主题（不是文件名）；`updated` = 最近实质修改日；`status` 由 review 流程维护。

### 3.2 互链规范
- 关联文档**必须相互链接**（相对路径，如 `[工单工作流台设计](../design/工单工作流台设计.md)`）。
- 「依赖/被依赖」「取代/被取代」「实践参考」三类关系都要显式写链接，不靠人脑记。
- 索引脚本与 CI 校验死链；改标题/移动文件必须同步改链接。

### 3.3 block 概念
- 一篇文档 = 若干 **block**。block 是 **diff 与 review 的最小单元**（§5.2）。
- **block 类型枚举**（解析 markdown 后逐块归一，文档内容由且仅由这些块组成）：

  | 类型 | 粒度约定 |
  |---|---|
  | frontmatter | 整段 YAML 头为一个块 |
  | 标题 | **每级标题各自独立成块**（`#`–`######` 不合并） |
  | 段落 | 一个自然段为一个块 |
  | 列表项 | **每个列表项独立成块**（嵌套项按自身层级计） |
  | 表格 | **表头独立成块 + 每个数据行独立成块**；同一行内的修改呈现时做到**单元格级对齐** |
  | 代码块 | 一个围栏代码块为一个块（语言标记随块走） |
  | 块引用 | 一个引用段为一个块 |
  | 图片 / figure | 一个图片（或 figure）为一个块 |
  | 分隔线 | 一条 `---`/`***` 为一个块 |

- **稳定身份**：每个 block 的身份 = **（类型 + 序位 + 内容摘要）**。序位 = 同类型块在文中的序号；内容摘要 = 归一化文本的短摘要（如标题文字、段首若干字）。跨轮 diff/rework 再审时按此身份对齐新旧 block，保证上一轮的意见能落到这一轮的对应块上。

## 4. 讨论先行 workflow（260904 修订；原「文档先行 workflow」五步保留骨架，入口改道 notes）

1. **提案**：要做一件新事 → 先在 `notes/discussions/`（或 `notes/epics/`）落讨论稿，讲清「做什么、为什么、怎么做、验收」——快糙起步，不要求成文体。
2. **达成一致**：人类 review 讨论（聊天里拍板即可），改到共识；**验证事件触发毕业**（拍板／收口／测试在案）——确认是真的了，才按写作指南改写成定稿文档迁入 `docs/`，`notes` 侧标「已转立项」。
3. **开工**：docs 定稿 status 转 active（或由人门批准）后，才允许派工单开工。
4. **传 context**：派活时，dispatcher 把相关文档路径 + 摘要写入 agent prompt（「先读 CLAUDE.md + <文档> 全文」）；**agent 不得自主浏览 notes/**（volatile 非其消费面），背景件走票内全文引用。
5. **变更同步**：实现中改了设计 → 先改文档，再改代码；文档是先行真源。若工单当场推翻 docs 条目：随票改（声明写集内）或落债条目登记（过渡机制，写集改革后退役）。泳道写 docs 走窄门：写集内＋同票同步＋过人门；**notes/ 泳道不写**（零依赖双向：不读也不写——agent 过程产物=票内 .suyou/ 结果件＋Temporal 审计）；**纯文档活不开泳道**（规则/术语/epic 类 main 侧直管＋人审即收，260904 宿主问定）。

## 5. UI 需求（人类参与是重点）

### 5.1 markdown render
- 查看文档时**渲染成 HTML**（标题层级、表格、代码块、粗体/斜体、链接、列表），**绝不显示 raw text**。
- 代码块带语法高亮与复制；表格带边框；链接可点。

### 5.2 block 级 change review（渲染态 diff）
- 场景：agent 在 worktree 上改文档、提交人类 review。
- **diff 基线行为契约**：diff base = **git 中该文档的已提交版本**（工作区/分支版本 vs 已提交版本）。**文档无改动时必须显示「无改动」**——不得把未变更的文档整篇算成「新增」。（实现侧曾出现因路径解析少了 `docs/` 前缀导致 base 取空、全文误判新增的 bug；本条是行为契约，实现细节见对应修复工单。）
- **渲染态呈现**：diff review 必须基于**渲染后的 markdown** 呈现——两侧均为渲染态 HTML（标题层级、表格、代码块、列表等按 §5.1 规则渲染），增/删高亮叠加在渲染态之上（新增绿、删除红、修改处内联高亮），**绝不展示 raw 文本行 diff**。表格行内修改按 §3.3 做单元格级对齐。
- **逐 block 审**：按 §3.3 把文档拆成 block，逐 block 标注 新增/删除/修改/未变；人类逐 block **通过 / 驳回 / 注释**，另给**整篇结论**（通过或驳回）。
- 这是「文档先行 + 人类参与」的落点——改动一眼看懂，不用盯 raw diff。

#### review 持久化与迭代闭环
- **持久化**：review 意见**服务端落盘**到 `docs/reviews/` 目录（不再只存在页面内存里）。每轮 review 存一条记录，字段含：**文档路径、diff base（基线提交）、reviewer、时间、轮次、逐 block 的 通过/驳回/注释、整篇结论**。重开同一文档的 review 时能载入历史记录**继续审**（未审完的块保持未决状态）。
- **闭环**：
  1. review 保存后生成可交付的 **「review 结论」** = 驳回块清单 + 各块注释 + 整篇结论；
  2. **dispatcher 据此派 rework 工单**给作者角色（工单 body 附 review 结论与对应 block 身份）；
  3. 作者改完提交，新一轮 diff **以新 base 再审**——block 按 §3.3 稳定身份跨轮对齐，上轮已通过的块默认继承、只重审变更块；
  4. 循环直至**全部 block 通过 + 整篇结论通过**；
  5. 全过后文档 status/frontmatter 流转按 §4 文档先行 workflow（status 转 active 由人门批准，`updated` 刷新）。

### 5.3 现状与差距
- 现状：`suyou-knowledge` 插件已有「知识库」页签（分类/标签/状态过滤 + 关键词检索 + 读全文 + review）。
- 已完成：M1 四目录重构与互链补全；M2 读全文 markdown render（raw→HTML）。
- 差距（M3，按本定稿修订中）：①diff 基线 bug——无变化文档被整篇算成新增（违反 §5.2 行为契约）；②diff 仍是 raw 文本行呈现，未做渲染态 diff；③block 粒度粗（仅小节级），未按 §3.3 枚举细化；④review 意见只存页面内存、不持久化，无 rework 迭代闭环（见 §5.2「review 持久化与迭代闭环」）。

## 7. 与现有系统集成

- **dispatcher 派活**：工单 prompt 强制带「先读 CLAUDE.md + 相关文档」；相关文档由工单 body 明确列出。
- **工单/人门**：design 类文档定稿归用户 review（人门）；实现工单挂 `proposal_id`/文档路径，可追溯。
- **knowledge 插件**：唯一的知识库入口（浏览/render/检索/review/block-diff）。
