# Knowledge Base Design

> This file is the frozen design of the suyou project's "knowledge base", and the first practice of the
> "docs first" principle. Any change to this document must go through document review (§5.2), and implementation follows only after consensus is reached.

## 1. Positioning and overall principles

The knowledge base is the suyou project's **living memory + basis for decisions**, carried by the `docs/` directory. Three overall principles:

1. **Discussion first, sedimentation on freeze** (revised 260904 along with the doc-lifecycle epic proposal; the former "docs first" principle is refined into a two-stage form): **think it through** in `notes/` (discussion drafts, decision rationale, epic tracking — fast, rough, volatile, and losing them does not hurt the system); only what is **confirmed to be true** goes into `docs/` (this directory: frozen, plain language, following the writing guide). Sedimentation is triggered by a **verification event** (a host ruling / a ticket merging in / a test on record all trigger it, at any time), not by waiting for a big cleanup. Iron rule for ticket references: contract content (what to do, acceptance criteria) is copied self-containedly into the ticket body; a long background document is referenced by path plus full text and **must already be committed and clean** (no uncommitted changes — a lane reads the HEAD frozen snapshot, so an agent cannot read a dirty revision); **referencing an uncommitted / dirty-modified file = refuse to create the ticket** (host order 260904, enforced by the engine's ticket-creation gate).
2. **Humans participate heavily**: documents are where humans review, decide and collaborate, and all UI must serve "humans reading comfortably".
3. **Searchable, linkable, diffable**: every document can be indexed and searched; related documents must link to each other; every change must be reviewable block by block as a "block-level diff".

## 2. Directory structure (four categories)

Four directories under `docs/`; a document belongs to exactly one category:

| Directory | Semantics | What goes in | What does not |
|---|---|---|---|
| `design/` | **Design** | suyou HLD, ticket workflow console design, product / gameplay / content development ideas, mechanism design — everything about "what the thing we want to build looks like and why we build it this way" | concrete operational steps |
| `content/` | **Content operations** | How to run content operations: concrete practices, processes, editor notes, expanded writing iron rules, pipeline usage | product / mechanism design |
| `ops/` | **Operations** | How the system is built, deployed and monitored; environments; incident handling | design decisions |
| `reference/` | **Reference material** | Past evaluations, research, spike records, excerpts of external material — "facts and conclusions kept for verification" | half-formed ideas |

- `docs/README.md` at the root is the human index (the entry point); `docs/index.json` is the machine index (generated by script).
- When the boundary is unclear: **design items go to design, operational steps to content, environment and deployment to ops, research/evaluation to reference**; if it is still unclear, report it rather than forcing it in.

## 3. Markdown conventions

### 3.1 frontmatter (required on every document)
```yaml
---
title: Document title
category: design | content | ops | reference
tags: [tag1, tag2]
status: active | draft | deprecated
updated: YYYY-MM-DD
---
```
- `title` = the document's subject (not the file name); `updated` = the date of the last substantive change; `status` is maintained by the review process.

### 3.2 Cross-linking conventions
- Related documents **must link to each other** (relative paths, e.g. `[ticket workflow console design](../design/ticket-workflow-console-design.md)`).
- All three kinds of relationship — "depends on / is depended on", "supersedes / is superseded by", "practical reference" — must be written out as explicit links rather than remembered by humans.
- The index script and CI check for dead links; changing a heading or moving a file requires updating the links in the same change.

### 3.3 The block concept
- A document = a number of **blocks**. A block is the **smallest unit of diff and review** (§5.2).
- **Block type enumeration** (after parsing the markdown each block is normalized; document content consists of these blocks and nothing else):

  | Type | Granularity convention |
  |---|---|
  | frontmatter | the whole YAML header is one block |
  | Heading | **each heading level is its own block** (`#`–`######` are not merged) |
  | Paragraph | one natural paragraph is one block |
  | List item | **each list item is its own block** (nested items count at their own level) |
  | Table | **the header is its own block + each data row is its own block**; changes within one row are presented with **cell-level alignment** |
  | Code block | one fenced code block is one block (the language tag travels with the block) |
  | Block quote | one quoted passage is one block |
  | Image / figure | one image (or figure) is one block |
  | Separator | one `---`/`***` is one block |

- **Stable identity**: a block's identity = **(type + ordinal + content digest)**. Ordinal = the index of the block among blocks of the same type in the document; content digest = a short digest of the normalized text (e.g. heading text, the first few characters of a paragraph). When a later round of diff/rework re-reviews, new and old blocks are aligned by this identity, so that the previous round's comments land on the corresponding block of the current round.

## 4. Discussion-first workflow (revised 260904; the five steps of the former "docs-first workflow" keep their skeleton, with the entrance rerouted to notes)

1. **Proposal**: to do something new → first write a discussion draft in `notes/discussions/` (or `notes/epics/`) covering "what to do, why, how, and how it is accepted" — start fast and rough, with no requirement to be polished prose.
2. **Reach consensus**: humans review the discussion (a ruling in chat is enough) and iterate to agreement; **a verification event triggers graduation** (a ruling / a merge-in / a test on record) — only once it is confirmed true is it rewritten into a frozen document per the writing guide and moved into `docs/`, with the `notes` side marked "converted to an epic proposal".
3. **Start work**: only after the frozen docs status turns active (or a human gate approves) may tickets be dispatched to start work.
4. **Pass context**: when dispatching work, the dispatcher writes the relevant document paths + summaries into the agent prompt ("first read CLAUDE.md + the full text of <document>"); **an agent must not browse notes/ on its own** (it is volatile and not their consumption surface), and background material comes through full-text references inside the ticket.
5. **Keep changes in sync**: if the design changes during implementation → change the document first, then the code; the document is the source of truth that comes first. If a ticket overturns a docs item on the spot: change it with the ticket (declared inside the write set) or file a debt entry (a transitional mechanism, retired after the write-set reform). Lane writes to docs go through a narrow gate: inside the write set + synchronized on the same ticket + passing a human gate; **a lane does not write notes/** (zero dependencies in both directions: it neither reads nor writes them — an agent's process artifacts = the ticket's .suyou/ result files + the Temporal audit trail); **pure documentation work opens no lane** (rule / terminology / epic items are run directly on the main side and closed on human review, as the host decided on 260904).

## 5. UI requirements (human participation is the point)

### 5.1 markdown render
- Viewing a document **renders it to HTML** (heading levels, tables, code blocks, bold/italic, links, lists); **raw text is never shown**.
- Code blocks have syntax highlighting and copy; tables have borders; links are clickable.

### 5.2 Block-level change review (rendered diff)
- Scenario: an agent edits a document in a worktree and submits it for human review.
- **Diff baseline behavioral contract**: diff base = **the committed version of that document in git** (working-tree/branch version vs committed version). **When a document has no changes it must show "no changes"** — an unchanged document must not be counted wholesale as "all new". (On the implementation side there was once a bug where a path resolution missing the `docs/` prefix produced an empty base and the whole document was misjudged as new; this clause is a behavioral contract, and the implementation details live in the corresponding fix ticket.)
- **Rendered presentation**: a diff review must be presented on the basis of **rendered markdown** — both sides are rendered HTML (heading levels, tables, code blocks, lists and so on rendered per the §5.1 rules), with add/delete highlights layered on top of the rendered form (additions green, deletions red, modifications highlighted inline), and **a raw text line diff is never shown**. In-row table modifications use cell-level alignment per §3.3.
- **Block-by-block review**: split the document into blocks per §3.3 and label each block added/deleted/modified/unchanged; humans mark each block **approve / reject / comment**, plus a **whole-document verdict** (approve or reject).
- This is where "docs first + human participation" lands — the change is understood at a glance, without staring at a raw diff.

#### Review persistence and the iteration loop
- **Persistence**: review comments are **persisted server-side** into the `docs/reviews/` directory (no longer living only in page memory). Each round of review stores one record whose fields are: **document path, diff base (baseline commit), reviewer, time, round, per-block approve/reject/comment, whole-document verdict**. Reopening a review of the same document loads the historical records so the reviewer can **continue reviewing** (blocks not yet reviewed stay undecided).
- **The loop**:
  1. after a review is saved, a deliverable **"review conclusion"** is generated = the list of rejected blocks + the comments on each block + the whole-document verdict;
  2. **the dispatcher dispatches a rework ticket** to the author role based on it (the ticket body carries the review conclusion and the identities of the corresponding blocks);
  3. once the author has made the changes and submitted, the new round of diff is **re-reviewed against a new base** — blocks are aligned across rounds by their §3.3 stable identity, blocks approved in the previous round are inherited by default, and only changed blocks are re-reviewed;
  4. iterate until **all blocks are approved + the whole-document verdict is approved**;
  5. once everything passes, the document's status/frontmatter transitions follow the §4 docs-first workflow (the status turning active is approved by a human gate, and `updated` is refreshed).

### 5.3 Current state and gaps
- Current state: the `suyou-knowledge` plugin already has a "knowledge base" tab (category/tag/status filters + keyword search + read full text + review).
- Done: M1 four-directory restructuring and cross-link completion; M2 read-full-text markdown render (raw→HTML).
- Gaps (M3, being revised against this freeze): ① the diff baseline bug — an unchanged document is counted wholesale as new (violating the §5.2 behavioral contract); ② diff is still presented as raw text lines, with no rendered diff; ③ block granularity is coarse (section level only) and not refined per the §3.3 enumeration; ④ review comments live only in page memory and are not persisted, with no rework iteration loop (see §5.2 "Review persistence and the iteration loop").

## 7. Integration with existing systems

- **Dispatcher dispatching**: the ticket prompt mandatorily carries "first read CLAUDE.md + the relevant documents"; the relevant documents are listed explicitly in the ticket body.
- **Tickets / human gate**: freezing a design-type document rests with user review (human gate); implementation tickets carry `proposal_id`/document paths and are traceable.
- **The knowledge plugin**: the single entry point to the knowledge base (browse / render / search / review / block-diff).
